# 局面分析資料層

這是一套把素材整理成「可比較、可推論、也可被推翻」的資料結構的方法，源自對劉仲敬論述方式的拆解。資料層和產出分開：同一份資料可以拿來改寫章節、寫新章、審稿，或寫單篇文章。

範例：`plan/tsmc/cases.yml`、`plan/tsmc/mechanisms.yml`。

## 適用範圍

素材必須同時滿足兩個條件：

1. 有行動者在做選擇：誰依賴誰、誰承擔代價、誰能定義規則。
2. 結論無法用實驗直接驗證。

| 書的類型 | 用哪幾層 |
|---|---|
| 產業史、公司競爭 | 四層全用：局面、意義框架、論證、場景 |
| 組織與權力 | 局面＋意義框架，場景要節制 |
| 技術設計取捨 | 只用角色、承諾、代價；不用歷史敘事的語氣 |
| 純機制、程序類 | 不適用 |

## 兩個檔案

**`cases.yml`：案例層。**只記局面，不記結論；機制連結只寫在 `mechanisms.yml`。

| 欄位 | 必填 | 說明 |
|---|---|---|
| `id`、`title`、`period` | 是 | |
| `evidence_status` | 是 | `verified`、`partial` 或 `unverified` |
| `roles`、`relations` | 是 | 角色與依賴關係 |
| `options`、`choice`、`outcome` | 視情況 | 選擇空間、實際選擇、結果 |
| `uncertain` | 是 | 存疑處；沒有出處時寫明缺什麼 |
| `sources` | 是 | 可為空，但要由 `uncertain` 說明 |
| `stated_reasons`、`contested`、`facts`、`feasibility_of_alternative` | 否 | 當事人自述、爭議、數字、替代方案是否可行 |

**`mechanisms.yml`：機制、意義框架與測試。**

- `mechanisms`：`hypothesis`、`prerequisites`、`causal_path`、`alternative_explanations`、`disconfirming_observations`、`boundary`、`supports`、`challenges`、`scene_seed`、`return_point`、`status`
- `frames`：同一個詞在不同位置上的讀法，描述與評價分開存
- `tests`：兩個表面相似的案例，機制必須給出不同的解釋

另有兩個 Markdown 檔：`voices.md`（外部聲音）與 `stance.md`（立場），格式見下方規則。

起始骨架見本目錄的 [`cases.yml`](cases.yml) 與 [`mechanisms.yml`](mechanisms.yml)。

## 規則

- **跨案例：**至少 1/4 的案例來自主題之外。建卡時要問：「還有誰在不同條件下面對同一個機制？」
- **反例：**每個機制至少一個 `challenges` 案例。沒有反例或只有單一支持案例的機制，標 `status: weak`；產出時可以寫成推測。
- **區辨力：**每個 `tests` 都要是 `pass` 或 `pass_weak`，`pass_weak` 要寫明弱在哪。過不了就把機制降為弱機制，不要硬湊。
- **描述與評價分開：**「背叛」「成功」「不可替代」這類詞是框架下的讀法，放進 `frames`。
- **證據措辭：**正文的事實敘述裡，報導或傳聞寫成「報導」或「時序吻合」，不寫「原因是」。沒查證的全稱說法（「第一次」「再也沒有」）不寫。
- **外部聲音：**定立場前，先找業內有聲量或有啟發的人（創辦人、架構師、對手、政治人物、評論者）對這個主題最尖銳的說法，記在 `plan/<name>/voices.md`：原話、日期、出處、利害關係、提取的立場。只收找得到原文或可靠轉述的話。要找正反兩方，最強的反方也要收。選聲音看它能不能推出新的判斷或帶出新事實，不看說得夠不夠尖銳。
- **立場：**先讀聲音，再定立場。已經有立場時，專門去找可能推翻它的聲音，讀完再決定保留、修正或換掉，並把決定和理由寫進 `stance.md`。每本書在 `plan/<name>/stance.md` 寫下一個偏頗但站得住的核心主張，優先從 `voices.md` 借來並註明出處，列出撐住它的事實和要正面處理的反例；最強的反方聲音也寫進去。
- **借用要點名：**外部聲音的原話寫進正文，標明是誰、何時、在哪說的，必要時註明利害關係（例如他賣的正是替代品）；借他的框架當詮釋時，在詮釋框裡點名。正文只引能推動立場或帶出新事實的幾則；其餘留在 `voices.md` 當推理材料，不把找到的都貼進正文。偏頗表現在選哪一方當立場、哪一方當反方，不表現在隱去出處。詮釋框都替這個立場說話：延伸它、用它解讀事實，或回應反例。沒有立場的詮釋只是單點機靈，再多也不會有啟發。
- **事實、不拘小節、偏頗：**
    - 事實從嚴，偏頗只能在選材和解讀，不能在事實；對立場不利的事實照寫在正文，由詮釋正面回應，不藏起來。
    - 不利的事實要主動去找，不只是不藏。立場定下後，專查同一時期對立場最不利的交易、數字和事件（例如供應商同時付錢給「正在離開」的客戶），寫進正文。
    - 論據要能直接推出結論。只是方向一致、但另有更直接解釋的事實（例如依客戶總部計的營收占比，被拿來證明政府給了特權），不能當立場的證據；照寫在正文當事實，在 `stance.md` 記下它為什麼不當論據。找不到直接證據時，去查，不要拿方向一致的事實頂替。
    - 不拘小節：不改變結論的細節不保留、不加但書，不在每個詮釋框附推翻條件。
    - 跨時代、跨領域的比喻和大膽推測可以寫，但只放在詮釋框，不當事實的證據。
- **時效：**時程、市占、排名要查最新來源。
- **場景：**只描寫角色的處境與選項，不替真實人物編內心戲或台詞。

## 檢查

```bash
uv run python tools/check-situation-data.py plan/<name>
```

會列出缺漏的案例引用、沒被引用的案例、沒有反例的機制、各測試狀態，以及各證據等級的案例數。

## 產出方式

| 用途 | 做法 |
|---|---|
| 改寫既有章節 | `/mkdocs-liu-rewrite` |
| 寫新章或新書 | 先建資料，再用 `/mkdocs-update` 或 `/mkdocs-create` 寫；詮釋框依下方格式 |
| 審稿 | 拿既有章節的每個推論對照 `mechanisms.yml`，找不到支撐的就列為問題 |
| 單篇文章 | 從一個機制和它的 `supports`、`challenges` 取材 |

章節裡的詮釋寫在 `!!! note "詮釋"` 裡（弱機制寫成推測，同樣放在這裡），場景寫在 `!!! example "示意場景"` 裡，並在提示框正上方放 `<!-- mech: <id> -->`、`<!-- frame: <term> -->` 或 `<!-- test: <id> -->`，讓每個推論都能追溯回資料。
