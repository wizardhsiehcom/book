# 第二篇：沒收到回覆，可以再按一次嗎？

日期：2026-09-28。依候選順序接續資料庫第 15–16 章。

## 目標與界線

讀者能分開客戶端的「未知」與資料庫的提交狀態，保留原 operation ID、完整意圖與 expected_version，並辨認舊操作結果和目前判定。

沿用本書 ApplyJudgment 契約。固定缺陷 2、初始版本 0，操作 X 意圖為 `(2, 0, 80, m1, lin)`。X 是 UUID 的教學簡稱。操作紀錄保留、權威資料庫與程序相同；沒有其他寫入，除明示的 Y 重判。互動呈現受控事件順序，不執行 SQL、不模擬鎖排程或網路。

## 分鏡

| 頁 | 問題 | 圖解或操作 |
|---|---|---|
| 1 | 沒有成功回覆代表失敗嗎？ | 客戶端未知／資料庫遮住 |
| 2 | 同一個錯誤能來自哪些過程？ | 提交後丟回覆、提交前斷線且伺服器完成回滾，兩條時間線 |
| 3 | 新連線查不到，就能建立新 ID 嗎？ | 預測題，說明無紀錄不足以證明回滾 |
| 4 | 重送要帶什麼？ | 固定 X 與五欄完整意圖，包含 expected_version |
| 5 | 重送怎樣與原交易協調？ | 同 ID 序列化判斷：已提交回舊結果；回滾且版本仍符才首次提交；未結束則等待 |
| 6 | 換故障窗口，結果如何？ | 四種受控情境；逐步看故障、原 ID 重送、結果或等待逾時 |
| 7 | 換 ID 又改版本會怎樣？ | 已提交後：只換 ID 被版本擋下；連版本也改才可能重複判定 |
| 8 | X 的結果和目前結果一樣嗎？ | X=80/v1，Y=90/v2，再送 X 回 80，現在仍 90 |
| 9 | 仍查不清楚時怎麼做？ | 保留未知、有限重試、待查核；回 15／16 與 L06 |

## 實作與驗收

- 新增 `docs/database-correctness/resources/unknown-outcome/` 的三個主題檔案；第 15、16 章新增入口。
- 使用共用 reader、原生 select/button、CSS 對照卡片。互動保存步數，換情境重設，離頁清理，提供靜態縮圖。
- 固定情境資料只保存事件後的受控快照，避免做出第二套資料庫程序。留下最小 Node 檢查，驗證顯示狀態、重送不新增、等待仍未知、掛載清理。
- 同步後嚴格建置；實際瀏覽器查 9 頁、窄版、兩倍文字、減少動態、互動返回、鍵盤、章節路徑與搬移後資產。
- 查核備料放 [database-sources.md](database-sources.md)；視覺與測試產物放 `data/visual-story/database-validation/`。
- 讀者試讀另記；不以畫面測試聲稱學習成效或真實 SQL 故障驗證。

實作、嚴格建置、自動檢查與瀏覽器驗收完成；驗收結果與範圍見 [驗收紀錄](database-verification.md)。
