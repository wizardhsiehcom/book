## 1. 目標與選題原則

讓讀者看見文字中省略的中間過程，讀完能預測換一組條件後的結果。每篇聚焦一個問題，從章節開啟，最後回到章節或實驗。

優先挑選有時間順序、空間結構、狀態轉移或參數取捨的內容。每頁只增加一個認知步驟；靜態圖已足夠時，就使用靜態圖。頁數依理解需求拆分。

## 3. 第一篇：一句話，怎樣才算收齊？

### 讀者與終點

讀者會看簡單函式呼叫，但還不熟 socket 與 framing。入口是第 08 章的「send 回了 40，對端只拿到 11 bytes」。

讀完應能：

1. 說明一次 send、一次 recv 與一筆訊息的邊界不必一致。
2. 看接收切段，指出哪些訊息能交出、哪些尾巴要保留。
3. 說明連線仍開著、收到 EOF、收齊訊息與業務完成各自代表什麼。
4. 回到第 09 章，辨認長度前綴與換行定界是在解同一種邊界問題。

### 已知資產與採用方式

- `playground/dist/tcp-story.js`：已有 HELLO／WORLD 的十頁故事與預測題。保留能講清楚的敘事及圖形，正式主題檔名統一為 `story.js`／`story.css`。
- `playground/dist/tcp-story.css`：沿用條帶與緩衝區的視覺語言；搬入前檢查選擇器，改為主題前綴，避免干擾 reader。
- `playground/dist/app.js`：另有切段模型與自檢，可抽取必要邏輯；不搬入整個 A／B／C 比較介面。
- `templates/visual-story/index.html`：作正式入口，沿用共用 reader 的翻頁、縮圖、索引與題目能力。
- `docs/systems-network-foundations/examples/l05_framing.py`：正式長度前綴實驗的參考；故事不假裝在瀏覽器裡執行真 TCP。

規劃時只完成原始碼盤點；後續正式實作與視覺驗收範圍見 [驗收紀錄](verification.md)。原始資料盤點詳見 [tcp-existing-demo.md](tcp-existing-demo.md)。

### 技術敘事界線

- 40／11 是開場情境；接著明確切換到 12 bytes 的 ASCII `HELLO\nWORLD\n` 教學串流。兩組數字不混用。
- `↵` 是換行 byte 的視覺符號；內容約定不含換行。真實文字不能普遍用 JavaScript 字串長度代替 UTF-8 byte 數。
- 演示控制的是餵入解析模型的切段，不是要求真 socket 固定按該大小回傳。
- 同色／異色只幫作者說明原始訊息；接收端實際拿到的 bytes 沒有訊息顏色。揭曉前不靠顏色偷渡邊界。
- `send` 成功不證明對方應用收到或完成工作；ACK 也不是業務回條。
- 正常 stream 以正數接收上限讀取時，空 bytes 表示 EOF，對端不再於該方向送來資料；不能推論雙向皆關閉或訊息已完整。保留半關閉的語意，排除 `recv(0)`。
- 第 09 章正式契約是 4 byte 大端長度＋UTF-8 JSON、64 byte 正文上限；故事只在最後建立對應與連結，不再實作第二套完整協定教學。

## 4. 第一篇分鏡草案

| 頁 | 讀者要跨過的步驟 | 圖解／操作 | 帶走的理解 |
|---|---|---|---|
| 1 | 遇到原章問題 | 並排 send=40、首次 recv=11；其餘位置標「目前無法僅憑這兩個數字判定」 | 呼叫成功與訊息完整需要不同證據 |
| 2 | 換成容易追蹤的小例子 | 送端原本有 HELLO 與 WORLD；標示先不加分隔符 | 送端知道的兩筆，不會自動成為接收端的邊界 |
| 3 | 站在接收端預測 | 只顯示 HE，使用 reader 的選擇題並遮住後續縮圖 | 目前無法確定訊息是否完整 |
| 4 | 看見跨邊界接收 | HE ＋ LLOWO，接收端視角先以同一樣式顯示 | 一次 recv 可能跨越原本兩筆資料 |
| 5 | 補上雙方約定 | 重新開始，送出 HELLO↵WORLD↵，說明現在共 12 bytes | 換行是雙方約定的資料，不是 TCP 自帶邊界 |
| 6 | 保存還不完整的尾巴 | HE 留在 buffer；已完成區保持空白 | 沒找到約定邊界，先保留 |
| 7 | 取出一筆但保留下一筆 | 收到 LLO↵WO，取出 HELLO，留下 WO | 不能把本次 recv 全部當成同一筆 |
| 8 | 完成第二筆 | 接上 RLD↵，取出 WORLD | 三次接收可以組成兩筆訊息 |
| 9 | 親手改切法 | 預設切段 [2,6,4]，另選全部一次／逐 byte；下一段、重設 | 切法改變，完整串流的解析結果不變 |
| 10 | 分開「等待」與「結束」 | 對照尾巴 WO 且仍開著／同樣尾巴但收到 EOF | 前者繼續等，後者依本例契約是截斷 |
| 11 | 對回正式教材 | 換行與長度前綴兩張簡圖；連回 08、09 與 L05 | framing 由應用契約決定；收齊也還不代表業務完成 |

頁數可以隨版面拆分。第 09 頁是唯一必要的操作模型，其他頁用靜態 HTML／SVG 與既有預測題即可。

## 5. 視覺與互動決策

- 每頁維持「這次收到 → 緩衝區 → 已完成訊息」的穩定位置，減少讀者重新找物件。
- byte 區用等寬字；狀態同時有文字與外形，避免只靠顏色。
- 先做第 03、07、09 頁，分別確認預測、資料移動與控制項三種版型，再補其餘分鏡。
- 手機版改為直向排列，完整顯示短字串。文字放大後拆行，不縮字硬塞。
- 不需自動播放、3D 或外部動畫庫；必要動態由按鈕推進，減少動態效果偏好下仍可理解。
- 互動使用原生 button／select。`mount(root, state)` 保存當頁進度並同步回傳事件清理函式；提供靜態 `previewArt`。
- 翻頁再返回保留狀態；當頁「重設」明確清空。沿用 reader 的既有重播語意，不私自改成全域清空題目。

若版面效果不確定，先在正式主題的三個代表頁預覽與截圖，記錄問題再改。參考素材及驗證截圖放 `data/visual-story/`，不用另建一套展示框架。

## 8. 實作順序與驗收

1. **資料定稿**：核對兩份研究紀錄，把需要保留的來源與界線寫入分鏡。
2. **代表頁**：以既有模板做第 03、07、09 頁，桌面與手機檢查文字、條帶、縮圖和索引遮擋。
3. **完整故事**：補齊分鏡、互動、來源、章節入口與返回路徑。
4. **模型驗證**：留下最小可重跑檢查，直接驗證正式故事使用的切段邏輯，不另複製一份演算法當測試。涵蓋所有完整串流切法結果一致、保留半筆尾巴、單次多筆、EOF 截斷及重設。
5. **工程驗證**：執行下列既有命令；其結果分別記錄，不以舊 playground PASS 代替正式主題通過。

```bash
node tools/check-story-reader.cjs
uv run python tools/check-story-package.py
./sync-assets.sh
uv run mkdocs build --strict -f configs/systems-network-foundations.yml
```

6. **正式產物驗收**：從建置後第 08 章進入，依序翻完、返回、索引跳頁、釘選、重播與作答；驗證第 09 章連結。互動離頁無殘留事件，返回狀態正確。
7. **視覺與可攜驗收**：桌面與窄螢幕、200% 文字放大、鍵盤、減少動態效果；複製完整建置目錄至暫存位置，檢查故事及書內返回。主題本身不需網路，不據此宣稱整本書所有 Mermaid／外連都能離線。
8. **教學驗收**：換一組未示範的切段，要求指出完整訊息與尾巴；再問 EOF 與業務完成。沒有讀者試讀時，只能記錄作者自查，不能宣稱已證明學習成效。

驗證紀錄要區分自動檢查、實際瀏覽器觀察、未測項。截圖留 `data/visual-story/validation/`；簡短結論及重跑方式留在本計畫旁的驗收紀錄。
