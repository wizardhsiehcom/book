## 定位：用一個小動作，把下一步變得明確

這是一本放在電腦旁邊翻的診斷與救援書。讀者遇到「明明 COPY 了卻找不到」「容器一跑就死」「改設定沒生效」「log 一片空白」「只有這台特別慢」，能先做一個局部、可撤回的動作，得到可觀察的差異，再理解必要機制。

書的價值是判斷：什麼時候值得繞過入口、保留退出容器、固定輸入、借別人的工具、暫時拿掉掛載、故意放慢依賴。每招說清楚省掉的工作，以及轉移到人工、磁碟、同步、等待或觀測失真的成本。硬編碼與臨時檔案可以出場，但要交代它們何時失去代表性。

不按 image／container／network／volume 的 API 分類編排。Dockerfile 和 CLI 的概念只在讀者已經看見小成果後補上。也不靠導購、付費診斷工具或「業界最佳」口號支撐內容；廠商來源只取可核對的機制與操作，不採改善百分比為本書承諾。

## 讀者、場景與邊界

- **讀者**：會 build、run、logs、exec，能看簡單 Dockerfile／Compose YAML；懂檔案路徑、環境變數和 stdout，但沒有大量現場排錯經驗。會一種腳本語言即可；實驗以少量 Python 與 shell 為主。
- **主要場景**：本機開發、CI 建置、單機 Compose 部署與維運診斷。把生產問題縮到隔離副本後操作；不把線上服務當故障注入實驗場。
- **平台**：主線是 Linux containers；以原生 Linux 為基準，Desktop macOS／Windows WSL 2 另寫差異。原生 Windows containers、Swarm、Kubernetes、GPU／模型訓練先不納入。
- **版本**：不虛構一套「已驗證最低版本」。寫作時記錄實測 CLI、Engine、Compose、Buildx、BuildKit、host OS、CPU、Desktop/VMM、image digest；歷史 issue 的版本只屬該案例。
- **閱讀方式**：可按症狀跳讀；每章最多一招主動作，相關操作作反例或延伸。預計每章 1,800–2,600 字，主文約 2.3–3.4 萬字，加四份短附錄；這是篇幅目標，不是已完成字數。

## 選題怎麼收斂

研究後保留 13 個問題：有第一手案例的掛載、入口、I/O、日誌與 stdin；有明確官方機制且可做短對照的停止取檔、build stage、局部 cache、就緒時序、訊號處理。後一類明確標「機制支持＋編輯提出實驗」，不假裝發生過本書作者的事故。

不把 export、每個 log driver、每種 cache 各湊一章；export 放在取檔反例，driver 放在日誌判斷，cache mount 留作延伸。慢日誌接收端等尚缺可控實驗的題目暫不進主線。完整決策見 [selection.md](../../data/docker-field-tricks/selection.md)。

## 每章固定節奏與標記

**現場症狀 → 小招式 → 必要原理 → 親手實驗 → 結果解讀 → 失效反例 → 收尾與撤回。** 先展示一個小差異，再談原理；提醒只放在會改變操作決策的地方，不寫成漫長前置警語。

章首用四種標記，可複選：

- **現有功能**：工具原本就有，直接指定參數或設定。
- **需要新增程式**：例如測試 wrapper、固定輸入解析器；明寫是本書新增。
- **需要重新建置**：變更 image 才需 build；重新建立 container 另寫「需重建容器」，不混用兩者。
- **版本／平台限定**：說明已知限制；沒有核實的最低版本列待驗，不猜。

所有章節的「預期」都是待測假設。親手實驗的時間目標為 5–15 分鐘（不含下載）；T11 I/O 多輪測量可到 20 分鐘。若實際達不到，縮減 fixture，不刪掉必要對照。

## 第 01 章｜明明 COPY 了，先把掛載拿掉

**標記**：現有功能；fixture 需要建置；測試副本需重建容器。**來源**：C01、M01。

1. **現場症狀**：build 成功，執行時腳本卻不見；繼續改 Dockerfile 可能浪費整輪建置。
2. **小招式**：固定同一 image ID，查看 Mounts，再開一個不帶該 bind mount 的副本；不要先重建 image。
3. **必要原理**：掛載遮住目標路徑；它沒有刪掉映像的原檔。bind source 是 daemon 端路徑。
4. **親手實驗**：小映像的 `/app/marker` 放 A，主機測試目錄放 B。A 組不掛載，B 組掛該目錄，比較讀到內容；再故意寫錯來源，用 `--mount` 預設報錯作補充。記錄 image ID、Mounts、檔案內容與退出碼。
5. **結果解讀**：拿掉掛載後 A 回來，只支持遮蔽假設；不能證明整個 app 正常。若兩組都缺檔，轉第 08／09 章。
6. **失效反例／前提與代價**：fixture 不宣告 VOLUME，避免另一層掛載混淆；遠端 daemon 路徑與本機不同。無掛載失去 live reload，換到重建與同步成本。
7. **收尾與撤回**：移除副本，還原開發掛載。若反覆發生，正式整理掛載用途與配置核對；不以清 volume 解決所有問題。

## 第 02 章｜改了設定沒用？先印出它真正吃到的值

**標記**：現有功能；需重建測試容器；config 選項依安裝版本核對。**來源**：C08、M03–M06。

1. **現場症狀**：修改 `.env` 後 restart 多次，程式仍顯示舊值；原成本是反覆猜覆寫來源。
2. **小招式**：用完全相同的 `-f` 順序與明確 `--env-file` 跑 `docker compose config`；另看 `config --environment`，再比容器實際值。
3. **必要原理**：插值、Compose 合併、建立容器和應用讀配置是不同步驟；restart 不等於套用新模型。
4. **親手實驗**：只用假變數 `FIELD_MODE`，依次設 env-file=A、shell=B，查看渲染差異；建立容器後改為 C，對照 restart 與指定 service 的 `up -d`，必要時用 `--force-recreate` 明確重建。存 container ID 與應用輸出值，不保存真實 secrets。
5. **結果解讀**：模型是 C、容器仍 A，問題在套用步驟；容器 C、程式仍 A，應查程式讀法。config 成功只證明配置可處理，不證明服務可用。
6. **失效反例／前提與代價**：C08 是舊版轉義差異，不能宣稱今日仍壞；不把渲染檔當無損模板。重建中斷服務並失去可寫層，所以在測試副本做。
7. **收尾與撤回**：恢復 env 與檔案、刪去敏輸出；再以同一配置重建副本。反覆需求可正式化成部署前的配置比較，但不要把機密輸出放進 CI log。

## 第 03 章｜容器死了，先把檔案拿出來

**標記**：現有功能；測試程式需新增；取檔不需 shell／重建 image。**來源**：R03–R05、RT2–RT3。

1. **現場症狀**：exec 進不去，想重跑才能看結果；但重跑會覆寫產物或重送工作。
2. **小招式**：對尚未刪除的停止容器，先 `docker diff` 找改動路徑，再 `docker cp` 拿特定檔案。
3. **必要原理**：停止不是刪除；檔案可寫層、掛載資料、程序記憶體分開看。
4. **親手實驗**：fixture 寫一個帶 run ID 的結果檔後 exit 1，分「保留容器」與 `--rm` 兩組；對保留組 cp 後核對 run ID。側欄在映像與 volume 放不同 marker，export tar 看哪個出現。
5. **結果解讀**：取到檔案證明該檔仍可讀，不代表程序記憶體還在或資料交易一致。diff 的 A/C/D 不提供誰寫、何時寫的完整因果。
6. **失效反例／前提與代價**：`--rm` 後已無同一現場；特殊檔案和 tmpfs 有限制；export 不含掛載 volume。保留失敗容器占空間，取檔也可能含敏感資料，所以只收指定產物。
7. **收尾與撤回**：核對產物後移除本次容器與暫存；頻繁需求正式化為失敗產物收集，而不是永遠堆積故障容器。

## 第 04 章｜一啟動就退出，先別讓它跑主程式

**標記**：現有功能；fixture 需建置；需重建診斷容器。**來源**：C03、M08、R10/R12。

1. **現場症狀**：entrypoint 立即失敗，還沒看清環境就退出；重試只能看到同一句錯誤。
2. **小招式**：在副本明確覆寫 entrypoint 為映像已有的 sleep，給有限秒數，再手動跑原入口。
3. **必要原理**：command 與 entrypoint 不同；留下進程只是爭取時間，初始化步驟未必執行。
4. **親手實驗**：fixture 入口檢查一個不存在的測試檔後失敗。固定 env/user/mount，替代入口留下副本，再 exec 原入口，核對能否重現相同錯誤。將診斷與正常啟動的 inspect 差異列出。
5. **結果解讀**：手動也失敗可支持檔案／設定假設；手動成功要追 wrapper、工作目錄與初始化差異，不能說只是 Docker 不穩。
6. **失效反例／前提與代價**：scratch／distroless 可能無 sleep 或 shell，轉第 03／05 章；新副本不是原容器的故障記憶體。跳過初始化換來人工重建步驟。
7. **收尾與撤回**：刪副本及 override，確認正式入口仍是原應用。反覆需求才做獨立 debug stage，與發布 target 明確分開。

## 第 05 章｜裡面沒有 curl，從旁邊借一套

**標記**：現有功能；Linux containers；工具映像需符合架構，不需改正式 image。**來源**：R01/R02、RT1。

1. **現場症狀**：極簡映像連 shell 都沒有，想測 localhost 卻準備重新打包工具。
2. **小招式**：一次性工具容器以 `--network container:<target>` 發送同一個請求。
3. **必要原理**：加入同一 bridge 與共用 network namespace 不同；後者才共用 loopback。
4. **親手實驗**：測試服務只 bind 127.0.0.1。A 組工具在同 bridge 對目標 IP 發請求，B 組共享 namespace 對 localhost；記錄成功／失敗和 HTTP 內容。再改成 bind 0.0.0.0，檢驗 A 組是否恢復。
5. **結果解讀**：B 成功可縮小 bind 位址／路徑問題；不能代替原程式的 TLS、proxy、認證與 DNS 函式庫測試。
6. **失效反例／前提與代價**：target 需活著且同 daemon；工具有自己的檔案系統與憑證。會增加一個工具容器及測試流量；普通 curl 不靠 privileged。
7. **收尾與撤回**：工具退出即移除；固定好用的工具 digest 與一條命令即可正式化，不把整套工具灌進每個正式映像。

## 第 06 章｜logs 沒字，先讓程式把字吐出來

**標記**：Python 開關為現有功能；fixture 需新增；driver 變更需重建容器。**來源**：C05、M11、R06–R08、RT4。

1. **現場症狀**：程式還活著，logs 要等退出才出現；原成本是誤查 driver、網路或服務啟動。
2. **小招式**：先以 Python `-u` 對照；仍沒有，再確認程式寫 stdout/stderr 還是檔案。
3. **必要原理**：應用緩衝、輸出目的地、Docker driver、遠端接收是不同階段。
4. **親手實驗**：固定版本 Python，每秒輸出一個帶時間的序號，不開 TTY；A 正常、B 加 -u。記首筆可見時間與退出時輸出。C 組改寫檔案，以 cp 看見 sentinel，但 logs 應看不到該檔內容。
5. **結果解讀**：B 提早可見支持緩衝假設；不能證明遠端收集沒有遺失。只看完畢後行數會漏掉「延遲但未丟」的差異。
6. **失效反例／前提與代價**：其他語言與 logging handler 不一定吃此開關；取消緩衝可能增加輸出開銷。dual logging cache 不是可靠斷線備援。
7. **收尾與撤回**：恢復輸出設定並刪副本。確有即時觀測需求才正式設定應用 logger；non-blocking 換延遲留延伸題，需同時量丟失。

## 第 07 章｜不走介面，餵同一份輸入再跑一次

**標記**：現有功能＋需要新增測試解析器；無需建置大型服務；歷史 Compose 行為依版本核對。**來源**：C06/C07、M08。

1. **現場症狀**：反覆點 UI 或重跑整批才能得到一次失敗；保存的輸入重導又碰到 TTY 問題。
2. **小招式**：把一筆去敏失敗輸入存成 fixture，交給讀 stdin 的命令；明確 `-T`。不讀輸入的診斷命令則接 `/dev/null`。
3. **必要原理**：TTY、stdin 和應用輸入格式分開；這是 Docker 提供執行入口，重播能力仍來自程式接受輸入，沒有內建萬用 replay 開關。
4. **親手實驗**：獨立 Compose 測試服務讀一筆 JSON、輸出指定欄位。固定 fixture checksum，兩次 run 比較 exit code、stdout/stderr 與欄位。再送一筆格式可讀但缺必要欄位的資料。側欄以 shell 前後標記對照「預設 stdin／-T／接 /dev/null」，檢查後半腳本是否真的執行。
5. **結果解讀**：成功輸入只證明傳輸入口通了；C06 的 tags 問題提醒語意仍可錯。固定輸入不涵蓋真實時序與併發。
6. **失效反例／前提與代價**：只支援互動 UI 的應用需新增入口；run 沿用的 volume／網路可能有副作用，故使用無真憑證、無外部資料卷的測試配置。`--no-deps` 不等於隔離。
7. **收尾與撤回**：刪一次性容器與不再需保留的 fixture；重要失敗案例可去敏後正式收為回歸資料。stdin 要給誰就明確指定，避免用 -T 假裝關掉輸入。

## 第 08 章｜找不到檔案，先換 build 的那個點

**標記**：現有功能；需要重新建置小型 fixture。**來源**：C02、M02。

1. **現場症狀**：Dockerfile 搬到子目錄後 COPY 失敗，開始搬檔案與亂加 `../`。
2. **小招式**：固定根目錄 context，用 `-f` 指定 Dockerfile；再以最小檔案集合確認「builder 看得到什麼」。
3. **必要原理**：Dockerfile 所在處不等於 context 根；ignore 決定可用檔案集合。
4. **親手實驗**：根目錄放單一 marker、子目錄放 Dockerfile，COPY 後印 marker。對照以子目錄／根目錄作 context；再用 ignore 刻意排除 marker，最後恢復。用 plain build log 與產物內容核對。
5. **結果解讀**：換 context 後成功，指向輸入集合；不能證明原 repo 沒有其他路徑錯誤。C02 原始例有多個問題，本書只隔離一個。
6. **失效反例／前提與代價**：放大 context 有傳輸與誤帶檔案成本；ignore 過度排除會製造另一種缺檔。不要以「永遠全包 tar」描述所有 BuildKit。
7. **收尾與撤回**：恢復測試檔與 ignore；常用命令回到專案原有 build 腳本，不另造一個通用建置框架。

## 第 09 章｜不必跑到最後，建到上一站就停

**標記**：現有功能；需要命名 stage，必要時修改 Dockerfile 並重新建置。**來源**：M07/M13。

1. **現場症狀**：build 成功但 final image 少檔案，重新跑全部依然不知道在哪丟失。
2. **小招式**：`--target` 建到已成功的前段，以明確 tag／`--load` 留在本機檢查。
3. **必要原理**：multi-stage 的產物只按 COPY 關係傳遞；BuildKit 處理目標的相依階段，不保證跑每個無關 stage。
4. **親手實驗**：build stage 產生 binary marker 與設定檔，final 故意只 COPY marker；對照前段／final 的檔案清單，補上漏 COPY 再驗證。記 stage 名、image ID 和檔案 checksum。
5. **結果解讀**：前段有而 final 無，縮小到交付邊界；前段沒有則回頭查產生步驟。
6. **失效反例／前提與代價**：不能把失敗 RUN 當可進入的成功 stage；要在它之前建立檢查點。debug stage 多一個維護面，可能帶工具與敏感中間產物，不發布到正式用途。
7. **收尾與撤回**：移除診斷 tag，恢復正式 target；經常需要才保留命名中間階段與產物核對。

## 第 10 章｜懷疑快取，只讓那一段重跑

**標記**：現有功能；需要重新建置；nonce ARG 是自訂；`--no-cache-filter` 依 CLI 支援確認。**來源**：M10/M13/M14。

1. **現場症狀**：改了輸入卻仍是舊產物；全清 cache 會丟掉其他昂貴成果，且可能掩蓋真正條件。
2. **小招式**：命名可疑 stage，只對該 stage 指定 no-cache-filter；以 plain log 核對哪一步真的重跑。
3. **必要原理**：layer cache、套件 cache mount、base image 與外部下載是不同狀態。secret 的內容不是 cache key。
4. **親手實驗**：完全使用假 secret 的 A/B 值，讓命令依它產出非敏感 marker；先只換假 secret，再對該 stage 停用 cache，比較 marker 與命中狀態。第二輪換成不含秘密的版本 nonce；不把 token 本身塞進 ARG。另放無相依的階段觀察是否受影響。
5. **結果解讀**：指定 stage 重跑後結果改變，支持該 build 邊界有未入 key 的輸入；不是宣告 Docker cache 有 bug。依賴它的下游可能也需重算。
6. **失效反例／前提與代價**：外部下載不固定仍可能漂移；no-cache 不等於 pull 新 base 或清空 cache mount。nonce 維護變成人工責任，不能不斷加隨機值假裝可重現。
7. **收尾與撤回**：移除測試 nonce 與 tag，保留原 cache；反覆需求正式化輸入版本與失效策略。套件 cache 加速先作延伸，不預填加速數字。

## 第 11 章｜不是程式慢？把小檔暫搬進去試一次

**標記**：現有功能＋需要新增有限檔案 fixture／計時腳本；Desktop 平台差異顯著。**來源**：C04、M12。

1. **現場症狀**：同一套測試在 Desktop 特別慢，還沒定位就想重寫程式或換框架。
2. **小招式**：把固定小檔案集合放進 named volume，與 bind mount 跑同一掃描工作。
3. **必要原理**：跨主機／VM 的共享路徑可能增加檔案操作成本；現代共享後端不同，不能沿用舊版倍率。
4. **親手實驗**：固定 image、CPU 配額與檔案 checksum，預建一份有限數量資料。兩種存放方式交錯跑至少三輪，冷暖分開，記中位數與範圍；資料複製時間另記。若先後順序主導結果，增加交錯，不能挑最快單次。
5. **結果解讀**：只有相同工作在新路徑穩定變快，才把 I/O 邊界列優先嫌疑；不能外推所有專案或聲稱降低同樣比例的正式流量延遲。
6. **失效反例／前提與代價**：CPU／網路瓶頸可能無差異；volume 初始化與更新、舊依賴、來源同步都是轉移成本。必須註記 Desktop/VMM/共享後端，不把原生 Linux 同等推論。
7. **收尾與撤回**：切回原路徑，核對名稱後只刪專用測試 volume。反覆獲益才分離「會編輯的原始碼」與「可重建的依賴」，寫清失效及更新方法。

## 第 12 章｜偶爾才壞，故意讓依賴慢一點

**標記**：現有 Compose 條件＋需要新增延遲 wrapper／探針；fixture 需建置。**來源**：M09；故障注入方法為本書提出，未實測。

1. **現場症狀**：第一次 up 偶爾連不到依賴，第二次就好；加一段固定 sleep 暫時壓住問題。
2. **小招式**：在隔離依賴副本刻意延後 ready 時刻，放大偶發窗口；比較 service_started 與 service_healthy。
3. **必要原理**：容器啟動、port 可連、業務 ready 是不同事件；健康檢查只代表所定義的條件。
4. **親手實驗**：小服務立刻啟動程序，但經設定的延遲才提供 ready 回應；client 只請求一次。先取零延遲基準，再用兩個較長延遲值；started／healthy 各跑多次，記錄 container 啟動、ready、client 請求與成功時間。延遲參數明寫是自訂測試程式，不是 Docker flag。
5. **結果解讀**：失敗隨 ready 延遲出現且 healthy gate 消除，支持啟動時序假設；不能證明運行途中永遠不斷線。
6. **失效反例／前提與代價**：healthcheck 若只看程序存在，仍會假綠；依賴啟動後再失效，需要應用重連而非再加 sleep。故意變慢增加測試等待，也可能改變競態，不能當正式效能數據。
7. **收尾與撤回**：移除注入 delay，恢復正常服務；保留有意義的 readiness 條件，必要時正式處理重試與重連。以超時界線退出，避免無限等待。

## 第 13 章｜stop 總等滿？看誰擋在 PID 1

**標記**：需要修改 wrapper，通常需重新建置；`--init` 是現有功能，API 1.25+；Linux／Windows 預設不同。**來源**：R09–R12、RT6。

1. **現場症狀**：每次停止都用滿寬限時間；先調短 timeout 可能只是更快強殺。
2. **小招式**：看 PID／PPID，再把 wrapper 最後啟動改為 exec 形式，讓應用接收訊號。
3. **必要原理**：Docker 先對主程序發停止訊號，超時才強殺；wrapper、child 與清理流程不會自動等價。
4. **親手實驗**：有限測試程式收到 SIGTERM 後寫 `cleanup-done` 再退出。A 用明確不轉送訊號的 wrapper，B 以 exec 取代它；固定寬限時間，保存 PID 樹、停止時間與清理標記。C 換成不處理訊號的程式，看 exec 為何仍不保證清理。
5. **結果解讀**：停止較快又有清理標記才支持流程改善；只有較快退出不能證明成功。137 不足以單獨斷言 OOM。
6. **失效反例／前提與代價**：exec 後 shell 的後續 cleanup 不會跑；多子程序需額外管理。Tini／--init 不保證修正不轉送訊號的 shell 或應用；訊號與 timeout 可被設定覆寫。
7. **收尾與撤回**：保留可回復的舊映像／wrapper；在副本驗證清理後才套用。正式化為一次最小 shutdown 檢查，不建立另一套通用程序管理器。
