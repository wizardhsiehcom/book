## 建議先修：會阻礙推演

### R1｜聚合答案缺少計數範圍，三與四互相矛盾

- 位置：[answers.md:31](../../docs/database-correctness/answers.md#06-aggregation)。
- 原文先說全庫 LEFT JOIN 有四列，最後卻說直接 `COUNT(d.defect_id)` 會得到「錯誤的三」。四列中的左表 defect_id 都非 NULL，因此全庫應是 4；3 只適用批次 A 的兩次判定加一筆未判。
- 讀者卡點：手算得到 4 後，會誤以為 COUNT 對重複值或 NULL 的規則理解錯了。
- 最小修正：改成「全庫會得到 4 而非 3；若只算批次 A，會得到 3 而非 2」，或明確限定末句只談批次 A。

### R2｜換新 ID 的預測题少了版本條件

- 位置：[16-unknown-outcome.md:16](../../docs/database-correctness/16-unknown-outcome.md)，對照 [05-apply.sql:43](../../docs/database-correctness/examples/05-apply.sql)。
- 問題：「再送一個新 ID，在哪一種情境會新增第二次判定？」看起來期待「情境 A 已提交，所以會重複」，但本書程序同時保護 expected_version。若只換 ID、保留原 expected_version，A 已提交後的版本衝突會拒絕新操作。
- 讀者卡點：第 10、15 章教過版本條件，照契約推演的讀者反而無法給出題目暗示的答案。
- 最小修正：把題目拆成「只換 ID、保留原版本會怎樣？」與「若又擅自換成最新版本，哪種情境可能重複判定？」明確說明新 ID 失去操作去重，不等於每次一定能通過版本檢查。

### R3｜並行章文字先提交，图卻先等待

- 位置：[10-concurrent-updates.md:26](../../docs/database-correctness/10-concurrent-updates.md)。
- 問題：先寫「A……然後提交。B 隨後……更新」，下一句才寫「A 未提交時，B 可能等候」。Mermaid 的 B 明確在 A 提交前發出更新。
- 讀者卡點：不確定本例是在證明實際鎖等待，還是在證明兩次先後執行的過期版本拒絕；兩種情境的最終零列相同，但等待證據不同。
- 最小修正：改成「A 更新後暫不提交；B 此時發出條件更新並等待；A 完成歷史、目前指標後提交；B 重新檢查條件得到零列」。圖可保留。

## 建議補足：入門鋪墊

### R4｜CTE 在 NULL 範例出場，還沒有一句讀法

- 位置：[04-null.md:20](../../docs/database-correctness/04-null.md)、[06-aggregation.md:35](../../docs/database-correctness/06-aggregation.md)。
- 問題：第 03 章剛教 SELECT／WHERE，第 04 章第一次展示 `WITH … AS`、`VALUES … AS v(...)`，第 06 章又用兩個 CTE 組合彙總，卻沒有解釋命名結果如何流入主查詢。
- 讀者卡點：可能把 WITH 當作建立永久表，或把 CTE 名稱視為必須預先存在的資料表；語法負擔遮住 NULL 與粒度主題。
- 最小修正：第一次使用前加兩句：「VALUES 在查詢中列出測試列；WITH 把這段查詢暫時命名，供緊接的查詢使用，不會建立永久表。」第 06 章加一句把兩個命名结果各自的一列意義說清楚。

### R5｜RCSI 沒有把縮寫和選項明確接起來

- 位置：[11-isolation.md:15](../../docs/database-correctness/11-isolation.md)。
- 問題：前文寫完整的 `READ_COMMITTED_SNAPSHOT OFF`，表格與圖改成 RCSI，但正文沒有直接說它們是同一選項的全名與縮寫。
- 讀者卡點：容易把 RCSI 當成與 READ COMMITTED、SNAPSHOT 並列的第五種隔離層級。
- 最小修正：表格前加「RCSI 是 READ_COMMITTED_SNAPSHOT 的縮寫；它改變 READ COMMITTED 的讀取方式，與另選 SNAPSHOT 隔離層級不同。」現有時間線已足夠，不必增圖。

### R6｜效能章缺少 logical reads 的單位解釋

- 位置：[14-query-plans.md:27](../../docs/database-correctness/14-query-plans.md)。
- 問題：本章用 36 → 2 支撐比較，卻只列英文指標名稱，沒有說 logical reads 是讀取資料頁的次數，而非回傳列數或實際磁碟讀取次數。
- 讀者卡點：可能把 100 筆結果與 2 次讀取看成衝突，或把它直接翻譯成磁碟 I/O 降為 1/18。
- 最小修正：第一次列量測指標時，補一句單位與解讀邊界；同段「操作量測、控制條件、實測結果」分成三段。scan／seek／lookup 也可各附短中文釋義，無需另開術語章。

## 可選潤飾

- **完整 seed 提早可見**：第 03 章第 11 行要求先預測分數篩選，但第 01 章表只有 ID、沒有分數。可在那張表加上 80／90／70，讓讀者不必先開完整 SQL 才能紙上推演。這是閱讀便利，不是缺少資料：完整 seed 與 labs 已提供。
- **減少相鄰重複**：第 06 章第 55、65 行重複 GROUP BY 不保證排序，第 57、67 行重複 DISTINCT 不修正粒度。留較具體的一段即可。第 04 章後半也可刪少量重述，保留欄位缺值與零子列的關鍵區別。
- **先提示升版的未完成前置**：第 18 章第 59 行才提醒 ApplyJudgment 尚未支援 source_name，放在 contract SQL 前會更容易讓讀者停在正確位置。第 9 行同時提 B02Lab 與「獨立升版實驗庫」，可明確說 B02Lab 是示例名稱、換庫名需同步腳本。
- **拆開長段落**：第 11 章第 42 行同時放環境準備、SNAPSHOT 時序、RCSI 對照與 timeout，可拆成三段；第 21 章第 7 行先定義憑證用途，再列需驗證內容，可降低一次讀取的負擔。進階內容本身有適用邊界，不建議刪除。
- **驗證紀錄同步**：verification.md 第 71 行仍寫「3 張 Mermaid」，目前來源共 10 張。應依實際最新檢查紀錄更新；第 09 章第 19 行「本文沒有啟動資料庫」也容易讓人誤解本書完全沒跑引擎，可限縮為「本章未進行崩潰／斷電驗證」。
- **字形統一**：15:71「讨論」、20:53「来源」、exercises:15「允许」改為繁體；不影響理解。
