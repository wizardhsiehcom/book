# 《Coding Agent 的運作原理：從模型到可控的工作系統》成書計畫

本書要讓會基本程式設計的讀者，看懂 coding agent 如何工作，並能為自己的任務選擇合適的設計。以指定論文為主要來源，依 ISO 24495-1 的淺白語言原則重組知識，寫成繁體中文教學書。

計畫日期：2026-10-07。原計畫交付後，同日依使用者指示完成首版正文、教學程式與網站建置；執行結果見文末。

## 1. 讀者完成本書後能做什麼

預設讀者會讀簡單的 Python，知道 API 是程式呼叫外部服務的介面，但沒有設計過 agent。不了解非同步程式、模型上下文或權限隔離的讀者，可先讀各章的前置說明。

讀完後，讀者應能：

1. 畫出一次任務從輸入、模型判斷、工具執行到完成驗證的流程。
2. 分辨模型能力、執行架構與外部工具各自負責的問題。
3. 解釋工具失敗、上下文不足、權限拒絕與停止條件如何影響結果。
4. 比較兩種架構的適用條件，而非只看功能數量。
5. 用小型實驗驗證一項設計選擇，並說明實驗不能證明什麼。

預計寫成 16 個核心概念頁，約 35,000–50,000 個中文字，另附導讀、詞彙與查閱資料。字數只供估量；不為湊字數重複介紹產品。

## 2. 來源與證據邊界

主要來源為 Paul Barbaste、Tristan Darrigol、Germain Vu、Tom Wiltberger 的 *Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems*。

- [論文入口](https://arxiv.org/abs/2609.00006)
- [本計畫採用的 v1 全文](https://arxiv.org/html/2609.00006v1)
- [論文標示的 CC BY 4.0 授權](https://creativecommons.org/licenses/by/4.0/)

規劃時先核對摘要、章節架構、七個分析面向與研究版本說明。寫作階段已分工閱讀全文相關段落及附錄，建立逐項對照並交叉查核教學內容；沒有獨立重做各產品原始碼稽核。

論文提供架構比較，不是同條件的效能排名。書中引用產品能力時，要註明論文快照；不能把快照當作今日產品規格。論文也指出 Claude Code 的分析來源日期與其他系統不同，案例表必須保留這項差異。

每項內容按以下方式處理：

| 內容 | 書中寫法 | 查核方式 |
|---|---|---|
| 原文記錄的實作 | 「論文在指定版本觀察到……」 | 連到章節、表格及版本資訊 |
| 作者的解釋或建議 | 「作者據此建議……」 | 保留前提，說明證據能支持到哪裡 |
| 本書的比喻、推導與練習 | 明示為本書教學例子 | 不冒稱原文實驗或作者結論 |
| 寫作時補充的新資料 | 與原文快照分列 | 引用官方文件或原始碼，記錄日期 |

例如，樣本中沒有某項技術，不能直接推成「所有 agent 都不需要它」。單一案例的成功，也不能推成某種架構較優的因果證據。

重新繪製圖表時註明改編來源；沿用原圖或程式前，核對對應素材的授權與署名要求。正文以自行撰寫的解說為主。

## 3. 依學習順序安排章節

用同一個教學任務貫穿全書：「請 agent 修正一個小型專案的錯誤，並交代如何確認修好。」先讓讀者看懂一次工作，再逐步加入失敗、限制與設計選擇。

下表是教學安排，並非原論文目錄的翻譯。每列是一個概念頁；來源章節供後續作者查核。

| 頁次與暫定標題 | 讀者要解決的問題 | 學習產出 | 論文對照 |
|---|---|---|---|
| 01 模型如何變成能工作的 agent | 模型之外還需要什麼？ | 任務流程與責任邊界圖 | §2 |
| 02 原始碼比較能告訴我們什麼 | 哪些結論可以相信到什麼程度？ | 一張證據判讀卡 | §4–5、§15.6 |
| 03 一次工作如何反覆前進 | 如何串起判斷、動作與結果？ | 逐步追蹤一輪執行紀錄 | §6 |
| 04 Agent 何時該停下來 | 完成、卡住與超出預算如何區分？ | 停止條件表 | §6、§16 |
| 05 模型如何接上工作流程 | 更換模型會牽動哪些地方？ | 模型介面與資料流圖 | §7 |
| 06 工具如何讓模型可靠地做事 | 工具要收什麼、回傳什麼？ | 一份含失敗回傳的工具契約 | §8 |
| 07 修改檔案前要確認什麼 | 找不到或找到多處時怎麼辦？ | 編輯失敗案例與處理規則 | §8.4 |
| 08 如何找出任務需要的程式碼 | 要讀哪些檔案才足夠？ | 查找步驟與停止搜尋的條件 | §9.7、§13、§16 |
| 09 對話放不下時要保留什麼 | 如何縮短內容又保留關鍵決定？ | 壓縮前後的資訊核對表 | §9 |
| 10 哪些知識應留到下一次任務 | 暫時紀錄與長期記憶如何分開？ | 一份可追溯的記憶範例 | §9.6 |
| 11 誰決定工具可以執行 | 提示、批准與隔離有何差別？ | 權限判斷及執行邊界圖 | §10 |
| 12 什麼任務值得交給多個 agent | 分工何時能抵銷協調成本？ | 一份分工或維持單人的理由 | §11 |
| 13 新能力應接在哪一層 | 規則、技能、工具與協定如何分工？ | 擴充需求對照表 | §12 |
| 14 如何比較不同系統的設計 | 如何從實作差異看出取捨？ | 依同一任務比較兩個案例 | §5–13、附錄 A |
| 15 工具成為平台後多了哪些責任 | 為何還要處理相容、分發與治理？ | 平台責任圖與版本變化案例 | §14–15 |
| 16 為自己的任務選出最小設計 | 哪些功能現在就需要？ | 設計草圖、驗證紀錄與限制 | §16–17 |

附錄規劃：

- **術語表**：中文名稱、英文名稱、白話定義與首次解釋頁。
- **系統查閱卡**：每個研究案例的角色、快照、特色與證據限制；對照案例另標，不混入同質排名。
- **論文對照索引**：把原文各項觀察、模式與建議映射到正文或附錄；未納入的項目記錄理由。
- **練習解答**：提供判斷依據與常見誤解，與題目分開。
- **來源與驗證紀錄**：列出引用版本、補充資料與已完成的檢查。

## 4. 每頁如何寫

每頁先回答一個問題，再用例子解釋原因。建議依序寫：

1. **先給答案**：前兩行說出這一頁最重要的判斷。
2. **放進任務**：指出貫穿案例在哪一步遇到問題。
3. **拆開機制**：先說輸入、處理與輸出，再介紹必要術語。
4. **比較選擇**：選兩個差異明確的做法，說明各自代價。
5. **指出邊界**：哪些情況不能套用這個結論。
6. **讓讀者判斷**：放一題追蹤、一題設計選擇，附解答連結。
7. **提供出處與下一步**：連到論文定位和下一個概念。

不強迫每頁使用相同小標；能用短段落講清楚的內容，不拆成空泛欄位。圖用來表達流程、邊界或比較，正文仍須能獨立閱讀。

## 5. 把 ISO 24495-1 變成可檢查的寫作要求

採用 `iso-24495` skill 的四項原則及繁體中文寫作手法。這是依公開原則實作的編輯流程，不宣稱取得 ISO 認證。

| 原則 | 本書的執行方式 | 驗收問題 |
|---|---|---|
| 相關 | 每頁對應一項讀者任務；深度實作細節移到查閱資料 | 這段是否幫讀者解釋、判斷或操作？ |
| 找得到 | 標題點明問題；頁首先給答案；提供來源與術語索引 | 讀者能否只靠目錄找到所需答案？ |
| 看得懂 | 一句一意；先例子後抽象；術語首次出現立即定義 | 讀者能否用自己的話說明機制？ |
| 用得上 | 給輸入、步驟、預期結果及失敗情況 | 讀者能否完成練習並判斷結果？ |

中文編輯規則：使用繁體中文；刪除公文腔與空泛開場；明寫動作者；同一概念固定名稱。Harness 首次解釋為「讓模型能執行任務的執行系統」，之後保留 Harness 作為專有名稱，避免每章換譯名。

一句超過約 40 字、一段超過五句時，回頭檢查是否混入多個意思。這些是編輯提醒，不是 ISO 條文或硬性字數限制。不得為縮短文字刪掉數字、條件與不確定性。

## 6. 教學實驗如何控制範圍

第一版用 Python 標準函式庫與固定的模擬模型回應，讓讀者不需 API 金鑰也能追蹤流程。真實模型接法列為選讀；若加入，另交代成本與結果變動。

只做三組小實驗：

1. **工作迴圈與停止**：正常完成、工具失敗及達到步數上限；讀者核對每次狀態變化。
2. **可預期的檔案編輯**：匹配為零、一處與多處；不明確時拒絕寫入，確認原檔未變。
3. **上下文保留**：比較壓縮前後是否保留任務、限制、已做決定及下一步；不把字數變少當作品質提升。

每組留下最小可執行檢查。實驗使用暫存目錄及白名單工具；不提供直接執行任意模型 shell 指令的預設路徑。教學原型不冒稱生產用沙箱。

論文的最小程式骨架作為閱讀材料。實作時逐項核對其省略項，不直接複製後宣稱已具備完整安全與錯誤處理。

```bash

node tools/check-book-palettes.cjs
```

最後人工檢查目錄、程式碼、表格、圖與手機寬度閱讀。建置成功只代表出版檔案可產生；內容可信與讀者看得懂，仍須分別驗收。
