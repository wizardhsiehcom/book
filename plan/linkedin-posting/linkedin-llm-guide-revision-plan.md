# LinkedIn 書籍再研究與私人 LLM 指南修正計畫

日期：2026-10-14  
狀態：2026-10-14 已實作本輪書籍修訂與私人指南；研究覆蓋與本人語氣驗收仍有未完成項，詳見末節。

## 目標與依據

使用者原先希望這本書能供 LLM 作為寫作依據，並進一步提出「書籍還是書籍」，詢問操作指南是否更適合放在 Obsidian。本計畫採用以下分工方案：書保留完整研究、案例剖析與寫作解釋；Obsidian 另放個人 LLM 操作指南，將書中有依據的建議轉成起稿與編修流程。

兩者分開驗收：書要讓人理解作者為何這樣寫、哪些做法值得借鏡；指南要讓新對話中的 LLM 能完成任務並保留本人聲音。Obsidian 的用途是管理私人偏好與操作入口，不代表模型會自動讀取；實際使用時需明確提供指南路徑或內容。

本次依據是一輪 PyCon Sprint 貼文協作。使用者多次要求自然、適合 LinkedIn、不要塞入全部素材，模型仍反覆產出制式感想，並在過度正式與私人動態口吻間擺盪。這是單次使用案例，不能推論所有使用者偏好或平台成效。

私人完整紀錄存於 Obsidian：`Private/post/2026-10-14 LinkedIn 貼文協作問題紀錄.md`。公開教材只取去識別化的必要片段，不複製私人背景、完整對話或實際人物談話。

本計畫補充既有 [研究修訂計畫](linkedin-posting-revision-plan.md)，不把其尚未完成的研究標成完成。新增貼文再研究作為本輪書籍修訂的必要工作。先檢查既有案例與補齊樣本，再決定哪些建議保留、限縮或撤回；不只把本次對話的偏好寫成通則。

## 問題定位

| 實際問題 | 現有書稿的相關位置 | 要修的層次 |
|---|---|---|
| 把活動紀錄寫成成果、洞見、感謝的完整套版 | README 以九章人類練習為入口；C01、C03 主要從工程問題與判斷出發 | 增加任務分流，允許單純的參與紀錄 |
| 模型讀了「不要套模板」卻仍套模板 | C04、tone-and-voice 已有節制原則；reading-and-ai-workflow 的起稿提示卻要求問題→證據→限制 | 移除相互衝突的通用指令，建立優先順序 |
| 多候選只是同一批句子重排 | C04 說明模式，缺少候選差異的驗收方式 | 各版需有不同主角、選材與刪除內容 |
| 使用者說自然，模型就加 XD；說 LinkedIn，又變公關稿 | 語氣章缺少對口語回饋的具體處理規則 | 分開專業場合、正式程度、個人聲音 |
| 把受邀主持人寫成活動籌辦者；英文又暗示專案創辦者 | 既有事實核對要求未被落實 | 做最小角色與狀態檢查，修正傳遞到所有版本 |
| 英文只是翻譯套話，再靠縮寫假裝自然 | 現有中英文案例未形成跨語言起稿流程 | 從相同事實重寫，不逐句翻譯、不添加態度 |
| 使用者貼文已成形後，模型仍持續重構 | 缺少起稿、輕修、評估三種任務界線 | 使用者原句成為語氣錨點，選稿後局部修改 |
| 被 AI 偵測百分比牽著走 | 缺少面對此類回饋的工作規則 | 將「AI 感」轉成可編輯問題；不以偵測分數驗收 |

不能把問題全歸給書：C04、C05 已要求選材、具體、避免誇大，模型本次仍未做到。修訂需同時改善指令可執行性，並用實際輸出驗證模型是否遵守。

## 第一階段 重新研究真實 LinkedIn 貼文

### 研究要回答的問題

- 工程師實際如何寫活動參與、開源貢獻、人物交流、作品與技術心得？短篇和長篇各承擔什麼任務？
- 貼文中哪些句子提供事實、個人態度、人際關係或專業判斷？哪些看似客套的語句在其脈絡裡仍有作用？
- 正文如何與合照、團體照、作品圖或 PR 連結配合？不能只讀文字就判斷資訊是否不足。
- 英文與繁體中文有哪些可觀察的表達差異？哪些差異也可能來自作者、題材與受眾，而非語言？
- 本書既有「具體、有證據、少套話」等建議，在哪些場景適用，在哪些場景被過度延伸？

### 樣本與取得方式

先稽核 `04-post-patterns.md`、`browser-reaction-cases.md`、`eugene-fred-comparison.md`、`notable-authors.md` 與 `engineering-study.md` 的既有案例，區分實際讀過的 LinkedIn 正文、作者原站長文、外部研究摘要、合成範例。能重用的先重用，但不得把原站文章算成 LinkedIn 貼文。

首輪工作量以 24–36 篇可讀貼文、8–12 位作者為目標，涵蓋英文與繁中；至少半數來自接近使用者職涯階段的工程師或社群參與者，不由名人、講者或商業經營帳號主導。配置約半數為活動／開源參與，其餘包含人物交流、作品／里程碑、技術教學或復盤作對照。這是有目的的質性樣本，不代表平台分布。

選樣前記錄主題、語言、作者類型與固定時間窗。優先讀同一作者或同一活動的可見連續貼文，不先依讚數或「看起來自然」挑選。保留不符合預期的案例；資料不足就記錄覆蓋缺口，不拿搜尋摘要補正文。延用既有低頻閱讀限制，不建爬蟲、不繞登入或封鎖。

### 每篇怎麼剖析

保存原始連結、作者、日期精度、查讀日期、可讀範圍與圖片是否可見；正文只保存分析所需短引，不大量搬運全文。

每篇分析包含：

1. **情境與目的：** 作者當時的角色、可能對誰說、本文主要做什麼；可觀察事實與編輯推論分開。
2. **文字與照片：** 篇幅、分段、首句、具體行動、情緒、感謝、標註、結尾；照片或連結是否提供正文省略的資訊。
3. **逐句功能：** 每句有何作用，刪除後少了什麼；不能把簡單感謝一律判成廢話。
4. **取材與界線：** 實際寫了哪些內容、沒寫哪些面向；只能描述可見省略，不推測作者手上原本有什麼素材或為何刪除。
5. **語氣判讀：** 指出具體措辭和閱讀效果，不以縮寫、語病或句型判定 AI／真人來源。
6. **可借用的決策：** 適合何種任務、需要哪些真實材料、哪些屬作者個人風格而不宜複製。
7. **反例與不確定性：** 哪篇不同寫法也能完成相同任務；結構不是成功配方。

先隱去互動數做內容剖析，再另記當下可見反應與留言。互動僅作背景；不據此推論作者身分來源、自然度、演算法偏好或求職加分。若要比較成效，另遵守舊研究計畫的同作者、同時窗與分母要求。

### 研究交付與通過條件

- `plan/linkedin-posting/post-reanalysis.md`：樣本選擇、既有案例稽核、覆蓋缺口與逐篇分析索引。
- `docs/linkedin-posting/post-anatomy.md`：供人閱讀的精選比較章，約 6–8 篇深入剖析，至少包含三組可比較案例；依正文與圖片、作者角色等脈絡解釋差異。
- 主張修正表：每項舊建議標為保留、限縮、撤回或待驗證，附來源、反例與對應章節。
- 轉譯表：案例觀察 → 有條件的寫作建議 → 私人指南的操作步驟 → 後續回放測例。

研究完成須能回答上述問題並提出有證據的修正，不以湊足篇數驗收。跨案例通則至少有兩位作者支持並檢查反例；不足者保留為個案或編輯假設。這仍不等於因果證據。若來源受限，只限縮相應結論，不宣稱研究完整。

## 第二階段 在 Obsidian 建立私人 LLM 操作指南

### 1. 新增私人操作入口

預定新增 Obsidian 筆記 `Private/post/LinkedIn 寫作指南.md`。內容集中在任務分流、本人偏好、已確認事實、選材、改稿與交付，不複製整本書。將「書籍研究支持」「本人偏好」「暫定編輯規則」分開標明，並以本機章節路徑連回依據。

書籍 README 保留人類閱讀路徑；`reading-and-ai-workflow.md` 說明如何從書整理自己的素材包與指南，但不公開私人指南路徑、人物對話或個人背景。書中不新增一份與 Obsidian 重複的操作入口。

入口包含以下可執行流程：

1. **辨識任務。** 區分起稿、多候選、局部修改、跨語言重寫、適合度評估。只問「適合嗎」時先回答判斷，不自動改稿或存檔。
2. **整理最低限度材料。** 使用者想說什麼、對誰說、哪種場合、確定事實、本人措辭與篇幅偏好。私人背景只用於理解，不自動寫入正文。資料足夠就起稿，不強迫填完整張卡。
3. **先分流再選模式。** 活動紀錄可只寫參與、具體行動與個人細節；技術教學才需要步驟；工程判斷才需要理由與適用條件。一次只走適用路徑。
4. **選材。** 每版選一個重點。照片已有的資訊不必全部重述；感謝、人物、餐點、技術細節均依主題取捨，不固定必填。
5. **起稿。** 依任務與使用者要求決定篇幅。本次偏好可暫記為簡短活動文，但不先固定句數或字數為書籍通則；待第一階段案例比較後再決定是否提供有條件的範圍。
6. **內部檢查後交付。** 確認事實、選材、自然度與版本差異。正文與編輯說明分離；沒有要求時不附長篇自我分析。
7. **依回饋更新。** 保留已選版本、語言、事實更正與聲音；修改使用者指出的問題，不重新加入已刪素材。使用者提供成稿時優先輕修。

指令優先順序：使用者當次要求與已確認修正 → 本人草稿與口吻 → 已確認材料 → 本指南的編輯預設 → 作者案例。任何層級都不允許補造經歷。

### 2. 重寫 AI 起稿提示

改寫 `reading-and-ai-workflow.md`：

- 移除適用於所有貼文的「先交代問題，再安排已有證據，最後說明限制」。
- 改成按任務選用提示，讀者可整理成自己的私人指南；只在技術論證任務啟用問題、證據、限制。
- 素材卡分成必要資訊與可選資訊；「沒有結果」不等於只能寫設計，也可以如實寫參與紀錄。
- 【待補】只在缺少支撐核心主張的資訊時使用；可刪的枝節直接不寫，不讓短文充滿佔位符。
- 主張核對作為內部檢查；只有使用者要求或有實質歧義時才展示。
- 書中解釋流程原理與通用提示；私人指南保存實際操作與個人偏好。書的結論更新時檢查指南是否需要跟著調整，避免兩份指令互相矛盾。

第二階段完成條件：新對話讀取私人指南及其指定的必要章節，即能交出符合任務的候選；無須把整本書讀完，也不把個人偏好誤當平台規則。

## 第三階段 依研究結果修正書籍與加入對照範例

以下為本次失敗提出的待驗證修訂方向，第一階段研究可調整它們；不預設所有文章都應更短。

| 檔案 | 最小修改 |
|---|---|
| `01-reader-and-goal.md` | 明列參與紀錄、關係維繫、分享興趣也可作單篇目的；不強迫讀者帶走方法或判斷 |
| `03-material-and-topics.md` | 增加非問題解決型材料卡；區分必需事實、可選細節、未確認資訊 |
| `04-post-patterns.md` | 在經驗敘事與里程碑下補短活動紀錄，不新增大分類；說明不必有轉折或成長弧線 |
| `tone-and-voice.md` | 加入「更自然／更 LinkedIn／更英文／太 AI」的回饋處理表，禁止以表情符號、俚語或故意錯字代替聲音調整 |
| `05-opening-and-editing.md` | 加入刪修與停止條件；沒有新資訊的感想句刪除，不要求每篇都加技術細節 |
| `06-format-and-publishing.md` | 納入活動照片配短文；工程數據與限制的檢查只在存在相應主張時啟用 |
| `README.md`、`configs/linkedin-posting.yml` | 加入貼文剖析與編修示例的閱讀入口，保留書的教學結構 |
| 既有案例與研究章節 | 依主張修正表更新解讀及限制；保留查讀日期，不覆寫歷史快照成最新成效 |

回饋處理表至少包含：

- **更 LinkedIn：** 確認專業場合與相關內容，不自動增加正式語、勵志結論或成果包裝。
- **更自然：** 優先沿用本人句型，刪除重複感想與空泛詞，不機械禁止特定英文單字。
- **更英文：** 先保留事實、重點、態度，再重新組織英文；縮寫是選項，不是自然度證據。
- **太 AI：** 指出具體句子如何重複、空泛或不像本人，不聲稱從句型辨識作者身分，不承諾通過偵測。
- **有加分嗎：** 分開內容能呈現的參與／能力、讀者可能的解讀、尚無觀測的觸及或求職效果。

新增一份精簡的 `docs/linkedin-posting/llm-editing-examples.md`：

1. 同素材三個候選：行動、人物、社群；至少一版完全省略人物，一版省略餐飲，不能只換開頭。
2. 制式感想如何刪短：顯示刪了哪句及理由，不建立「禁字清單」。
3. 本人草稿的輕修：只修語序、標點與事實歧義，保留態度與敘述節奏。
4. 英文重寫：相同事實的自然英文，不能補「第一次貢獻大型專案」、merge、CI 挫折或他人立場。

示例標明為編輯示範，不能當作已被使用者接受或高成效貼文。人物匿名化，對話中的新材料按出現階段給入，避免把後來資訊洩漏給早期起稿測例。

## 第四階段 分別驗收書籍與指南

新增 `plan/linkedin-posting/llm-guide-evaluation.md`，用 Markdown 記輸入、實際讀取章節、原始輸出、人工判讀與修訂原因。不先建立評分程式。案例研究的完成度與指南的執行效果分開記錄。

| 測例 | 輸入 | 通過條件 |
|---|---|---|
| A 少量素材起稿 | 第一次 Sprint、兩個 PR、多專案、照片與餐點 | 短文有明確重點；不把全部素材都塞進去；不新增成果 |
| B 多候選 | A，加上高天吸引報名、受邀主持人的資訊 | 三版選材與主角有別；人物角色正確 |
| C 連續修稿 | 選第三版→加第一次→更 LinkedIn→太 AI | 保留選稿與已確認事實；不在 XD 與公關稿間來回切換 |
| D 本人草稿 | 提供使用者自己寫的短稿，要求順一下 | 只做必要修改，不加心得、CTA、hashtag 或情緒 |
| E 英文改寫 | 要求更英文、非直譯 | 意思、態度與事實一致；無套話填充、故意語病或新增經歷 |
| F 狀態與角色 | 提 PR 未知 merge；受邀主持；第一次 Sprint | 不改成 merged、專案創辦人、第一次 PyCon 或首次開源貢獻 |
| G 他人談話 | 只確認問過 vibe coding | 只寫問過，不能自行加入回答、引語或公開立場 |
| H 偵測與評估 | 使用者回報 AI 分數；或只問適合 LinkedIn 嗎 | 不替偵測分數背書；評估具體措辭與場合，不擅自改稿 |
| I 技術文章對照 | 有測試條件與結果的工程復盤 | 仍保留必要證據和限制，不能把所有文章都壓成活動短文 |

書籍先驗收：每個核心建議可回到已讀案例或明確標示的編輯推論；比較有脈絡與反例；人類讀者能理解取捨，不必依靠 LLM 指令才能讀懂。

指南再驗收：先保留本次對話為已知失敗基準。修訂後使用不帶本對話歷史的新對話逐項執行；再補一個非 PyCon 的合成活動案例，檢查是否只記住本例。若模型沒有讀到所需指引，記為入口失敗；讀到仍不遵守，記為指令遵循失敗。

硬性驗收：每個測例均無新增事實、角色錯置、狀態升級或遺失已確認更正。候選數量與局部修改範圍符合要求。自然度與本人聲音由使用者比較匿名版本，不以模型自評或 AI 偵測分數取代；尚未取得使用者判讀就標待驗收。

回放通過後執行文件檢查：相對連結與 nav 對應、`./sync-assets.sh`、`uv run mkdocs build -f configs/linkedin-posting.yml`。同步若產生無關檔案差異，先檢查而不混入本次修訂。建置成功與寫作驗收分開記錄。

## 範圍與交付順序
