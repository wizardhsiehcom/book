# 「那些有點土，卻能解決問題的工程技巧」書籍規劃 Prompt

用途：把任何技術領域換成一份以現場經驗、取巧方法與小實驗為主的書籍規劃。整段複製下方 prompt，填入主題即可；未指定的欄位可省略。

## 可直接使用的 Prompt

```text
我想規劃一本關於【技術領域】的「現場招式」書。

核心概念是：那些有點土、看似苟且、不按教科書出牌，卻能解決問題的工程技巧。

我要挖掘的是有經驗的工程師在現場會做、初學者卻不知道還能這樣做的小動作。例如：繞過繁瑣入口、保存輸入重播、暫時關掉某項功能、故意製造極端情境、固定某個原本可變的條件、用少量規則補位、用簡單工具替代通用系統，或用便宜的對照實驗找出問題在哪裡。

讀者背景：【會基本操作，但缺少現場經驗；可自行修改】
常見情境：【開發／除錯／訓練／部署／維運，或具體專案】
預期產出：【預設為研究資料＋book plan，不直接寫完整正文】
資料存放：【預設 data/<主題>-field-tricks/】
規劃存放：【依專案慣例；無慣例時放 plan/<主題>/】

請依下列方向工作。

一、先抓住這本書的味道

- 從「現場卡住了什麼，老手會先動哪裡」出發，讓讀者產生「原來還可以這樣試」的感覺。
- 優先找改動小、回饋快、可以撤回，卻能省很多時間或排除一大類問題的招式。
- 可以收錄硬編碼、臨時開關、土法規則、手動介入、犧牲通用性的捷徑。要說明它省掉什麼，又把成本轉移到哪裡。
- 不必每招都違反最佳實踐。重點是實際操作中不容易被教材講出來的判斷與做法。
- 特別留意反直覺的動作：故意變慢來定位錯誤、先讓模型背答案、先固定尺寸、關掉自動化、先用假輸入、把大問題縮成一個小案例。
- 技巧不一定在核心演算法裡。輸入、標註、介面、啟動方式、前後處理、佇列、視覺化與人的操作流程，都可能是最值得取巧的地方。
- 避免把內容寫成 API 目錄、一般入門課、最佳實踐清單或一串「調參即可改善」的建議。每個題目都要有具體動作與可觀察的結果。

二、先研究，再規劃，最後才寫

- 搜尋中文與英文部落格、第一人稱踩坑紀錄、工程團隊文章、原始專案及 issue。優先找有實際症狀、嘗試過程、程式或對照結果的內容。
- 部落格用來發現現場招式；技術機制再對照官方文件、原始碼或原始研究。
- 不把搜尋摘要當成已讀正文，也不把轉載、翻譯和同一案例的多篇整理當成獨立證據。
- 先把需要的資料寫入資料目錄，再根據證據整理選題與 book plan。不要先定好章節，再只找支持既定大綱的文章。
- 每筆資料記錄：來源連結、作者與日期（未知則標記）、閱讀完整度、症狀、操作、有效前提、代價、證據品質、可設計的小實驗。
- 分清楚「來源作者實測」「文件或程式碼支持的機制」「我們提出但尚未執行的實驗」。不要把他人的數字寫成自己的成果。
- 搜尋到錯誤、過度概括或缺少實驗條件的說法，也記下不採用的原因。不要用來源數量取代品質。
- 多 agent 的使用與模型選擇遵循本次任務授權，不預設特定模型或委派方式。

三、用這些問題篩選每一招

1. 工程師到底卡在哪裡？原本要付出什麼成本？
2. 他具體動了什麼？能否用幾步操作或一小段程式說清楚？
3. 為什麼可能有效？它控制、繞過或替代了哪一段流程？
4. 哪些條件成立才能用？依賴什麼版本、資料、硬體或業務假設？
5. 省下的代價轉移到哪裡？例如延遲、記憶體、人工、召回率或維護成本。
6. 怎麼做最小對照，判斷是真的解決問題，還是把問題藏起來？
7. 這次結果能證明什麼，不能證明什麼？
8. 怎麼撤回？什麼情況值得把臨時招式正式化？

四、形成一本能拿到電腦旁邊照做的書

- 依症狀與操作目的分部，例如控制入口、縮小問題、讓錯誤現形、資料省工、系統補位、部署救援。依主題調整，不強套分類。
- 章名要像現場問題或具體動作，例如「Python 正常，C++ 卻跑歪」「慢的可能是畫字」「不接設備，直接重播一次」。
- 不預設章節數。先挑最有證據、最能做出短實驗、彼此不重複的招式，再決定結構。
- 每章固定節奏：現場症狀 → 小招式 → 必要原理 → 親手實驗 → 結果解讀 → 失效反例 → 收尾與撤回。
- 標記「現有功能可直接操作」「需要新增程式」「需要重新訓練或建置」「僅適用特定版本」。不要把自訂開關寫成工具內建功能。
- 診斷用的故意過擬合、同步或假輸入，可以是好招；拿它們冒充泛化、正式效能或真實結果則應當反例處理。
- 讓讀者先得到一個小成果，再補理解這招所需的概念。保留現場感，不讓風險提醒或理論淹沒操作。

請交付：
1. 已存檔的中英文研究資料與索引。
2. 值得採用的招式清單、延伸題，以及不採用的說法與理由。
3. 一份 book plan：定位、讀者、章節、每章問題與實驗、前提與代價、來源對應、建議撰寫順序。

完成研究與規劃後，清楚說明哪些案例還沒有親自重現。除非這次任務另外要求，先不要寫完整正文。
```

## TensorRT 套用範例

把上述欄位換成：

```text
技術領域：TensorRT 推論部署與除錯
讀者背景：能匯出 ONNX、跑基本推論，但遇到精度差異或效能問題時容易盲目調參
常見情境：Python／C++ 結果不一致、動態尺寸、FP16／INT8、GPU 非同步與串流延遲
預期產出：研究資料＋book plan
資料存放：data/tensorrt-field-tricks/
規劃存放：plan/tensorrt/
```

候選搜尋方向可以包含「保存 tensor 直接重播」「暫時固定 shape」「退回較高精度找差異」「先同步一次看錯在哪」「關掉前後處理看看真正瓶頸」。這些只是研究入口，適用性與 API 仍須查證，不能預先當成有效配方。

## 一句話喚起這個方向

> 用 `prompts/field-tricks-book.md` 的概念，幫我研究並規劃一本【主題】現場招式書：先搜中英文實務經驗，把資料存到 `data/`，再整理那些有點土、但在特定條件下很好用的技巧。
