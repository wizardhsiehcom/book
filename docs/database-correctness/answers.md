# 練習答案

先完成各章預測與無提示題，再閱讀本頁。這裡說明推理；實際引擎結果另列於 [驗證紀錄](verification.md)。

## 01｜身分 {#01-identity}

同一 defect_no 可在兩個批次重用，因此 (batch_id, defect_no) 才是此合成資料中的業務鍵。seed 的 (10,1) 與 (20,1) 是不同缺陷，分別由 defect_id=1 與 3 參照。Defects 的主鍵是 defect_id；Judgments 的主鍵是 judgment_id；Batches 的主鍵是 batch_id。Batches 一對多 Defects，Defects 一對多 Judgments。缺陷 1 的兩次判定是兩個事件 101、102；缺陷 2 沒有判定子列；缺陷 3 有 103。UNIQUE(batch_id, defect_no) 防止同一批次重複缺陷號，不能改成 UNIQUE(defect_no)。

## 02｜正規化 {#02-normalization}

批次標籤由 batch_id 決定；缺陷由 defect_id 參照，業務身分由 batch_id+defect_no 組成；一次判定的分數和 model_version 依 judgment_id 的事件列保存。若將 label 複製到每個缺陷和判定列，批次改名須更新多筆，少更新一筆就形成不一致。若平面表要求每列有 judgment_id，批次或尚未判定的缺陷難以獨立記錄；刪除最後一個事件也可能抹掉唯一標籤。

三個實用檢查是：欄位是否以原子值儲存（1NF 直覺）；複合候選鍵上的描述欄是否依賴整個鍵（2NF 直覺）；欄位是否描述它所屬實體而非經其他非鍵欄位間接依賴（3NF 直覺）。目前拆為 Batches、Defects、Judgments 讓批次標籤只存一處，判定事件保留各自模型版本。反正規化可能節省 JOIN，代價是同步、回填與判斷權威值的規則。

## 03｜查詢 {#03-query}

不加 DISTINCT 而只投影 defect_id 時仍有兩列，兩列的值都是 1；投影不會自動去重。score >= 80 會留下 judgment 102（90）及 101（80），按 defect_id、score DESC、judgment_id 排序為 102、101。只投影 defect_id 並加 DISTINCT 會只輸出 1，適合回答「哪些缺陷曾達門檻」，不適合列舉事件，因 101 和 102 的差別被折疊。沒有 ORDER BY 不保證列順序；只排序分數時，同分列仍無先後保證。judgment_id 可以作確定的平手鍵，但不能據此聲稱事件在時間上較晚。

## 04｜NULL {#04-null}

NOT EXISTS 子查詢查找不到對應 Judgments 的缺陷，因此 seed 只回 defect_id=2。score=NULL 的獨立樣例只有一列是缺值；score=0 是實際零分；score=80 是已知分數。一般比較如 score=NULL 或 score<>80 對 NULL 產生 UNKNOWN，WHERE 不留下它；IS NULL 才會選出它。本書 Judgments.score 是 NOT NULL，所以這是獨立 VALUES 教學例，不是合法 seed 列。

NOT IN 集合只要含 NULL，就可能使候選值比較結果成 UNKNOWN。題示 Candidate 為 1、2，Excluded 為 1、NULL；x=1 因匹配 1 被排除，x=2 的 NOT IN 結果仍 UNKNOWN，因此沒有候選值通過。若需求是「不存在一筆相等的已知排除值」，NOT EXISTS 可以直接寫出關聯。空字串、零與 NULL 都有不同意義；零次判定則是沒有子列。

## 05｜JOIN {#05-joins}

INNER JOIN 回傳三組：(1,101)、(1,102)、(3,103)，缺陷 2 無配對而消失。LEFT JOIN 保留全部缺陷，回傳四列：(1,101)、(1,102)、(2,NULL)、(3,103)。把 score>=80 放在 ON，仍保留缺陷 2、3 作為無符合判定的 NULL 列，合計四列；放在 WHERE，補 NULL 後又篩掉不符合者，只剩 101、102 兩列。對 LEFT JOIN，ON 的右側條件限制可配對事件，WHERE 是篩結果列。以 defect_no 單獨連接不正確，因不同批次都能有 defect_no=1。

## 06｜聚合 {#06-aggregation}

Defects LEFT JOIN Judgments 的輸入是四列，故 COUNT(*)=4；其中只有三個 judgment_id 非 NULL，COUNT(j.judgment_id)=3。COUNT(expression) 不計 NULL；COUNT(*) 計 JOIN 結果中的每一列。批次 10 有兩個缺陷、兩次判定；批次 20 有一個缺陷、一次判定。先在 Defects 粒度算缺陷數，再在每缺陷連事件的結果上計判定數，最後接回 Batches，可避免不同一對多來源互相展開。若對全庫 JOIN 結果直接 COUNT(d.defect_id)，會得到 4 而非實際的 3 個缺陷；若只算批次 A，則會得到 3 而非 2。兩者都是因為缺陷 1 被數了兩次。

## 07｜約束 {#07-constraints}

同批次重複缺陷號由 UNIQUE(batch_id, defect_no) 拒絕；不存在的 batch_id 由外鍵拒絕；101 分由 CHECK(score BETWEEN 0 AND 100) 拒絕；NULL 分數由 NOT NULL 拒絕。DEFAULT 只在省略欄位時提供值，例如 version_no 預設 0；它不限制範圍，也不會把明確 NULL 自動變成 0。

只有 CHECK 的 nullable score 欄位在 NULL 時產生 UNKNOWN；SQL Server 的 CHECK 不因 UNKNOWN 拒絕列，所以要同時設 NOT NULL 才表示必填。兩個匯入者可以先同時查到自然鍵不存在，再各自 INSERT；應用檢查之間有競爭窗口。UNIQUE 是資料庫寫入邊界的最後保護，讓重複值無法同時存在；它不自動替你決定衝突回應、交易重試或輸入是否合法等所有業務規則。

## 08｜交易 {#ch08}

若先更新版本、每句各自自動提交，再插入判定，第二句因 `CHECK` 失敗時，版本仍可能已加一；資料狀態不符合「版本與判定一起變更」的業務意圖。若兩步在同一交易內，錯誤後執行 `ROLLBACK`，版本恢復原值，失敗判定列不存在。若整組成功並 `COMMIT`，版本及新歷史列一起保存。實際成功流程若也更新 `current_judgment_id`，指標必須加入同一交易；本章簡化故障實驗只證明版本與歷史列的原子性。交易不取代 CHECK 約束，也不涵蓋外部通知。

## 09｜提交與持久性 {#ch09}

提交請求送出但應用沒有收到回覆時，伺服器已提交與尚未提交都仍可能；用戶端例外不能區分它們。應使用穩定操作識別碼重連查詢，再判斷是否需要重送。資料頁可能仍在 buffer pool，交易記錄已落穩定儲存時，完整持久性提交仍可由復原程序重做；這不等於涵蓋儲存裝置謊報寫入、媒體毀損或所有電力故障。支援更強復原主張要有指定環境中的故障注入、重啟與資料比對紀錄。若資料庫強制延遲持久性，回覆時記錄可能尚未落盤，故需先查設定。

## 10｜並行更新 {#ch10}

B 應先處理條件更新影響列數為 0：回報版本衝突，重新讀取目前狀態，重新評估操作是否仍成立；確認後才以新版本重新執行完整業務交易。不能只重送失敗 UPDATE，因為它的 expected version 仍是舊值，或因只重送最後一步而漏掉判定／指標一致性。以 `WHERE version_no = @expected_version` 作為原子檢查；影響 1 列才可插入事件並更新目前指標，否則不新增事件。事件 ID 也應避免與 A 使用的 ID 衝突。

## 11｜隔離層級 {#ch11}

SNAPSHOT 交易在 `BEGIN TRANSACTION` 後尚未存取資料時，第一個資料存取陳述式才取得交易序號／快照。若 A 在 B 首次讀取前提交，B 首次讀取可看到 A 的新版本；之後 A 再提交更新，B 的第二次讀取仍應看到首次讀取建立快照時的版本。基線 RCSI OFF 的 READ COMMITTED 以鎖處理讀取，兩個 SELECT 各自讀已提交資料，A 的更新若在兩次讀取間提交，第二次可能看到新值；若 A 尚未提交且持有衝突寫入鎖，讀取可能等待。RCSI ON 的 READ COMMITTED 也可能讓兩次語句看到不同狀態，但各語句讀的是各自開始時的版本，而非整筆交易固定快照。

## 12｜鎖等待與死結 {#ch12}

1205 表示 SQL Server 選了死結受害者並回滾該交易。確認原因後可以重試整筆可重入的業務交易，而非只重送最後一條 SQL。1222 表示 `LOCK_TIMEOUT` 到期，當前語句取消；明確交易可能仍在，先查 `XACT_STATE()` 並回滾或完成清理。應用程式自己的 command timeout 只證明用戶端停止等待，無法據此確認伺服器交易結果；需要檢查連線／交易狀態並用持久化操作識別碼查核結果。三者不能共用盲目 sleep-and-retry。

## 13｜索引 {#ch13}

對「查一個缺陷並依建立時間排序歷史」的候選，可用 `(defect_id, created_at DESC, judgment_id DESC)`；`defect_id` 是等值篩選，後兩個欄位供排序及平手決定。若讀取 `score`、`model_version`、`operator_name`，可將它們列為 INCLUDE 候選，減少回表，但需承擔儲存與寫入維護。三筆 seed 資料太少，無法代表目標選擇率或資料量；要以代表性資料執行查詢並比較計畫與 logical reads。若查詢改成全表按分數篩選，該索引的前導欄位不符合新查詢形狀，可能毫無幫助。

## 14｜查詢計畫 {#ch14}

至少記錄：結果列集合、估計與實際列數、logical reads、CPU／elapsed time、索引與資料量（也可另記 build、compatibility、統計狀態）。要支持索引對目標工作負載有幫助，需在相同代表性資料與查詢參數下，比較索引前後的實際計畫和多次讀取量，並考慮索引帶來的寫入及儲存成本。小資料集選 scan、大資料集選 seek 並不矛盾：最佳化器會按估計成本選擇，scan 可能在小表或高命中率下更便宜。沒有實測讀取量與工作負載證據時，只能提出候選，不能宣稱改善幅度。


## 15｜重送與重判 {#q15}

依本書精確文字比較契約，`m1` 與 `M1` 是不同意圖；同一操作 ID 必須拒絕，不變更任何資料。若所有意圖欄位相同，則回傳 Operations 所保存的舊判定與結果版本，不把 Defects 的目前值改回去。唯一鍵只能禁止相同 ID 同時存在，不能保證判定、目前指標與操作紀錄三者一起提交，也不能替你判斷同 ID 的 payload 是否相同。

## 16｜查不到的未知 {#q16}

先預測題：只看 t4 無法分辨 A／B。假設沒有其他寫入，只換新 ID、保留原 expected_version 時，A 已提交並推進版本，新請求會因版本衝突被拒絕；B 已回滾、版本未變，新請求可完成首次判定。若在 A 情境擅自換成目前版本並使用新 ID，便可能通過版本檢查，為同一原始意圖再新增一次判定。換 ID 會失去操作去重，但不代表一定能通過版本檢查。

不能把延遲副本的缺列當作主庫沒有提交。保存原 operation ID、完整意圖、錯誤、嘗試時間與目前 unknown 狀態，等待能查核權威資料庫。取得符合意圖且對應到固定判定的操作收據，才可回覆該操作成功；仍查不到、逾時或連線失敗時維持未知。原 ID 的協調重入可以避免產生第二次邏輯操作；換新 ID 則失去這個保護。

## 17｜通知重複與倒序 {#q17}

relay 沒有持久確認時通常需要補送，接收端用穩定 event ID 將去重紀錄與本地效果一起提交。避免倒序使目前值退回舊值，還需每個缺陷的業務版本或重新查權威目前值；event ID 去重只識別「是不是同一事件」，不比較不同事件的新舊。若效果是另一個外部服務，接收端本地交易仍包不住它。


## 18｜`legacy-unknown` 表示什麼？ {#q18}

它表示「這筆舊操作的真實來源無法由既有資料證明」，不是來源系統名稱，也不是資料庫已找到來源。回填只是把未知狀態明確寫下來；如果原始匯入紀錄、檔案或外部系統還有可核實線索，可以另做人工對帳後記錄新的證據，但不能因為欄位不再是 NULL 就宣稱血緣已知。

新 writer 忘記提供 `source_name` 時，contract 後的 `NOT NULL` 會拒絕 INSERT。contract 前，新增欄位仍允許舊 writer 留 NULL，所以服務或監控要查 `WHERE source_name IS NULL`；回填完成後的零筆只代表查核當下沒有 NULL，還要確認不再有舊 writer 在部署期間新增 NULL。不要替 `source_name` 加預設值 `legacy-unknown`，因為那會讓新程式漏傳來源也通過。

## 19｜VERIFYONLY 成功，還原為何仍可能失敗？ {#q19}

兩者檢查不同內容。`RESTORE VERIFYONLY` 可檢查備份組完整與媒體可讀，但不會真的配置目的檔案或還原資料庫，也不驗證資料結構；還原時若 SQL Server 主機無法存取新資料／記錄檔路徑，或 logical name 對錯、備份組其他部分有問題，仍可能失敗。應以 `RESTORE FILELISTONLY` 取得備份邏輯檔名，選新的服務端路徑與未使用的目標資料庫名稱，再實際 RESTORE。

「指定判定已恢復」至少需要：實際還原完成、`DBCC CHECKDB` 的檢查結果、恢復的目標時間／備份鏈明確，且讀回指定 `defect_id` 的目前指標、指標所連的 Judgment，以及要保留的 Operations／歷史列。只有列數相同不足以證明列內容相同；可對指定欄位做雙向 `EXCEPT`，並查外鍵所表達的不變條件。源庫若在備份後仍有新寫入，直接拿現況和較舊備份比較，差異不一定是還原錯誤；要以備份截止點的預期狀態作基準。量得的還原時間和資料遺失範圍要來自實際演練，不能由範例推估。

## 20｜目前判定與一次操作結果，如何分開查？ {#q20}

`dbo.Defects.current_judgment_id` 決定目前判定。查目前分數時，用 `defect_id` 和 `(defect_id, current_judgment_id)` 對上 Judgment；`created_at` 即使比較晚，也不會覆蓋此明確指標。兩筆時間相同時，僅排序 `created_at DESC` 無法唯一選列；加 `judgment_id` 只能讓排序有固定平手規則，仍不能證明編號較大就是業務上目前。

本題沿用 seed 的 102：它沒有 Operations 列，故只能證明目前指標指向 102，不能從現有資料證明它來自哪個請求。對後續由程序新增的判定，才可沿收據追溯。

舊 operation 重送時，先以 `operation_id` 找到 Operations，核對其目標與所有意圖欄位，再沿 `Operations.judgment_id` 取得當次 Judgment。這是回覆「該次請求造成什麼」；查 `Defects.current_judgment_id` 則回答「現在目前是什麼」。若同一 defect 後來有新判定，兩個答案理應不同。Operation 的 `expected_version`／`result_version` 說明版本轉移，Judgment 保存分數、模型、操作者和紀錄時間；第 18 章新增的 `source_name` 標記來源類別。現有 schema 沒有原始影像或完整模型輸入，故無法只靠這些列重播原始推論。

## 21｜清掉收據後的舊 GUID 要如何處理？ {#q21}

第 45 天的舊請求把到期欄改成第 60 天，若它改寫了服務端簽發的憑證內容，驗簽會失敗，服務應拒絕，不能信任客戶端時間。若服務端真的簽發了一張有效至第 60 天的憑證，卻只保留 30 天操作列，則保留規則違反有效窗口；收據可能已在憑證到期前刪除，不能自動當成首次執行，應撤銷／隔離此類 token 並查核。保留期限必須覆蓋服務允許的最晚到期時間。

若第 1 天是首次送達，沒有收據是正常狀況；用相同 ID 在同一安全處理入口執行整筆交易即可。若它是提交回應不明後的重試，也不能只憑「查不到」斷言舊交易未成功；權威主庫查詢、收據尚未清除、無還原遺失、同一交易原子保存業務效果與收據、operation ID 主鍵及 expected-version 條件，都必須成立。符合這些前提時，可用完整原 ID 再進入同一交易：舊提交若存在會命中收據並回原 Judgment；若兩個同 ID 請求並行，唯一鍵只允許一筆提交，另一筆回滾後重新查核。若前提不成立或意圖不一致，停止自動重入並人工對帳。這裡的安全性來自可重入的原子交易契約，不是單看缺列；真正的新判定仍要使用新的 operation ID 和憑證。

目前 schema 沒有逐筆保存 `expires_at`／epoch，也沒有獨立的 Operations 建立時間；用 `Judgments.created_at` 估算候選年齡，只能在「判定與操作同一交易建立」且有效期有服務端上限、created_at 由 DB 預設或受控服務端提供的前提下保守使用。需要逐筆核對期限時，應保存受驗證的發行資訊或保留收據；若 Operations 兼負歷史來源鏈接，刪除也會犧牲稽核證據。保留期限由最長合法重送窗口與業務／法規保存要求共同決定，不能由客戶端時間或本章任意選一個天數。

## 設備校正遷移題：評閱提示 {#transfer}

可以用廠區加設備代號作業務鍵，另設設備代理鍵。校正事件保存量測值、單位、方法版本與輸入來源；量測值要有適合精度的型別與範圍，不直接套 AOI 的 0–100 分。每個操作保存不可變意圖與當次校正結果，設備目前值與歷史查詢分開。

合格答案須能説明相同 ID 的精確比較範圍、條件更新何時失敗、失敗後交易怎樣清理，並用雙連線證據確認。升版保留舊資料中的未知來源，不偽造來源。保留窗口尚未決定時，不應加自動刪收據工作；至少先確認最長離線／重送契約。

這不是唯一模型。若採不同的目前值表示或並行策略，只要能指出不變條件、提供反例、說明限制並實測，就可成立。只用功能展示、同一 session 的 SELECT 或備份檔大小，不能替代題目要求的證據。
