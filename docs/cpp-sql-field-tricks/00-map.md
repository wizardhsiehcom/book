# 全書地圖：先拿回一次工作的控制權

不要一開始就把「整個系統正確」當成一次實驗的目標。先讓一筆資料能重跑，再問哪一段與預期不同。每次得到結果，都要知道它排除了什麼、還沒碰到什麼。

```mermaid
flowchart LR
    A["01–04<br/>同一產物、同一輸入"] --> B["05–09<br/>讀取與參數邊界"]
    B --> C["10–12<br/>寫入、回滾、等待"]
    C --> D["13–15<br/>時間與失敗範圍"]
    D --> E["16–17<br/>比對與交付"]
```

看箭頭帶走的東西：前一部留下可重跑基準，後一部才有資格把差異歸因於單一條件。這不是強制解鎖順序；如果手上已有基準，可以直接查症狀。

## 第一次讀的路線

先完成[環境與範例](appendix-lab.md)。依序讀 01–04，學會用固定入口控制核心；05–06 看懂資料真正進 C++ 的樣子；10–12 再碰寫入與等待；13–15 釐清慢與失敗；16–17 收尾。07、08、09、14 在遇到對應症狀時插入。

`handle` 是 ODBC 操作物件的識別，不是資料列；`connection` 對應一次資料庫連線；`statement` 在連線上送出 SQL 和讀結果。這三個詞會在第 05 章用錯誤紀錄具體接起來。交易和鎖則等第 11–12 章真正需要時再補。

## 三種成果，不必走向同一種架構

一次查詢保留紀錄就好；每天要重跑的命令留成小腳本；在有限目標上很好檢查的固定映射，也可以是可交付方案。把它正式化之前，先問有沒有人反覆使用、錯誤成本多高，而不是問它看起來夠不夠「工程化」。
