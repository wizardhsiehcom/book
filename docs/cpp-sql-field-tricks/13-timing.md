# 13｜慢的可能不是查詢，是你拿到資料之後做的事

使用者說「查資料要三十秒」，你就開始找索引。但按鈕背後還有連線、取列、字串轉換、核心計算、逐筆寫回與通知。只量按下到結束，你沒有足夠證據把時間分給 SQL。

## 先讓一段時間有名字

本章先用三段足夠小的測量：execute、fetch＋mapping、core。範例使用 `steady_clock` 算經過時間，避免牆上時間校正干擾差值。它不是跨機器的事件時鐘，也不自動等於 CPU 使用時間。

先跑沒延遲的基準：

```powershell
.\run-sql-case.ps1 timing-base
```

記下三段與 score 20。再只換成核心前故意等待 120 ms 的版本：

```powershell
.\run-sql-case.ps1 timing
```

預測變慢的是 core 段，而不是 execute。這兩條路徑共用一筆 SQL 與 `process_job`，差別只有 `sleep_for`；故意等待不做計算，所以 core 段變長也不代表演算法吃 CPU。

## 用假延遲驗你的尺，不拿來宣稱效能

本版在注入版本看見 core 段超過 120 ms；實際時間受排程影響，沒有要求恰好 120。再跑一次 baseline，確認沒有把每輪都在變的資料量誤認為 delay 的效果。精確示例記在[實測頁](appendix-validation.md)，它們不是性能承諾。

如果增加的時間落到 execute，先檢查計時點是不是跨過另一段工作；如果三段加總比總時間少很多，差額可能在建連、檔案輸出或你沒包到的清理。不要把「其餘」默默分配給你懷疑的函式。

## 真專案再按需要拆細

| 邊界 | 先固定什麼 | 看什麼差異 |
|---|---|---|
| connect | 端點、driver、是否新程序 | 建連／重用成本 |
| execute | SQL、值與型別、交易 | 伺服器與首個回應等待 |
| fetch／轉換 | 完整列數、欄位與輸出量 | 取資料與轉型成本 |
| core | 同一 fixture、相同規則 | 計算或內部等待 |
| write／commit／notify | 相同工作量、效果契約 | 寫入、提交及外部等待 |

上表後兩類外部階段不是本版三段計時器全都量過的內容，而是移植位置。execute 返回不保證所有列都已傳完；工具只顯示第一頁、程式卻讀完全部，也不是公平比較。

關掉逐列 log 可能變快，代價是少了觀測；留下總列數、結果摘要與必要樣本再比。把寫庫換成本地檔只能診斷那個階段的成本，不能把替身速度當成正式吞吐量。
