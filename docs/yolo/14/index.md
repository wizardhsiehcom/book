# 改進流程：可重現基線、假設與接受閘門

改進不是「在測試集上看數字漲就上線」。正確順序是：先鎖住可重現的[基線](../07/index.md)與協定，再對[資料](../04/index.md)與[標註](../05/index.md)做稽核，提出可證偽的假設，做受控變更，用驗證集選實驗，最後才對一次未動過的測試集做最終判定。測試集用來當發布閘門，不是用來挑模型。

## 為什麼測試集不能當選模器

驗證集的工作是比較實驗：哪個假設成立、哪個變更該留下。測試集必須在最終候選與協定都鎖定之後才碰一次。若最終測試未過發布閘門，應停止發布並調查，而不是對著同一份測試集反覆調參。若要重新主張「新版本更好」，需要一份新的、事先保留的 held-out，而不是把舊測試集再當調參盤。

測試集與驗證集的落差本身，不能單獨證明過擬合。落差也可能來自抽樣波動、領域外洩漏、標註錯誤，或推論協定不一致。要診斷，應回到[評估定義](../06/index.md)、[錯誤分析](../13/index.md)與[基準協定](../19/index.md)，而不是直接把「測集掉了」當成過擬合鐵證。

## 假設、單因子與交互

單因子變更適合當第一刀：一次只改一件事，較容易把因果對上。這不是教條。當因子會交互（例如輸入尺寸與增強、後處理閾值與延遲），後續應改用受控的析因設計，而不是永遠假裝世界是可加的。固定種子有助於版本對版本比較；換種子做重複則用來揭示變異，兩者並不互斥，也不是「禁止換種子」。

公開文件層面（查閱日期 2026-09-08），Ultralytics 訓練提示把 `scale` 描述為縮放／填充／裁切這類幾何增強，把 `multi_scale` 描述為訓練時改變輸入尺寸；`patience` 用於早停。訓練模式的 API 參考見官方 `modes/train` 文件。此處不捏造預設值；實際鍵名與行為以當日文件為準。見 [Model Training Tips](https://docs.ultralytics.com/guides/model-training-tips/) 與 [Train](https://docs.ultralytics.com/modes/train/)。

## 品質指標必須具體

「品質分數變好」無法當閘門。偵測任務應先寫死指標：例如以 COCO 風格的 AP50:95 當主指標，召回當輔指標，而不是把兩者混成一句「比較準」。延遲同樣要寫死：同一硬體、同一 batch、同一精度、同一計時協定（含前處理與後處理的端到端，或明確排除哪一段），才能和[推論](../11/index.md)與發布預算對齊。

## 合成示例：先過延遲閘門再談測集

下列數字是合成示例，不是實測。基線：`imgsz=640`，AP50:95 = 0.41，端到端 P95 = 22 ms。候選：把輸入改到 `imgsz=960`，AP50:95 = 0.43，端到端 P95 = 48 ms。發布預算是端到端 P95 ≤ 30 ms。候選在驗證階段就已超出延遲預算，應在碰測試集之前拒絕。接受的是「協定內同時滿足準確率與延遲」；拒絕的是「準確率微升但延遲爆預算」。這與 `multi_scale`（訓練期變尺寸）不是同一件事：此例是部署輸入尺寸變更，應單獨記錄，避免和增強裡的 `scale` 混名。

## 失敗診斷與接受條件

若驗證集上升、測試集下降：先查標註一致性、類別定義漂移、以及是否有驗證集洩漏進訓練。若延遲在開發機合格、目標機不合格：先對齊硬體、精度與計時，而不是立刻改架構。若早停很早觸發：檢查 `patience` 對應的監控指標是否就是你要優化的 AP50:95，而不是另一個代理損失。

接受閘門應事先寫下，例如：驗證集 AP50:95 不低於基線、端到端 P95 在預算內、錯誤類型沒有不可接受的新失敗模式，且測試集只在候選鎖定後評估一次。通過則可進入[後續改進](../14/index.md)的下一輪假設；失敗則停發布、調查，不對同一測試集調參。
