# 第 04 章　資料設計

YOLO 專案在標註工具與訓練指令之前，先要能回答三件事：場景有沒有被資料真正覆蓋、類別名稱與標註契約是否凍結、切分有沒有把同一來源的相鄰樣本同時放進 train 與 val。這三件事做錯，後面的 mAP 數字再漂亮也只是在測記憶，不是在測泛化。

本章把資料當工程物件來管，不把「多抓一些圖」當成策略。覆蓋決定你能不能在現場條件下工作；類別契約決定標註、yaml、後處理與產品文案能不能對上同一套名字；切分與版本凍結決定實驗能不能重跑、能不能拿 val 做早停、能不能拿 test 當一次對外數字。

## 這一章要解決的決策

- 任務場景、負樣本、長尾類別要怎麼列清單，而不是憑感覺補資料。
- 類別 id、名稱、空類、忽略區要寫成可執行的契約，避免訓練與部署各講各的。
- 同影片相鄰影格、同 camera、同 session 為何會造成洩漏，切分單位該用什麼。
- train / val / test 各自能做與不能做什麼；用雜湊找重複的限制在哪。
- 資料 manifest 與版本凍結要寫到什麼粒度，實驗才回得去。

## 章內頁面

- [場景覆蓋、負樣本、長尾與類別契約](coverage.md)：先把「資料夠不夠」拆成可檢查的覆蓋表與契約，再決定要不要加圖。
- [切分、洩漏與版本凍結](split-and-version.md)：按 group 切分、避開不穩定的 `hash()`、寫 manifest、凍結版本。內附可執行的標準庫切分與 `assert` 自查。

## 讀完應能交出的產物

1. 一張場景 × 條件 × 類別的覆蓋表，標出缺口與負樣本來源。
2. 一份類別契約（名稱、id、空類政策、忽略規則），與 `data.yaml` 對得上。
3. 以 camera / session / 影片 / 時間窗為 group 的切分規則，以及對應的 manifest 與版本號。
