# 評估 YOLO 部署：堆高機行人預警的代價與指標

設一座倉儲要在堆高機動線上做行人預警。漏報一次行人，車輛可能繼續前進，後果是碰撞風險；誤報一次，堆高機無謂減速，班次被打斷。假設現場把一次空報估成約三十秒產能損失，把一次漏報估成不可接受的接近事件。兩種成本不對稱，評估就不能停在「模型準不準」，而要問：這個營運點每班會空報幾次、會漏掉幾次真實行人事件。

本章有三個目標。第一，把單張影像上的對與錯定義清楚，再接到框對齊與分數門檻。第二，把精確率、召回率換成現場讀得懂的事件率。第三，把驗證集上的摘要數字，和線上真實事件分開看。Ultralytics 驗證模式與 COCO 評估器是公開的指標算法來源，用來計算平均精度一類標準數字；營運點怎麼切、事件怎麼算，則是應用工程協議，不是套件替你簽的安全證明。偵測模型單獨通過指標，絕不代表預警系統已通過安全認證。

閱讀順序依概念依賴。先分清真陽性、假陽性、假陰性，見[對錯三種計數](tp-fp-fn.md)。「對上了」靠交並比：訓練時的樣本指派、指標計算、推論時的非極大值抑制，各自可以使用不同門檻，沒有宇宙通用的 IoU。訓練指派是一條規則，可以結合多種匹配指標或 top-k，不能把某個 0.5 門檻誤當成唯一真理，細節見[IoU 的三種角色](iou-three-roles.md)。有了對錯才談[精確率與召回率](precision-recall.md)。分數切在哪裡決定你活在哪一個營運點，見[信心門檻](confidence-cutoff.md)；切完之後，才有現場在乎的[事件率](event-rate.md)。[平均精度與 mAP](ap-map.md)是跨許多門檻的摘要，適合比較模型，不能直接當警報開關。[驗證與測試](validation-test.md)決定這些數字能不能外推。門檻掃描的合成示範見[threshold_demo.py](examples/threshold_demo.py)。

用一組合成數字把落差講死。某班次兩百趟通過路口，其中八次真有行人。系統發出十二次警報：六次對上行人，六次空報，兩次行人沒響。事件層的精確率是六除以十二，召回率是六除以八；換成事件語言，則是每班六次空報、兩次漏報。若驗收寫成「每班空報不得超過四次、漏報必須為零」，這個營運點立刻不合格——即使驗證集 mAP 看起來體面。mAP 平均了許多分數門檻；現場只活在一個門檻上，而且事件發生在時間軸，同一行人連拍多幀也不該重複計成多次漏報。

常見失敗有四種：用驗證 mAP 代替漏報事件數；把訓練指派用的 IoU 誤當成指標 IoU；把信心門檻調高就宣稱系統更安全；在同一批圖上又調門檻又宣稱泛化。驗收應分開寫兩層。指標層：依公開評估器在保留集合上報告指定 IoU 與類別的精度摘要。事件層：用事先寫死的時間窗、去重規則、班次分母，量測空報率與漏報率。安全相關決策需要獨立的系統安全流程與現場控制，不能由偵測分數單獨背書。公開說明見 [Ultralytics Val](https://docs.ultralytics.com/modes/val/)；COCO 評估器則是常見 AP 實作來源。兩者都不替你定義虛警預算。
