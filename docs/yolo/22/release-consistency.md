# 發布與載入一致性：服務真的換到哪一版？

`current` 已指向新版本，推論服務卻仍持有舊模型。若健康頁只回答「程序活著」，工作台就會誤報發布成功。

本頁沿用 [監控與回滾](monitoring-rollback.md) 的不可變套件，補上切換、載入與恢復的判準。範圍限定為單機、單一發布控制者、允許短暫停機；多副本滾動更新需另驗路由及版本混用，不能套用本頁結論。

## 三個版本欄位分開記

| 欄位 | 由誰提供 | 能證明什麼 |
|---|---|---|
| 目標 `desired_release` | 發布要求 | 想切到哪一版 |
| 指標 `current_release` | 磁碟上的 current | 新啟動者將解析到哪個套件 |
| 載入 `loaded_release` | 實際推論程序 | 該程序本次載入的完整套件身分 |

服務要在載入模型、設定與探測推論成功後，才回報 ready，並提供 `session_id`、`release_id`、套件清冊摘要與探測結果。回報須從本次實際解析及載入的套件取得，不能只照抄發布要求。

啟動時將 current 解析成一個不可變版本根目錄，模型與設定都從該根讀取；不要每讀一個檔又重新解析 current。否則切換期間可能讀到新版權重與舊版類別。正在使用或作為回滾目標的套件不可刪除。

## 先有合格候選，再切換

候選必須通過 [生命週期追溯](../07/lifecycle-lineage.md) 的關係檢查與 [評估門檻](../14/index.md)。缺報告、模型摘要不符、必要切片未覆蓋或指標不合格，發布入口應拒絕，並保持現行服務與 current 不變。

完整清冊至少涵蓋權重、類別、前後處理、門檻與環境契約。第 23 章現有 `manifest.py` 只核對它列出的四個檔案；擴充套件時也要擴充清冊與驗證，不能因原腳本印出 OK 就推論新欄位已驗證。

## 可恢復的切換順序

1. **準備**：先核對候選與上一個已驗證版本。保存 `activation_id`、前版、目標版、評估引用及 `prepared` 狀態。同時只允許一個切換作業。
2. **停止**：停止接受新工作並等待舊服務完成收尾。超過事先設定的期限就標失敗；未確認舊程序停止前不得宣稱已換版。
3. **切換**：在同一檔案系統內，建立暫存指標，再原子替換 current。只替換受控的指標，不覆寫完整套件。
4. **載入**：用新的 session 啟動服務，解析一次套件根、核對摘要、載入模型與設定，完成固定探測。
5. **確認**：在有界等待內取得該 session 的 ready；載入版本和摘要均等於目標，再保存 `activated`，開始接受工作。

同一 `activation_id` 的重送必須保留相同前版與目標；意圖不同即拒絕。若查核時 current 已被其他作業改動，先停止此次操作並處理衝突，不能用過期的前版紀錄覆蓋較新的發布。

Python 的 [os.replace 文件](https://docs.python.org/3.13/library/os.html#os.replace) 說明成功改名的原子性，以及跨檔案系統可能失敗。這只涵蓋名稱切換，沒有把模型載入、程序重啟和發布紀錄變成同一筆交易；Windows 的符號連結權限也需另驗。上述流程為本書設計，沒有宣稱已在服務上實跑。

## 每個空窗都要有恢復答案

| 當機／失敗的位置 | 恢復時先看 | 可以做的決定 |
|---|---|---|
| 已保存 prepared，尚未停止 | 現有 session、current、切換紀錄 | 確認無其他控制者後繼續，或取消此次切換 |
| 舊服務停止，current 尚未改 | 前版套件與停止證據 | 繼續切換；若取消則啟動前版並重新驗證 ready |
| current 已改，服務未 ready | current 與目標是否一致、有無殘留候選程序 | 確認程序停止後重試載入，或回滾 |
| 候選 ready，成功紀錄尚未保存 | 本次 session 的實際載入摘要與探測 | 符合目標則補記 activated；不能只讀 current |
| 查詢回應遺失 | 同 activation 的持久紀錄及服務觀察 | 先查核；無證據就保持 unknown，不盲目再發布 |

重啟後舊 ready 檔只能當歷史紀錄。要確認目前可服務，必須聯絡目前程序或重新啟動探測。只讀舊檔，會把早已退出的 session 當成活著。

## 回滾也要走完載入確認

候選載入失敗時，先停止並確認候選程序退出，再核對前版完整套件，把 current 指回前版，以新 session 啟動並驗證 ready。記錄目標、原因與實際載入身分後，才可標 `rolled_back`。

若前版也缺檔或無法載入，狀態為 `recovery_failed`，服務保持停止並明示不可用。指標指回去了，但舊模型沒有成功載入，不能報「已恢復」。第一次部署沒有前版時，失敗就維持未就緒狀態，不捏造回滾目標。

探測只證明指定輸入可執行與版本對齊。上線品質仍需 [監控與回滾](monitoring-rollback.md) 的代表性標註與現場監測；程序中斷測試亦不能當成斷電耐久性證明。

## 練習與判準

`desired=r3`、`current=r3`，ready 回報卻是 `loaded=r2`。可以標 activated 嗎？若 r3 載入失敗，r2 的類別檔也遺失，能否只把 r2 權重複製回去？

### 核對答案

兩者都不可以。第一題缺少目標版本的實際載入證據；應查錯誤 session、快取或設定路徑。第二題缺少完整回滾套件，應標恢復失敗並停止服務，從可信備份恢復完整版本後重驗。
