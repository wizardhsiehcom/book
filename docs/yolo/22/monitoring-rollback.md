# 監控與回滾

上線後真正要盯的，不是儀表板上某一條線是否好看，而是這次釋出是否仍與當初驗收過的那份品質敘事一致。信心分數與偵測數量的漂移，頂多是代理指標：它們可能反映場景改變、門檻改變、或標註習慣改變，卻不能單獨證明模型變好或變壞。實際品質仍須靠具代表性、且經過稽核的標註樣本來對照；沒有這層錨點，監控只是在追自己的影子。

可回滾的前提是盤點不可變。每一次釋出都應留下一份清冊：模型權重、訓練與校驗資料版本、類別定義、前處理、偵測頭、數值精度、執行環境、校準方式與決策門檻。清冊不是備註，而是之後比對「現在跑的是不是當初簽過的那一份」的唯一依據。驗證產物雜湊時，應依程序的結束狀態判斷成敗，而不是看殼層輸出是否非空——非空輸出可能只是警告、進度列或無關雜訊，結束狀態才對應契約是否成立。

流量切換同樣要分層。影子路徑只記錄候選推論，不對生產發出任何動作，因此不能拿影子「看起來正常」當上線許可。金絲雀路徑才承載真實流量，且品質、延遲與回滾條件必須事先寫死：未達標就停，而不是臨場開會。推論參數本身請對照官方說明（見 [Ultralytics Predict 模式](https://docs.ultralytics.com/modes/predict/)），本文不重述旗標細節。

平台中立的順序手冊可以固定如下，實作由部署專案提供，本文不給可執行服務或殼層指令。先依該服務既有的操作程序停止現行推論；再驗證候選產物與清冊一致；在同一檔案系統上以暫存符號連結再原子改名接到 current，避免跨裝置改名留下半套狀態；以新的追蹤工作階段重啟；檢查健康條件。任一步失敗，就還原到上一份已驗證釋出，而不是修補正在跑的那一份。Windows 上建立符號連結的權限因站點而異，必須在現場確認，不可假設開發機設定可直接搬到產線。

以上是工程建議，不是對所有組織一體適用的強制令。規模、法遵與值班編制不同，閘門寬嚴可以調整，但「代理指標不能取代稽核標註、清冊不可變、影子不動作、金絲雀有預設回滾、改名在同一檔案系統上完成」這幾條，是讓監控真正連得上回滾的最小結構。細節與現場接線見 [邊緣部署專案](../23/edge-deployment.md)。
