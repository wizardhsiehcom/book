# 持久化任務：中斷後先查證，再決定重跑

訓練程式結束前已寫出模型，工作台卻在更新狀態前被停止。重新開啟時，只看到 `running`。直接重跑會多花一次訓練成本；直接標成功，又可能把半寫的模型交給評估。

本頁教你把「想完成的工作、執行嘗試、完成證據」分開記錄。先讀 [checkpoint 與實驗紀錄](checkpoints-and-records.md)；checkpoint 如何接續沿用該頁，本頁處理訓練外面的工作流程。以下是單機、單一工作執行者的教學契約，並非 Ultralytics 內建的任務系統。

## 三種身分各自回答什麼

| 身分 | 問題 | 重送時的規則 |
|---|---|---|
| `job_id` | 使用者要求完成哪件事？ | 同一要求保留 ID；完整輸入意圖必須相同 |
| `attempt_id` | 哪一次執行產生這些證據？ | 每次真正重新執行都新建，保留舊嘗試 |
| `run_id` | 這是哪一條訓練實驗？ | 純 resume 可沿用；改資料、設定或起點應另開實驗 |

「輸入意圖」至少包括階段名稱、不可變輸入版本、程式與設定摘要。以相同 `job_id` 送來不同意圖要拒絕；不同 ID 的相同輸入則可以是刻意重複實驗，不能自行合併。版本欄位見 [生命週期追溯](lifecycle-lineage.md)。

在回覆「已接受」之前，先保存工作與輸入意圖。記憶體 queue 只用來排程，重啟後的待辦以持久化紀錄為準。JSON 檔或資料庫是儲存方式；是否能可靠恢復，取決於下面的轉移與證據規則。

## 每次嘗試的狀態

| 狀態 | 意義 | 可以接下游嗎？ |
|---|---|---|
| `queued` | 已保存要求，尚未啟動 | 否 |
| `running` | 已記錄執行者與嘗試，正在工作 | 否 |
| `succeeded` | 產物完整、身分相符，完成證據已保存 | 可以交給下一階段；不代表模型合格 |
| `failed` | 已知執行失敗，附錯誤與剩餘產物 | 否 |
| `interrupted` | 已確認舊執行者停止，結果仍需查核 | 否 |

`unknown` 是查詢端目前拿不到證據的觀察，不要因查詢逾時就把工作改為 `failed`。`rejected` 則是評估結果：評估程式可以成功完成，同時判定模型不得發布。

正常轉移為 `queued → running → succeeded / failed`。重啟時先確認舊執行者及其子程序已停止，才能把遺留的 `running` 改成 `interrupted` 並查核。只看 PID 不足以辨認原程序，PID 可能重用；應結合啟動身分與程序擁有權。無法確認時停止自動接手，避免兩個執行者同時改同一份輸出。

重試保留原嘗試的結局，新建 `attempt_id`。若發現原嘗試其實已有完整完成證據，可補記 `succeeded` 及查核原因，不需重跑。

## 產物和狀態之間的空窗

採用以下可恢復順序，輸出目錄以嘗試身分隔離：

1. 保存 `running`、輸入意圖與 `attempt_id`。
2. 寫到該嘗試的暫存目錄；下游只接受正式完成目錄。
3. 關閉產物，檢查預期檔案、大小、雜湊與格式；產生包含輸入身分的完成清冊。
4. 將完整目錄發布到尚不存在的正式位置；不得覆寫另一個嘗試。
5. 再更新任務為 `succeeded`，連到完成清冊。

完成清冊要由該階段在成功完成後產生。不能在重啟時對任意殘留檔算個雜湊，就把它升格為完成證據。模型格式能讀取，也不等於訓練已達約定的停止條件。

| 中斷位置 | 重啟後看到什麼 | 處理 |
|---|---|---|
| 第 1 步前 | 沒有接受紀錄 | 同 ID 可重新提交；呼叫端先查詢 |
| 第 2 步中 | `running` 加暫存檔 | 確認舊程序停止；隔離殘檔，再決定 resume 或重跑 |
| 第 4 步後、第 5 步前 | 完整正式產物，但狀態仍舊 | 核對清冊、輸入與檔案後補記成功 |
| 第 5 步後 | 成功紀錄與完整產物 | 回傳原結果，避免重做 |
| 查到成功，但產物遺失或不符 | 紀錄與儲存不一致 | 封鎖下游並記錄完整性故障；不得靜默改檔 |

這個順序是本書的設計建議。SQLite 的交易可以保護資料庫內的狀態更新，外部模型檔案仍需上述查核流程。[SQLite 原子提交文件](https://www.sqlite.org/atomiccommit.html) 說明 journal、提交與恢復，以及對儲存系統的假設；它不替工作台驗證模型是否完整。

## 恢復策略要按階段選

- **資料檢查與評估**：固定輸入與程式後可以重跑，但保存每次嘗試；評估資料或協定變動時另建工作。
- **訓練**：先確認 checkpoint 可接續及設定相容；不成立時新開 run，記錄來源與成本。
- **發布**：先核對發布紀錄、目標版本與服務載入回報。回應遺失時不得盲目再切換，詳見 [發布與載入一致性](../22/release-consistency.md)。

教學驗證先限於程序中斷與重啟。斷電、作業系統崩潰、網路檔案系統與多執行者協調須另訂儲存及接手契約，不能由一次程序重啟測試推論已涵蓋。

## 練習與判準

1. `job-7` 已有完整輸出，但狀態是 `running`。列出可以補記成功前必須查的證據。
2. 同 `job-7` 重送，資料從 `ds-1` 換成 `ds-2`，可否沿用？
3. 評估程式正常結束，夜間召回低於門檻。任務與發布結果各是什麼？

### 核對答案

1. 舊執行者已停止、嘗試與輸入意圖一致、正式完成清冊存在且可信、檔案與清冊相符、階段完成條件成立。只看副檔名或 exit code 不足。
2. 拒絕同 ID 改意圖；建立新工作及適當的新 run。
3. 評估嘗試為 `succeeded`，候選的評估決策為 `rejected`，發布入口必須拒絕。
