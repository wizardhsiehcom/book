收尾前先確認結果已留存。刪掉唯一故障容器後才想起要 cp，沒有一條命令可以回到同一個現場。以下是資源類型索引，實際名稱與命令以各章當輪變數為準。

## 撤回也需要一個觀察值

「改回去了」最好有具體核對。例如入口回復後 inspect 的 Entrypoint 正確；Compose 用原配置建立的新容器讀到原值；暫時換掉的掛載已恢復原來源。只刪除暫存檔不一定恢復執行狀態。

映像刪除和建置快取清除是不同操作。本書不要求清除共用 base image，也不要求清除全機 cache。暫存目錄故意先保留給你核對原始輸出，確認不用後再按完整路徑刪除，不從模糊的 shell 變數批次清理陌生目錄。

## 何時不要讓土法變成永久系統

只為一次調查加的 delay、假資料或 sleep 入口，結案就撤回。反覆有用的動作可以留下，但先說清楚誰維護、何時失效、怎麼知道它壞了。如果一個捷徑需要每次由資深工程師手動記住五件事，那些人工成本已經是設計的一部分。

正式化不一定需要新平台。一條版本化命令、一個小回歸輸入、一個針對產物的 assertion，常常就足夠。只有當這些簡單方法已經表現出明確上限，再考慮更通用的工具。

## 從 C++ 的 `test_mode` 與 Python 的 `uv` script 回看

這套判準不只適用 Docker。接手 C++ 專案時，常會看到一個寫在程式碼區塊裡、靠手動開關的 `test_mode`。它可以是很好的第一支探針：先讓某個分支可重現，觀察副作用與錯誤邊界，再決定要不要把它改成命令列選項、測試 fixture、依賴注入或正式的 feature flag。但若它能被正式 binary 帶到 production，且唯一的關閉保證是「記得上線前改回去」，就不能把它當成已完成的工程設計。

`uv` script 則把一次性的 Python 檢查包成可重跑的命令，並把腳本依賴與執行方式放在同一個交接點。它的正式化方向通常不是把腳本硬塞進產品，而是確認它是否值得留下：偶發調查就保留紀錄後刪除；反覆使用就版本化、固定輸入與依賴，補上退出碼和最小驗收；再往後才判斷是否需要併入正式工具或 CI。

兩者和本書的 Docker 招式共用同一條路徑：**臨時改動不是答案，而是取得下一個答案的受控方法。**
