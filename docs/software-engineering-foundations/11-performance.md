# 效能：先知道時間花在哪裡

unordered_set 的版本比較漂亮，但總時間沒變。這不代表理論錯了：也許 parse／查重只占一小段，絕大部分時間在逐張查遠端圖片。

## 定義計時範圍

先說量的是什麼：只有查重、整份清單解析、所有檔案 metadata，還是整支 CLI 的啟動到結束。範圍不同，數字不能互相比。用 steady_clock 量一段經過時間；不要把時鐘解析度誤認成每次測量的精確度。

固定資料量、輸入內容、硬體、編譯旗標與本地／遠端檔案條件。多次測量看分布或中位數，不只挑最快一次。小工作太短時，啟動與測量本身可能占大部分，可重複同一純計算再攤平，但要防止最佳化把無用結果消掉。

## 先找瓶頸再換做法

在 C00，可先用只解析的局部實驗比較 G02／G03，再量完整報告。如果只解析明顯改善而整體沒差，優化方向可能要轉向 filesystem 呼叫或部署條件。不能因總時間不變就盲目開 thread；併發會加入排程、共享資源與錯誤收尾的成本。

量測記錄至少有命令、版本、輸入規模、範圍、原始結果和解釋。CPU profiler 能指出熱點，但取樣結果也有觀測條件，不是每個短函式都能精準計到。

**Q11：** 要比較兩版查重，能不能讓一版讀本地 SSD、另一版讀 NAS？為什麼 Release／Debug 也要一致？
