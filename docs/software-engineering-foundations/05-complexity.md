# 複雜度：清單變大時，哪件事增加最快

每新增一列，就跟所有舊列比較身分。三筆資料看不出問題，三萬筆可能把比較次數推到數億。

## 先數工作量

n 筆互異資料，逐筆查重的比較數是 `0 + 1 + ... + (n-1)`，即 `n(n-1)/2`。這是最壞輸入的一種明確計數，不是猜測毫秒數。C00 G03 用 seen 集合避免每次掃完整份前綴，在平均雜湊行為下把整批查重的期望成本降到線性附近。

大 O 說明規模成長的階數，省略常數，不保證某台機器的小輸入必然更快。集合分配、hash 計算都要成本；若總共十筆，簡單掃描可能已經夠用。此處保留兩個版本，是為了學會判斷規模，而不是規定任何查找都用 hash。

## CPU 工作與 I/O 不同

整個工具仍要查檔案。若每次 filesystem 查詢都等遠端檔案系統，省下 CPU 比較不一定改善總時間。先把解析、查重與檔案檢查分開量，再選瓶頸。把總時間全部歸因給容器，是跳過觀察。

執行書附原理實驗，它會核對 4 與 8 筆掃描的比較次數。接著推導 16 筆，不必先跑 benchmark。若改成每次呼叫 `reserve(size+1)`，也要思考會不會破壞容器原本的成長策略。

**Q05：** G03 不再兩層 for，可以直接宣稱整個檔案檢查器是嚴格 O(n)、而且一定更快嗎？你還需要說明哪些假設？
