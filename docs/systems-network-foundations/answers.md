# 解答

## 各章

**Q01.** 不可以。STARTED 只是標準輸出裡的一行，退出碼是 2。完成要同時看見約定的結果行，以及退出碼 0。

**Q02.** 程序還在，表示它尚未退出。它也可以正阻塞在 `recv`，這段時間 CPU 時間幾乎不增加。進度要看這張圖的工作狀態，不能只看 PID 還在。

**Q03.** 不可以。相同數字可能來自不同位址空間，或來自壽命已結束的另一個物件。兩個程序預設各有自己的 heap。

**Q04.** 兩支函式都把每個 byte 加進總和，所以計時裡都有一次完整讀取。複製較慢只表示這次多付了複製的成本。下游若仍要求自己的緩衝區，zero-copy 的前提並不成立。

**Q05.** 不應該。接受條件是完整標頭、約定長度的正文，以及結尾標記。路徑存在只表示有個目錄項。

**Q06.** 沒有。flush 交的是使用者空間緩衝。fsync 要求把該檔案送到儲存裝置，而且 POSIX 把傳輸性質留給實作。這次實驗沒有斷電。

**Q07.** 不可以。這只表示本機把 `localhost` 解成 loopback 位址。接收站的位址、port，以及那裡有沒有 listener，都還沒查。

**Q08.** 不可以。TCP 不保留這 40 bytes 的邊界。11 bytes 可能是長度欄的一部分，也可能跨到下一筆。要等定界規則說它完整。

**Q09.** 交出錯誤。宣告的 80 bytes 還沒到齊就遇到關閉，緩衝區裡是截斷，不是一筆訊息。

**Q10.** 記成 HTTP 層的結果。連線已經建立，404 是回應列上的狀態。連線被拒時不會有這一行。

**Q11.** 這次建置的 GIL 開著，預設 CPython 一次只有一條執行緒執行 Python bytecode。兩個加總即使丟到 `to_thread`，也不會因此各佔一顆核心同時跑完。事件迴圈本身一次也只跑一個 Task。

**Q12.** 兩邊都讀到 0，同步之後各自寫回 1。鎖保護了單次讀和單次寫，沒有保護「讀到的值仍是最新」這件組合。

**Q13.** 長度 0 可能是還沒提交、全部被拒絕，或已經做完。要看提交數是否等於接受加拒絕，以及接受數是否等於完成、取消與未完成之和。

**Q14.** 0.15 的三倍已經超過 0.20。正確版每段只能使用當時剩下的預算，總時間停在預算加上計時容忍裡。

**Q15.** 記成未知。worker 可以是完成，客戶端沒有收下那份回覆。這和連線斷開是兩筆帳。

**Q16.** 不可以。200 來自會說謊的健康檢查。就緒仍是 503，提交應被拒絕。

**Q17.** 不可以單憑「程序已經沒了」記成功。incomplete 表示有一筆已接受的工作沒有做完。cleanup 檔沒出現時，也不能用 marker 補成成功。

**Q18.** 總等待把 sleep、佇列堵住與鎖堵住加在同一條數上。分類器若沒有分開的 `queue_wait_s` 與 `lock_wait_s`，就沒有可對上預測的欄位。

**Q19.** 不會。預設 bridge 讓容器使用自己的 network namespace，容器裡的 127.0.0.1 是容器自己的 loopback。主機上的客戶端連的是主機的 loopback。

## 終點題的一種帳

| 編號 | 接受？ | 檔案 | worker | 客戶端 |
|---|---|---|---|---|
| M-1 | 接受，其後完成 | 完整才發布 | completed | received |
| M-2 | 接受，其後完成 | 完整才發布 | completed | received |
| M-3 | 可以接受工作，但檔案檢查拒絕 | 半檔，不發布 | 沒有完成品 | 失敗於完整性，原因明確 |
| M-4 | 接受且 worker 完成 | 完整 | completed | unknown |
| M-5 | 接受 | 尚未發布 | incomplete | 停止時未完成 |
| M-6 | 拒絕 | 未進入接收端 | 沒有這筆 | 拒絕 |

容量 2。若 M-1 與 M-2 仍佔著名額，後面的接受要等名額或被拒絕；表上的「接受」表示最終有沒有進入接收端，順序要在你的腳本裡固定。提交 6。若六筆裡只有被拒的那幾筆不算接受，接受數仍要等於完成、未完成與取消之和。M-3 若在進入接收端前就因半檔被拒，它算拒絕，不要同時算 incomplete。

打穿錯誤實作的兩個檢查：半檔直接出現在正式路徑時，接受函式必須回絕；M-4 的客戶端狀態在回覆被丟之後必須仍是 unknown。
