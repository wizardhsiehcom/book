# 10｜批次與人工審查：先定義可接受的等待與錯誤

**考綱：4.5、5.5。** 本章把大量資料處理拆成兩個問題：什麼時間必須有結果，以及什麼品質纔可直接使用。

## 批次適合能等待的工作

官方文件說 Message Batches 在背景處理、可有最多 24 小時處理窗口，並提供相對標準 API 的 50% 費用折扣。它適合非阻塞、可容忍等待的分析；不能因為多數批次很快完成，就把它當作有低延遲保證的同步 API。[Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

| 工作 | 選擇 | 判準 |
|---|---|---|
| 使用者按鈕後等待判斷 | 同步處理 | 結果阻塞互動 |
| PR 合併前必須取得結果 | 同步／可控時限流程 | 開發者正在等待 |
| 週末彙整活動描述 | 批次 | 可等待背景工作 |
| 次日整理歷史資料品質 | 依可接受期限決定 | 要確認最差處理窗口 |

「每天晚上送出、早上一定交付」並非只要叫做夜間任務就成立；仍須核對時間窗口。批次不會在單一請求內替你完成自訂工具的多輪往返。需要 client tool 結果再推理時，由應用程式另行編排，不能指望批次請求自己等待你執行工具。[官方考綱 §6，4.5](appendix-sources.md)

## custom_id 比回傳順序可靠

本書設計的 ID 如 `event-041-v2`、`event-042-v2`，同時標記資料與版本。結果回來應用 `custom_id` 對應原輸入，再區分成功、失敗及未完成。不要用陣列的第 3 筆直接當成第 3 份文件。

只重送失敗項，並先處理失敗原因。若文件太長，就以能保持證據關係的方式拆分；若來源沒有必要欄位，重送仍無法修復。正式送大量文件前，先以小樣本調整 prompt、schema 和空值策略。[Batch processing](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

## 原創期限練習

假設業務要求資料到達後 30 小時內交付，批次執行預留 24 小時，整理與交付預留 1 小時。那麼等候送出最多隻能佔 5 小時；每 4 小時送一次，最差情況為 4 + 24 + 1 = 29 小時。

這是用考綱的窗口做容量規劃的教學算例，不是把 24 小時解讀成每個項目都一定成功完成。失敗重試仍需額外預算；有硬性結果交付義務的流程，還應定義不能完成時的替代輸出。[官方考綱 §6，4.5](appendix-sources.md)

## 總準確率會掩蓋哪裡出錯

以下是本書虛構驗證資料：950 份一般活動單正確 941 份，50 份特殊格式正確 30 份。總共 971／1,000 = 97.1%，但特殊格式只有 60%。若只看總平均就關閉人工，最需要人工的羣體反而被淹沒。

因此依文件型態和欄位分開評估。日期、總額與聯絡資訊不一定有相同準確率；錯誤成本也不同。高信心樣本仍應做分層隨機抽查，纔有機會抓到模型很有把握的新型錯誤。[官方考綱 §6，5.5](appendix-sources.md)

## 信心先校準，才能當路由訊號

讓模型回傳欄位級信心之後，要用有標準答案的驗證集比較：被標 0.9 的日期到底有多少正確？是否某種文件的高信心特別不可靠？門檻應根據觀察調整，而非把 0.9 當成已驗證的九成概率。

本書建議的學習流程是：低信心、來源矛盾或高影響欄位送人工；高信心且通過語意驗證的資料才進入自動通道，並持續分層抽查。這是練習架構，實際門檻由標註資料、錯誤代價與可用人力決定。

**自測：** 抽樣只抽模型自己標低信心的資料，能估計全體高信心資料的錯誤率嗎？不能；高信心羣體沒有被抽樣，正是盲區。
