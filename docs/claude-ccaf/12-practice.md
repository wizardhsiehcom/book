# 12｜18 題原創情境練習

題目由本書自行設計，**不是官方題庫、回憶題或等值模擬考**。六組情境各三題；每題標明單選或複選數量。建議先寫「限制 → 選擇 → 排除原因」，再展開解析。全對也不能換算成官方 scaled score。

!!! note "關於干擾項"
    本章的四個選項都是**實務上真的有人會選的做法**，不是一個正解配三個明顯的笑話。多數題目的判別點落在兩個都說得通的選項之間，靠刪去法或選最長的那個過不了關。答錯不代表你不懂，但要能講出「為什麼另一個在這個限制下不行」。

## 先建立時間感

本書 18 題不做計時，但正式考試會。60 題／120 分鐘換算下來**平均每題兩分鐘**——這是由題數與時限推得的算術，不是官方建議的作答節奏。

真正的成本不平均分佈在題目上。考試從六個情境隨機出四個，每個情境有一段生產環境敘述框住一組題目；**閱讀成本集中在每組的第一題**，之後同組的題目共用同一份設定。所以配速要以「組」為單位想：進入新情境時允許自己多花時間把目標、硬性條件、可用工具讀清楚，同組後續題目就會快起來。用本書練習時，可以刻意在每組情境開頭多停一下，練這個節奏。

另外兩件在計時下最容易失分的事：**複選題會明示要選幾項**，動手前先數清楚；以及每題都要回頭確認情境的硬性條件有沒有被你選的方案違反。[六個情境的官方設定](00-exam-map.md#六個情境的讀法)先讀熟，考場上的閱讀量就會小一點。

## 情境一：活動訂位客服

助理可查票券與申請改期，實際改期前必須確認票券所有權。政策只寫同城市活動可改期。

### Q01｜單選；1.4、1.5

測試發現助理偶爾跳過所有權確認就呼叫改期工具。哪個修正最直接處理失敗原因？

- A. 把驗證規則移到 system prompt 最前面，並寫明違規的具體後果。
- B. 在改期工具執行前檢查已驗證身分與票券所有權，不符就拒絕。
- C. 用 PostToolUse hook 偵測未驗證的改期，並在回應中標示警告。
- D. 要求模型在每次改期前先輸出一段自我檢查的推理再繼續。

??? note "答案與逐項解析"
    **B。** 只有執行邊界上的檢查能讓「未驗證就改期」變成不可能發生，而不是不太會發生。A 改變的是指引強度，模型仍可能跳過；C 的時機在工具跑完之後，這一次的副作用已經發生，它適合偵測與補救而不是阻擋；D 讓模型自我檢查等於用同一個會出錯的機制去驗證自己。回讀[執行約束](03-enforcement.md)。

### Q02｜複選，選兩項；5.2

哪兩種情況應直接進入人工判斷或接手流程？

- A. 使用者明確表示現在要由真人處理。
- B. 使用者語氣明顯不佳，且問題需要跨部門協調才能完成。
- C. 請求落在政策未涵蓋的範圍，沒有可依據的規則。
- D. 同一筆查詢已連續兩次逾時，第三次重試仍在進行中。

??? note "答案與逐項解析"
    **A、C。** A 是明確表達的偏好，不需要被「我應該做得到」覆寫；C 是政策缺口，代理不能自行補造規則。B 把兩個訊號綁在一起看起來很有說服力，但情緒不是判準，跨部門協調也可能仍在代理能處理的範圍內——要看的是有沒有可依據的規則。D 仍在恢復中，尚未證明無法取得進展。回讀[升級條件](09-context-reliability.md)。

### Q03｜單選；2.2、5.3

票券查詢逾時，程式卻回傳成功與空清單，助理因此告訴使用者「你沒有票券」。應先改哪裡？

- A. 在助理的回覆模板加上「若查無資料請確認網路狀況」的提示。
- B. 把查詢逾時時間拉長，並在逾時後自動重試三次再回覆。
- C. 要求助理在回覆前再查一次，兩次結果一致才對外說明。
- D. 讓工具回傳可區分的失敗狀態，並標示這次是否可重試。

??? note "答案與逐項解析"
    **D。** 根因是資料契約把「未知」壓成了「不存在」，下游拿到的資訊本身就是錯的。B 會降低逾時發生率，但只要發生一次，錯誤結論照樣產生；C 兩次都逾時就會得到兩個一致的空清單，反而更有說服力地說錯；A 把技術狀態推給使用者判斷。這三者都在症狀上打轉。回讀[錯誤契約](04-tool-contracts.md)。

## 情境二：票券程式重構

團隊用 Claude Code 維護多套服務，測試檔分散在各 package。

### Q04｜單選；3.1

資深工程師的 Claude 都會使用共用 fixture，新成員卻常自建資料。規範目前放在資深工程師的 `~/.claude/CLAUDE.md`。先做什麼？

- A. 請資深工程師把他的設定檔複製一份給每位新進成員。
- B. 把規範改寫成 skill，讓成員在需要寫測試時自行呼叫。
- C. 把規範移到版控中的專案 CLAUDE.md，讓所有成員自動載入。
- D. 在 PR 模板加上一條「是否使用共用 fixture」的檢查項目。

??? note "答案與逐項解析"
    **C。** 問題是規範待在只有一個人拿得到的作用域，把它移到隨 repo 分享的位置就直接解決。A 治標且每次有人加入或改規範就要重做一次；B 讓「每次寫測試都該遵守」的規範變成要記得主動呼叫；D 在事後攔截，但那時程式已經寫完了。B 和 D 都可以當補強，不是第一步。回讀[設定位置](06-claude-code.md)。

### Q05｜單選；3.3

一份很長的測試規範只在修改測試檔時需要，而 `*.test.ts` 散在 `src/`、`packages/`、`services/`。最合適的配置？

- A. 用 `.claude/rules/` 的 `paths` 比對 `**/*.test.ts` 條件載入。
- B. 寫進 repo 根目錄的 CLAUDE.md，確保任何情況都不會漏掉。
- C. 在每個含有測試檔的目錄各放一份對應的 CLAUDE.md。
- D. 放進測試 fixture 模組的檔頭註解，讓讀到程式就看到。

??? note "答案與逐項解析"
    **A。** 需求有兩個條件：跨目錄適用，而且只在相關時才載入。B 確實不會漏，但一份很長的規範會在每一輪都佔用上下文，包括完全不碰測試的工作；C 涵蓋得到卻要維護 N 份，時間久了必然漂移；D 只有在模型剛好讀到那個檔案時才生效。回讀[path 規則](06-claude-code.md)。

### Q06｜單選；3.4、3.5

需求是把所有服務改成新的日期契約，有三種相容方案，時區策略還沒決定。下一步？

- A. 先挑一個服務完整改完並通過測試，再照同一套模式改其餘服務。
- B. 先為新契約寫好測試，讓失敗的測試逐步驅動各服務的修改。
- C. 先把所有日期欄位統一成字串，之後再逐步收斂成明確格式。
- D. 先探索使用範圍、確認時區與相容策略，再產出遷移計畫。

??? note "答案與逐項解析"
    **D。** 三個選項都是好習慣，但它們共同的前提是「要做什麼已經確定」。時區策略未決代表語意本身還沒定案：A 的第一個服務會把某個時區假設固定下來，後面照抄就把錯誤放大；B 寫出的測試會把未定的語意寫死成斷言；C 統一成字串等於把決定往後推，同時失去型別檢查。回讀[規劃與迭代](06-claude-code.md)。

## 情境三：活動市場研究

協調者分派來源調查與統計分析，再交由整合者產出有引用的報告。

### Q07｜複選，選兩項；1.2、1.3

使用標準非 fork 子代理時，哪兩項可避免整合者缺乏必要資料？

- A. 假設整合者會沿用協調者已載入的專案設定與對話內容。
- B. 在委派內容中附上已確認的發現與各自的來源位置。
- C. 讓整合者與調查者共用同一組工具，確保取得相同資料。
- D. 在交付格式中要求每個結論標註支持它的來源與缺口。

??? note "答案與逐項解析"
    **B、D。** B 補上拿不到的上下文，D 讓證據關係在交接後仍然存在。C 最容易誤選——工具能力與對話內容是兩回事，給了相同工具不代表知道前面查過什麼、結論是什麼；A 則是把 fork 的行為套到一般子代理。回讀[任務交接](02-orchestration.md)。

### Q08｜單選；5.6

兩份可信報告，一份統計去年全年入場人次為 12 萬，一份統計今年第一季付費票券為 8 萬。整合時應如何處理？

- A. 以較新的來源為準，並在附註說明採用新資料的理由。
- B. 換算成同一期間的月平均之後，再比較兩者的差距。
- C. 並列兩個數字，各自標註期間、統計母體與來源出處。
- D. 請兩份報告的作者確認哪一方的統計方法比較嚴謹。

??? note "答案與逐項解析"
    **C。** 期間不同、母體也不同（全部入場 vs 付費票券），在對齊定義之前它們根本不是同一個量。B 看起來最像在做嚴謹處理，但把兩個母體不同的數字換算到同一期間，只會產出一個看起來可比、實際上沒有意義的數字；A 的「較新」在這裡不是品質問題而是期間問題；D 把定義差異誤判成方法優劣。回讀[來源與時間](09-context-reliability.md)。

### Q09｜單選；1.2、1.6

三個 worker 都查一般活動需求，無人查企業活動，報告卻聲稱涵蓋全市場。最能修正根因的做法？

- A. 由協調者重新界定範圍，針對未覆蓋的族群另行委派調查。
- B. 在報告中加註「本次調查可能未涵蓋部分市場族群」的但書。
- C. 增加 worker 數量，讓更多平行調查提高覆蓋到的機率。
- D. 讓三個 worker 交叉檢查彼此的結果，找出遺漏的部分。

??? note "答案與逐項解析"
    **A。** 缺口來自拆工時範圍就沒有涵蓋企業活動，只有回到分派層才補得起來。B 是誠實的，也應該做，但它揭露問題而不修正問題；C 用機率取代設計，三個 worker 沒查到的族群，六個也未必會查；D 的三個人共用同一個盲區，交叉檢查看不到不存在的東西。回讀[協調者責任](02-orchestration.md)。

## 情境四：開發者探索工具

助理需要理解陌生 repo，內建工具和 MCP 工具皆可用。

### Q10｜單選；2.5

你要找出所有呼叫 `reserve_seat` 的位置。最合適的做法？

- A. 用 Glob 收集所有原始碼檔案，再逐一 Read 檢查內容。
- B. 用 Bash 執行一次全文檢索，把輸出直接當成完整呼叫清單。
- C. 用 Read 打開入口檔案，順著 import 逐層往下追蹤呼叫鏈。
- D. 用 Grep 搜尋名稱，再 Read 命中處確認脈絡與可能的別名。

??? note "答案與逐項解析"
    **D。** 先用內容搜尋縮小範圍，再讀取確認，是內建工具的預期用法。B 最接近正確——搜尋確實是對的方向，但把原始輸出當成最終答案會漏掉 wrapper 重新匯出後改名的呼叫，也無法判斷命中處是定義還是呼叫；A 把整個 repo 讀進上下文，成本高且定位並沒有變準；C 在有動態註冊或多入口時會斷線。回讀[內建工具](04-tool-contracts.md)。

### Q11｜單選；2.1、2.4

MCP 可以搜尋未簽出 repo 的文件，但 agent 一直用本地 Grep。該 MCP 工具的描述只有「搜尋」兩個字。優先改什麼？

- A. 在 system prompt 加一條規則，要求優先使用 MCP 工具搜尋。
- B. 改寫描述，寫明可搜尋未簽出的專案並回傳議題 ID 與連結。
- C. 把本地 Grep 從這個 agent 的工具集中移除，消除競爭選項。
- D. 調高 MCP server 的優先序，讓它的工具排在清單前面。

??? note "答案與逐項解析"
    **B。** 現象可以被「模型不知道這個工具能做什麼」完整解釋，先驗證這個原因最省。A 用規則壓過描述，在本地搜尋才是對的任務上會反過來出錯；C 確實會逼它改用 MCP，但代價是失去一個合理能力，而且沒有修好描述，換個情境還會再犯；D 把工具清單順序當成路由控制，那不是選擇機制。回讀[MCP 可發現性](05-mcp.md)。

### Q12｜複選，選兩項；1.7、5.4

昨天的調查中斷，今天部分程式已被重構。哪兩項能同時處理「進度」與「舊結論是否過期」？

- A. 讀取工作索引，取得已完成、部分完成與待做項目的位置。
- B. 用 `--resume` 續跑昨天的 session，讓模型接續先前的脈絡。
- C. 比對來源版本，把受變更影響的結論標記為需要重查。
- D. 請模型先摘要昨天的結論，再以那份摘要為基礎繼續往下。

??? note "答案與逐項解析"
    **A、C。** 題目問的是兩件事同時成立：A 給進度，C 給新鮮度。B 是最容易誤選的——resume 是文件記載的正當機制，也真的能接續對話狀態，但它維持的是對話，不會偵測共用檔案已經被改過，昨天的結論會原封不動地被當成現況；D 連進度都保不住，摘要還會把該重查的細節一起磨掉。回讀[可恢復狀態](09-context-reliability.md)。

## 情境五：CI 的程式審查

每次 PR 更新會呼叫 Claude Code，開發者只希望看到具體、未解決的問題。

### Q13｜單選；3.6

CI 執行時一直停在等待互動輸入。應先使用哪個有文件記載的方式？

- A. 在 CI 步驟中預先用管線送入換行，跳過可能出現的提問。
- B. 縮短該步驟的逾時設定，讓卡住的工作自動結束後重跑。
- C. 改用 `claude -p` 非互動執行，並把輸出取成 JSON 格式。
- D. 在 CLAUDE.md 寫明「不要提問，直接執行到完成為止」。

??? note "答案與逐項解析"
    **C。** `-p`（`--print`）就是為非互動情境設計的執行方式。A 是實務上常見的土法，能矇混過某些提問，但送進去的換行等於盲目接受未知的預設值；B 把卡住變成失敗再重來，每次都卡；D 是上下文指引，不改變執行模式。另外注意 JSON 外層不代表內容已符合你的業務 schema。回讀[CI 執行](07-ci-review.md)。

### Q14｜單選；4.1、4.2

模型反覆報告已被程式前置檢查擋掉的空值錯誤。如何優先降低這類誤報？

- A. 把這個類別的 severity 調降，讓它不再出現在主要清單中。
- B. 在 prompt 要求模型只回報自己信心高於九成的問題再輸出。
- C. 讓第二個模型複審所有空值類發現，兩者未達共識就不輸出。
- D. 判準加上「須指出可到達失敗的路徑」，並附正反對照例。

??? note "答案與逐項解析"
    **D。** 誤報的成因是判準沒有界定什麼叫做「問題」，補上可達性要求與一組僅差在有無前置檢查的對照例，直接畫出決策邊界。A 讓噪音消失但真正的空值缺陷也一起被降級；B 的信心是模型自述的，不是校準過的機率，寫「九成」不會改變它的判斷依據；C 成本翻倍，而兩個模型可能一起犯同一個判準不清的錯。回讀[few-shot 判準](07-ci-review.md)。

### Q15｜單選；3.6、4.6

生成者的自審漏掉了跨檔案的介面不一致。哪種組合最貼近問題？

- A. 把整個差異一次送進單一 pass，確保審查者看得到全貌。
- B. 由獨立上下文審查，並分成逐檔 pass 與跨檔整合 pass。
- C. 在同一個 session 請生成者針對介面再仔細檢查一次全部檔案。
- D. 只審查被修改的介面定義檔，呼叫端交給型別檢查處理。

??? note "答案與逐項解析"
    **B。** 問題有兩層：生成者會沿用自己先前的合理化，以及跨檔依賴需要專門的注意力分配。A 只處理第二層，而且全量單一 pass 容易讓某幾個檔案獲得深入檢查、其他被略過；C 兩層都沒處理；D 在動態語言或介面經過轉換時會直接漏掉。回讀[多 pass 架構](07-ci-review.md)。

## 情境六：大量活動文件抽取

服務抽取不同格式的活動報價，部分缺稅號，部分總額與明細不一致。

### Q16｜複選，選兩項；4.3、4.4

哪兩項設計能同時容納來源缺失與來源矛盾？

- A. 稅號欄位設為必填但允許 null，並定義 null 之後的處理流程。
- B. 缺稅號時依同批文件最常見的格式產生一個格式正確的佔位值。
- C. 總額不一致時以明細加總為準，並在備註中記錄原始印出的值。
- D. 同時保留來源印出的總額與計算所得的總額，並標記兩者矛盾。

??? note "答案與逐項解析"
    **A、D。** A 讓「沒有這項資訊」可以被明確表達，D 讓矛盾保持可見。C 最容易誤選，因為它有記錄原值、看起來很負責——但它已經替來源做了「明細才是對的」這個判斷，而那可能是明細漏抽而不是總額印錯，該由業務規則或人工決定；B 產出的是格式合法的虛構資料，比缺值更難被下游發現。回讀[輸出驗證](08-structured-output.md)。

### Q17｜單選；4.5

一項任務阻塞使用者當下的報價確認；另一項是每週歷史文件分析，可以等一天。批次怎麼分配？

- A. 每週分析走批次；即時確認維持能滿足互動需求的同步流程。
- B. 兩項都走批次，並為即時確認的請求設定較高的處理優先序。
- C. 兩項都走同步，避免批次回傳順序不同造成結果對應錯誤。
- D. 即時確認也走批次，但縮短輪詢間隔以取得成本上的優勢。

??? note "答案與逐項解析"
    **A。** 判準是延遲容忍度。B 假設批次接受優先序而能保證延遲，但批次的處理窗口本來就不是低延遲承諾；D 同理，輪詢再密也不會讓結果提早產生；C 擔心的對應錯誤是真的存在，但那是用 `custom_id` 解決的問題，不構成放棄批次的理由。仍須核對實際期限與失敗重試預算。回讀[批次窗口](10-batch-human-review.md)。

### Q18｜單選；5.5

總準確率很高，但特殊格式的樣本少、錯誤率明顯偏高。如何決定是否減少人工？

- A. 先補足特殊格式的標註樣本，再依整體準確率決定自動化門檻。
- B. 依文件型態與欄位分別評估，並對高信心群體保留隨機抽查。
- C. 把信心門檻由 0.9 提高到 0.95，減少誤判進入自動通道。
- D. 特殊格式全部轉人工，其餘依整體準確率開放全面自動化。

??? note "答案與逐項解析"
    **B。** 分層才看得到被平均蓋掉的弱項，抽查才抓得到模型很有把握的新型錯誤。A 補樣本的直覺是對的，但補完又回頭用整體平均決策，等於繞一圈回到原本的錯誤；D 已經做了一半的分層，卻對其餘部分放棄抽查，高信心群體就此成為盲區；C 假設 0.9 到 0.95 之間的差距代表真實機率，那需要先用標註資料校準過才成立。回讀[人工與校準](10-batch-human-review.md)。

## 訂正方法

每題記錄選項、漏看的情境限制、錯誤假設、應回讀章節與一個可驗證實驗。不要只背正確字母。

以下是弱項清單的欄位骨架，第一列是填法示例：

| 題號 | 我選了／正解 | 漏看的限制 | 錯誤假設 | 回讀 | 可驗證實驗 |
|---|---|---|---|---|---|
| Q03 | B／D | 題目說的是「逾時」，不是查無資料 | 我以為降低逾時發生率就等於修好錯誤回報 | [04](04-tool-contracts.md) | 在 [Lab 1](11-labs.md) 分別測空清單與逾時，確認兩者狀態不同 |
|  |  |  |  |  |  |

「錯誤假設」那一欄最值得寫滿。選錯的字母下一輪就忘了，但假設會重複犯——同一個假設通常會在不同情境的題目裡再害你一次。

**特別留意選了「次佳解」的題目。** 本章多數題目的干擾項是實務上合理、只是在這個限制下不成立的做法。如果你選的是那一個，代表方向對但沒有讀出關鍵限制，這比完全不懂更容易在考場重演。

回到[考綱地圖](00-exam-map.md)標記仍無法解釋的任務；下一輪先修補依賴觀念，再重做改寫後的情境。

弱項補完之後，用[情境包](13-scenario-set.md)做一次計時測驗：單一情境、連續 12 題、26 分鐘。本章練的是判斷，那一章練的是在時間壓力下維持同樣的判斷。
