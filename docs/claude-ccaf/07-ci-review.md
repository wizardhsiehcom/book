# 07｜CI 審查：從泛泛建議到可驗證問題

**考綱：3.6、4.1、4.2、4.6。** 本章把 Claude Code 接到非互動流程，並說明為何多說一次「仔細檢查」不等於好的審查設計。

## 先讓流程能結束與被機器讀取

CI 沒有人坐在終端前回答問題。考綱指定用 `claude -p`（`--print`）執行非互動工作，並以 `--output-format json`、`--json-schema` 產生可解析結果。下列是命令格式示意，實際執行前須準備測試 repo、CLI 與必要權限：[官方考綱 §6，3.6](appendix-sources.md)

```bash
claude -p "檢查本次差異中的可重現缺陷；每項附路徑、觸發條件與影響" --output-format json
```

JSON 外層不代表內文 findings 已符合你的業務 schema。若要自動處理，需要額外指定 schema 並檢查 CLI 的結果封裝；錯誤、超時與未完成必須有不同的工作狀態。非互動也不等於免除所有權限檢查；CI 應在預先界定的範圍執行。

本書設計的 finding 欄位是 `path`、`location`、`trigger`、`impact`、`severity`、`detected_pattern` 與 `suggested_fix`。`detected_pattern` 讓日後可以依誤報類型分析，而不只統計總共有幾條留言。

## 明確的判準比信心形容詞有效

「只報高信心問題」沒有說明什麼是問題。對程式註解的檢查，可改成「只有當註解聲稱的行為和可指出的程式行為矛盾時才報告；單純用字偏好不報告」。對缺陷，要求具體輸入、執行路徑與可觀察後果。[官方考綱 §6，4.1](appendix-sources.md)

原創判準範例：

| 發現 | 是否報告 | 證據要求 |
|---|---|---|
| 空清單進入索引存取造成例外 | 是 | 指出空清單可到達該分支 |
| 想把區域變數改成另一個名字 | 否 | 不在功能性審查範圍 |
| 註解說不寫檔，但函式會寫入 | 是 | 指出實際寫入路徑 |
| 猜測 API 可能慢，但沒有路徑或測量 | 不直接定為缺陷 | 列為待驗證問題 |

如果某一類建議一直被合理駁回，先暫停該類並分析樣本，不必讓它拖累其他可靠類別。調整判準之後，用保留驗證集評估，避免只修好已看過的例子。

## Few-shot 教的是判斷邊界

下面是本書的兩個教學樣本，應與 schema 一起傳入審查 prompt，而非只用長篇抽象規則：

```text
案例 A：函式先檢查 items 為空便返回，之後才用 items[0]。
輸出：不報告空清單越界；先行檢查排除了觸發條件。

案例 B：函式直接讀 items[0]，呼叫者可能傳入 []。
輸出：報告缺陷，指出呼叫者、讀取位置、[] 的觸發條件與保護方式。
```

A 與 B 的表面都有 `items[0]`，差別是能否到達失敗狀態。好的 few-shot 包含容易混淆的正反例，使模型學會依條件判斷，而非見到某字串就報錯。輸出格式不一致時，也用示例展示各欄位應有的粒度。[官方考綱 §6，4.2](appendix-sources.md)

## 獨立審查與多 pass 解決不同問題

生成程式的同一個 session，可能沿用自己先前的合理化。獨立審查應拿到需求、差異、必要上下文與測試，但不帶入生成者的整段推理。這是降低偏差的安排，不是保證第二個模型一定正確。

多 pass 處理的是注意力分配：先逐檔檢查局部缺陷，再看跨檔呼叫、型別和狀態流程。只有逐檔 pass 會漏掉 A 改介面、B 沒跟著改；只有全量 pass 可能讓某幾檔獲得深入檢查、其他檔被略過。[官方考綱 §6，4.6](appendix-sources.md)

## 重跑不要重複製造噪音

新 commit 進來時，帶入先前 findings 的狀態，要求只列新出現或仍未解決的問題。已有測試也應提供給生成器，避免重複建議同一個案例。repo 的 `CLAUDE.md` 可記錄 fixture、測試命令、什麼纔是有價值的測試，以及 review 範圍。

**自測：** 大型 PR 裡有相同模式，一處報錯、一處沒報。直接要求三次投票是第一選擇嗎？先確認能否用局部 pass 加整合 pass 改善注意力與上下文，再評估是否需要重複評審。
