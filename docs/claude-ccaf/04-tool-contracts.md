# 04｜工具契約：讓正確選擇比猜測容易

**考綱：2.1、2.2、2.3、2.5。** 讀完應能修改一份容易誤用的工具介面，並根據錯誤類型決定恢復方式。

## 名稱、描述與邊界一起設計

假設平臺有 `get_data` 和 `find_data`，描述都只有「取得票券資料」。模型無法知道哪個接受票券 ID、哪個接受客戶 ID。把提示詞寫得更長，未必能彌補兩個介面本身的模糊。

可改成 `lookup_ticket_by_id`（單一票券）與 `list_customer_tickets`（某客戶的票券清單）。描述要寫清輸入格式、回傳內容、空結果意義、是否有副作用，以及何時改用另一個工具。設計工具的原則與替人寫清楚的函式契約相近，只是此處選擇者是模型。[工具介面原理](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)

```json
{
  "name": "lookup_ticket_by_id",
  "description": "以完整票券 ID（例如 T-041）查詢單張票券狀態與活動 ID；唯讀。不接受客戶姓名。需要客戶全部票券時使用 list_customer_tickets。查無票券回傳 found=false，不代表服務故障。",
  "input_schema": {
    "type": "object",
    "properties": {"ticket_id": {"type": "string"}},
    "required": ["ticket_id"],
    "additionalProperties": false
  }
}
```

這是 API 工具定義示意，MCP 工具 schema 命名和外層封裝應使用 MCP 規格。不要因為兩者都採 JSON，就假設封裝完全相同。

先用有歧義的測試輸入評估選擇：「我想看看這次訂票」「這個帳號最近的活動」。如果模型持續選錯，檢查名稱、描述與 system prompt 中有沒有過度依賴關鍵字的路由規則，再考慮拆分工具。[官方考綱 §6，2.1](appendix-sources.md)

## 讓錯誤告訴下一步

MCP 的 `isError` 用來表示工具執行失敗。下列 `errorCategory`、`isRetryable` 等是本書的應用層 schema，不是 MCP 規定每個工具必須具備的標準欄位。

```json
{
  "isError": true,
  "content": [{
    "type": "text",
    "text": "{\"errorCategory\":\"permission\",\"isRetryable\":false,\"message\":\"此帳號無權查看票券\",\"nextAction\":\"request_authorized_access\"}"
  }]
}
```

| 結果 | 意義 | 合理下一步 |
|---|---|---|
| 查詢成功但空清單 | 沒有符合條件的資料 | 說明或調整查詢範圍 |
| 暫時逾時 | 本次取不到結果 | 有限重試，保存已做嘗試 |
| 輸入格式不合法 | 參數有問題 | 修正具體欄位後重送 |
| 權限不足 | 呼叫者不被允許 | 尋求授權或轉交，不盲目重試 |
| 業務規則拒絕 | 動作不符合政策 | 說明限制或升級處理 |

把 timeout 回成空清單會把「未知」偽裝成「不存在」。反過來，每個空結果都當錯誤重試，也會浪費資源。worker 可以先恢復短暫錯誤；無法恢復才把嘗試、部分成果與替代方式交給 coordinator。[官方考綱 §6，2.2；5.3](appendix-sources.md)

## 工具越多不一定越能幹

研究員需要搜尋與讀取；整合者主要需要已有證據。全部工具都交給每個 agent，會增加誤選和越界操作機會。不過也不必把角色邊界做成每次簡單查覈都要來回轉派：可以給整合者一個只接受既有來源範圍的狹窄核實工具，複雜調查再交回協調者。

`tool_choice` 選擇的是呼叫策略：`auto` 可選工具或文字，`any` 要求呼叫某個工具，指定 `{"type":"tool","name":"..."}` 則要求特定工具。它不等於業務授權，也不替你執行工具。若第一步必須抽取識別資料，可先強制該工具、處理結果，再開始後續輪次。[官方考綱 §6，2.3](appendix-sources.md)

## 內建工具：先縮小，再閱讀

| 目標 | 工具 | 原因 |
|---|---|---|
| 找 `*.test.ts` 檔案 | Glob | 比對路徑 |
| 找錯誤字串或函式呼叫 | Grep | 搜尋內容 |
| 理解已找到的實作 | Read | 取得上下文 |
| 修改唯一、明確的一小段 | Edit | 控制修改範圍 |
| 建新檔或必要的整檔重寫 | Write | 寫入完整內容 |
| 執行測試、建置指令 | Bash | 執行程式 |

如果 Edit 的字串不唯一，先讀檔、擴大到唯一上下文；必要時再基於最新全文 Write，並檢查差異。追函式也別只搜原始名字：wrapper 可能改名 export，需列出重新匯出的名稱再逐一搜尋。這比一次載入整個 repo 更容易維持有根據的理解。[官方考綱 §6，2.5](appendix-sources.md)

**自測：** 讀取服務回覆權限不足，重送五次仍相同。該增加重試次數嗎？不應；分類已指向授權問題。修正錯誤契約或權限處理，比延長重試更接近根因。
