# 11｜實作工作坊：用失敗案例驗證理解

本章包含一個**不需要 API key 的可執行 Python 練習**，以及四組要在自己的測試環境完成的整合任務。模擬器驗證控制流程與資料驗證，不代表已串接 Claude 或 MCP。整合任務不會在本書建置時自動執行，也不會對真實帳號發送訊息或修改交易。

## Lab 0：先跑出可觀察的工具往返

下載 [offline_lab.py](examples/offline_lab.py)，需要 Python 3.10 或以上，不依賴第三方套件。從 repo 根目錄執行：

```bash
python docs/claude-ccaf/examples/offline_lab.py
```

若從書頁下載檔案，在下載目錄執行 `python offline_lab.py`。預期最後印出 `PASS: 7 offline checks`。

程式提供預先編寫的模型回應。第一輪同時產生兩個票券查詢，執行端逐一處理並保留呼叫 ID；第二輪讀取結果才結束。其餘檢查涵蓋來源缺失、明細總額矛盾、截斷與迴圈預算。

| 檢查 | 預期觀察 | 對應觀念 |
|---|---|---|
| 兩個工具請求 | 兩個結果各有正確 ID，第二輪看得到 | 1.1 |
| 未知工具 | 回傳結構化失敗，不執行任意名稱 | 2.1–2.2 |
| 身分未核實 | gate 拒絕動作 | 1.4 |
| 工具請求持續重複 | 預算耗盡標未完成 | 1.1 |
| 回應截斷 | 不標成功 | 1.1、4.4 |
| 金額矛盾 | 保留來源總額並標記錯誤 | 4.4 |
| 來源缺欄位 | 接受 null，不因缺失而憑空補值 | 4.3 |

讀完後修改 fixture：讓 T-041 也變成不可改期，觀察結果是否跟著改；再故意交換兩個 `tool_use_id`，思考下游如何被誤導。模擬器的業務回覆只是 fixture，沒有 LLM 推論能力。

## Lab 1：接上真實模型的唯讀助理

先備：[迴圈](01-agent-loop.md)、[執行約束](03-enforcement.md)、[工具契約](04-tool-contracts.md)。準備自己的開發環境與測試資料，使用安裝版本的 SDK 文件；模型 ID 使用你有權存取的版本。

1. 定義 `lookup_ticket_by_id` 與 `list_customer_tickets`，讓名稱、輸入邊界與空結果語意明確。
2. 選 Messages API 自管迴圈，或 Agent SDK 提供的執行環境；記錄哪一層負責工具執行。
3. 測試單一 ID、含糊請求、無資料、逾時、權限不足。保留請求與結果的對應 ID。
4. 加入假的 `change_event`，執行前先核實身分與所有權。此處只修改記憶體 fixture。
5. 使用者要求人工時直接交接，附已查資料、未結事項與未執行動作。

**驗收：** 沒有身分確認時，fixture 的狀態不得改變；空結果和服務失敗必須有不同狀態；未知工具不可被動態執行。記下模型版本、SDK 版本、測試輸入與失敗例，不能只展示一次成功對話。

## Lab 2：讓新同事重現 Claude Code 行為

先備：[MCP](05-mcp.md)、[Claude Code 設定](06-claude-code.md)。建立獨立練習 repo，不在正在使用的專案裡實驗破壞性設定。

1. 專案 `CLAUDE.md` 寫入測試命令與 fixture 規範；個人偏好放使用者 scope。
2. 為散佈各處的測試檔建立 path rule，檢查 matching 和 non-matching 檔案的載入行為。
3. 建立 trace skill，指定 `context: fork` 與工具設定。觀察主對話接收到的是什麼。
4. 接入一個自己可用的測試 MCP server，專案設定只保存變數名稱。
5. 用一個單函式修正和一個跨模組遷移，比較直接執行與先規劃。

**驗收：** 換到乾淨的使用者環境、補上所需憑證後，共享規範仍可取得；個人設定不應被誤當團隊規範。記錄載入檔案與 MCP 連線狀態，不只截取「我已讀取」的模型文字。

## Lab 3：抽取、驗證與人工分流

先備：[結構化輸出](08-structured-output.md)、[批次](10-batch-human-review.md)。製作十份虛構活動報價，涵蓋空欄位、格式差異與互相矛盾的總額，另保留未用於調 prompt 的驗證資料。

1. 定義 nullable 欄位、`other`／`unclear` 與來源位置。
2. 用你版本支援的 strict output，完成後再檢查語意。
3. 只對可修正的抽取錯誤重試，回傳原文、失敗輸出與明確驗證訊息。
4. 每筆附 `custom_id`，模擬順序打亂與部分失敗，確認只重送失敗項。
5. 依文件型態、欄位拆分準確率；高信心羣體也抽查。

**驗收：** 無稅號文件沒有虛構稅號；來源總額有矛盾時不被偷偷更正；報告說明樣本數很小，不能把此實驗當正式校準結果。真實 Message Batches 提交是額外整合練習，會產生 API 使用量。

## Lab 4：有缺口仍能追溯的研究管線

先備：[編排](02-orchestration.md)、[上下文](09-context-reliability.md)。用兩份自己撰寫的活動統計文件，其中一份按入場人次、另一份按付費票券計數。

1. 委派兩個獨立調查任務，明確分配來源與交付格式。
2. 每項結果含 claim、來源、定位、期間、統計口徑與缺口。
3. 模擬其中一個 worker 失敗；先局部恢復，失敗則帶部分結果回協調者。
4. 輸出 manifest，停止後再恢復；變更其中一份來源，確認舊結果會被標待重查。
5. 整合報告保留不可比較的數字，區分已確認結論與未決問題。

**驗收：** 移除一份來源後，報告不再聲稱全範圍已查覈；恢復後不重複已確認完成且仍有效的工作；每個結論可反查來源。這四組任務是本書原創教學設計，與[官方考綱備考練習](appendix-sources.md)覆蓋相同能力，但不是實際考題。
