# 13｜情境包：12 題連續作答

[18 題練習](12-practice.md)一次一個觀念，適合定位弱項。這一章換一種形態：**單一情境敘述，連續 12 題，計時作答**，貼近考場上真正的節奏。

題目仍由本書自行設計，**不是官方題庫、回憶題或等值模擬考**。考綱公開了六個情境的設定，但**沒有公開每個情境的題數**；12 題是用 60 題除以 4 個情境取的近似值。全對不能換算成 scaled score。

四個選項都是實務上真的有人會選的做法，判別點多半落在兩個都說得通的選項之間；選最長的或用刪去法過不了關。

## 使用方式

1. **計時 26 分鐘**：12 題約 24 分鐘，另留 2 分鐘讀情境。時間到就停，未答完的題目本身就是資訊。
2. **閉卷**：不要開其他章節，考場也不會讓你開。
3. 每題先寫「限制 → 選擇 → 排除原因」再展開解析。
4. 情境敘述只讀一次，之後靠筆記；考場上重讀敘述是最貴的動作。

這個情境對應官方的 Customer Support Resolution Agent（主要領域 1、2、5），另含一題結構化交接。語境是本書的活動票券平臺，不是官方情境內容。

## 情境設定

你要為一個城市活動票券平臺建立**客服解決代理**，使用 Claude Agent SDK。代理透過自訂 MCP 工具存取後端：

| 工具 | 作用 | 性質 |
|---|---|---|
| `get_customer` | 依已驗證身分取客戶資料 | 唯讀 |
| `lookup_ticket` | 查票券狀態與所屬活動 | 唯讀 |
| `process_change` | 執行改期 | **有副作用** |
| `escalate_to_human` | 轉人工接手 | 出口 |

已知條件：

- 目標是首次接觸解決率 80% 以上，同時要知道何時該轉人工。
- 改期政策**只涵蓋同城市活動**；跨城市改期政策未定義。
- 尖峰時段票券服務偶爾逾時。
- 團隊有多人共用這套設定，並用子代理處理批次爭議案件的彙整。

### S01｜單選；1.1

某一輪回應中，代理的文字寫著「已為您改期」，但該回應的 `stop_reason` 是 `tool_use`，而且整段對話裡沒有任何 `process_change` 的 `tool_result`。應如何處理？

- A. 先把文字回覆給使用者，同時在背景送出這次的改期請求。
- B. 執行回應中待處理的工具請求；這次改期尚未真的發生。
- C. 記錄為已完成，並在下一輪主動向使用者確認改期結果。
- D. 重送使用者的原始訊息，讓模型重新產生一次完整回應。

??? note "答案與逐項解析"
    **B。** `tool_use` 表示模型還在提出動作，工具尚未執行，也就不可能有業務結果。A 分成兩路看似務實，但「背景送出」需要有人真的執行那個工具請求，繞開迴圈只是把同一件事換個地方做，還讓回覆先於結果；C 直接把模型的敘述當成協定狀態；D 丟掉已經產生的工具請求，重跑還可能造成重複改期。回讀[Agent 迴圈](01-agent-loop.md)。

### S02｜複選，選兩項；1.4、1.5

測試發現代理偶爾在尚未取得可信的已驗證身分時就呼叫 `process_change`。哪兩項能真正阻擋這個動作？

- A. 用 `PostToolUse` hook 偵測到未驗證的改期時回傳阻擋指示。
- B. 在 `process_change` 執行前檢查已驗證身分與票券所有權。
- C. 在 system prompt 明列違反驗證規則會造成的具體業務後果。
- D. 後端在真正寫入的當下再次確認條件仍然成立才提交。

??? note "答案與逐項解析"
    **B、D。** 兩者都在副作用發生之前，或發生的同一個交易裡。A 最容易誤選，因為 hook 確實是正確的機制類別——只是 `PostToolUse` 的時機在工具跑完之後，擋不掉這一次；C 是機率性指引。B 和 D 也不重複：通過 gate 只代表可以嘗試，寫入當下條件仍可能已經改變。回讀[執行約束](03-enforcement.md)。

### S03｜單選；2.1

`lookup_ticket` 與 `get_customer` 的描述都只寫「取得資料」。代理常拿客戶 email 去呼叫 `lookup_ticket`，得到空結果。優先做什麼？

- A. 在 system prompt 加入輸入形態與對應工具的路由規則。
- B. 讓 `lookup_ticket` 收到 email 格式時自動改查客戶資料。
- C. 改寫兩者的描述，寫明接受的輸入與該改用另一個的時機。
- D. 合併成單一工具，由參數的型別決定實際查詢哪一種資料。

??? note "答案與逐項解析"
    **C。** 誤用源自兩個介面本身無法區分，修在描述上最接近根因。A 的關鍵字路由在沒見過的說法上會再壞一次；B 是很常見的「寬容輸入」設計，短期有效，但它把歧義藏起來，之後查客戶時該回哪一種資料會更難講清楚；D 讓一個工具承擔兩種語意，描述反而更難寫。回讀[工具契約](04-tool-contracts.md)。

### S04｜單選；2.2

尖峰時段 `lookup_ticket` 逾時，目前實作回傳 `{"tickets": []}`。該怎麼修？

- A. 讓工具回傳可區分的失敗狀態，並標示這次是否可重試。
- B. 拉長逾時設定，並在逾時後自動重試三次再回覆使用者。
- C. 逾時就直接呼叫 `escalate_to_human`，避免給出錯誤資訊。
- D. 回覆前再查一次，兩次結果一致才把「沒有票券」說出口。

??? note "答案與逐項解析"
    **A。** 契約把「未知」壓成「不存在」，這是資訊在進入模型之前就已經遺失。B 降低發生率但沒有修好那一次；D 在服務持續逾時的情況下會得到兩個一致的空清單，反而更有把握地說錯；C 保守但放棄了短暫錯誤本來可以在工具層恢復的機會，尖峰時段會把大量可自助的案件推給人。回讀[錯誤契約](04-tool-contracts.md)。

### S05｜單選；2.4

你在本機新增的票券 MCP server 可以正常使用，新同事 clone 專案後卻看不到這些工具。第一個要檢查什麼？

- A. 確認新同事使用的模型版本是否支援目前的 MCP 規格。
- B. 檢查 server 是否設在使用者作用域，憑證變數是否各自設定。
- C. 請新同事重新安裝 CLI 並清除本機的工具快取之後再試。
- D. 把設定拆開，讓每一種能力各自對應一個獨立的 server。

??? note "答案與逐項解析"
    **B。** 「只有我能用」最常見的兩個原因就是設定放在個人作用域，以及專案只提交了變數名稱而各人的憑證尚未設定。C 是很自然的第一反應，重裝也真的解決過不少問題，但它不會讓一份不在版控裡的設定出現在別人機器上；A 把設定問題誤判成能力問題；D 是對 server 與能力關係的誤解，同一個 server 可以同時提供多種能力。回讀[MCP 設定](05-mcp.md)。

### S06｜複選，選兩項；1.2、1.3

你把「彙整本週爭議案件」交給一個標準（非 fork）子代理。哪兩項是必要的？

- A. 假設共用同一組工具就代表也共用了完整的對話內容。
- B. 在委派內容中帶入已確認的案件事實與各自的來源位置。
- C. 先請協調者把對話存成檔案，讓子代理需要時自行查閱。
- D. 在交付格式中要求每個結論附上 `case_id` 與支持的依據。

??? note "答案與逐項解析"
    **B、D。** 標準子代理拿不到父對話，必要上下文得顯式傳入；交付格式則保住交接之後的證據關係。C 乍看是個聰明的替代方案，但它把「哪些是重點」的判斷丟給子代理自己去撈，而它並不知道該找什麼；A 混淆工具能力與對話內容。回讀[任務編排](02-orchestration.md)。

### S07｜單選；5.2

以下哪一個情況應立即進入人工接手？

- A. 使用者語氣不佳，而且這個問題需要跨部門協調才能完成。
- B. 同一筆查詢已經連續兩次逾時，第三次重試仍在進行當中。
- C. 請求落在政策未涵蓋的範圍，沒有可以依據的規則可套用。
- D. 使用者在同一則訊息中提出兩個彼此獨立的不同問題。

??? note "答案與逐項解析"
    **C。** 政策缺口不能由代理自行補造，判斷本身必須升級。A 綁了兩個看起來都很像升級訊號的條件，但情緒不是判準，跨部門協調也可能仍在既有政策內；B 還在恢復中，尚未證明無法取得進展；D 拆成兩個 issue 各自處理即可。回讀[升級條件](09-context-reliability.md)。

### S08｜單選；5.1

長對話需要壓縮時，哪一項**最不該**被摘要成敘述？

- A. 使用者描述問題發生經過的來龍去脈。
- B. 代理解釋改期政策時所使用的措辭。
- C. 已確認的票號、張數與指定的改期日期。
- D. 使用者對這次處理速度的主觀感受。

??? note "答案與逐項解析"
    **C。** 精確的交易事實應該存在獨立的 case facts，必要時每輪注入；一旦被摘成「幾張票、想近期改期」就再也追不回來。A、B、D 都是敘事性或主觀內容，壓縮它們不會破壞後續判斷的依據。回讀[上下文可靠性](09-context-reliability.md)。

### S09｜單選；5.3

子代理查政策時逾時，但場地容量已經查到。它的回傳應該是什麼？

- A. 回傳容量結果、失敗類型，以及哪些結論還不能被支持。
- B. 回傳容量結果，政策欄位留空，交由協調者自行判斷。
- C. 標記整批任務失敗，等待協調者決定是否重新指派。
- D. 以最接近的同類政策推估後填入，並註明該值為推估。

??? note "答案與逐項解析"
    **A。** 協調者要能同時看到成果與缺口，才決定得了重試、換來源或標記未覆蓋。B 最接近正確，也保留了成果，但空欄位無法分辨「查了沒有」與「根本沒查到」，失敗類型與已嘗試的查詢就此消失；C 丟掉可用成果；D 產生一個看起來有依據的數字，下游很難察覺它是推估。回讀[錯誤傳播](09-context-reliability.md)。

### S10｜單選；4.3

轉人工的交接物件裡有一個 `policy_exception_reason` 欄位，多數案件並不適用。下游的人工佇列**需要分辨「代理判斷後認為不適用」與「代理根本沒處理這個欄位」**。應如何設計？

- A. 設為選填，不適用的案件就直接省略這個欄位不輸出。
- B. 不適用時填入空字串，讓欄位型別在所有案件中保持一致。
- C. 設為必填且允許 `null`，並定義 `null` 所代表的明確意義。
- D. 另外加一個布林欄位，表示這一欄是否已經被處理過。

??? note "答案與逐項解析"
    **C。** `required` 保證欄位一定出現，`null` 表達「已判斷、不適用」，兩者不衝突，正好切開下游要分辨的兩種狀態。D 確實也能表達出這個區別，是四個選項裡最值得討論的一個——但它用兩個欄位表示一件事，兩者可能不同步，而 required 加 nullable 已經內建了同樣的語意；A 讓缺席同時代表兩種意思；B 用空字串佔位，日後會和真實理由混淆。回讀[結構化輸出](08-structured-output.md)。

### S11｜複選，選兩項；1.7、5.4

昨天的爭議案件調查中斷，今天後端的改期政策設定檔已經更新。哪兩項能同時處理「進度」與「舊結論是否過期」？

- A. 用 `--resume` 續跑昨天的 session，讓模型接續原本的脈絡。
- B. 讀取工作索引，取得各項工作的狀態與對應的結果位置。
- C. 比對來源版本，把受設定變更影響的結論標記為需要重查。
- D. 請模型先摘要昨天的結論，再以那份摘要為基礎繼續往下。

??? note "答案與逐項解析"
    **B、C。** 題目要求兩件事同時成立：B 給進度，C 給新鮮度。A 是文件記載的正當機制，也真的能接續對話狀態，但它維持的是對話而不是外部世界——政策檔昨天到今天改過，resume 不會知道，舊結論會原封不動地被當成現況；D 連進度都保不住。回讀[可恢復狀態](09-context-reliability.md)。

### S12｜單選；5.5

你想把高信心案件自動結案。整體準確率 96%，但「跨城市請求」這一類只有 62%，而且該類樣本僅 40 筆。怎麼決定？

- A. 先補足跨城市的標註樣本，再依整體準確率決定自動化門檻。
- B. 把自動結案的信心門檻由 0.9 調高到 0.95，收緊自動通道。
- C. 跨城市一律維持人工，其餘案件依整體準確率全面自動結案。
- D. 依請求類型分別校準，高信心群體仍保留隨機分層抽查。

??? note "答案與逐項解析"
    **D。** 總平均會蓋掉最需要人工的那一群，而 40 筆樣本本身也代表 62% 這個估計並不穩定。C 已經做了一半的分層，是最容易誤選的——但它對其餘案件放棄抽查，模型很有把握的新型錯誤就再也抓不到；A 補樣本的方向對，補完卻又回頭用整體平均決策；B 假設 0.9 與 0.95 的差距對應真實機率，那要先用標註資料校準過才成立。回讀[人工與校準](10-batch-human-review.md)。

## 對答之後

先看**時間**再看分數：12 題有沒有在 26 分鐘內做完？如果超時，超在哪幾題、原因是不熟還是反覆重讀情境？考場上四個情境接連出現，單一情境超時會壓縮到後面的情境。

再把答錯與猶豫的題目填進[弱項清單](12-practice.md#訂正方法)。這一章的題目跨了四個領域，同一份錯誤假設可能同時害你錯掉 S04 和 S09——**跨題重複出現的假設，比單題的對錯更值得記**。

**選到「次佳解」要另外標記。** S09 的 B、S10 的 D、S12 的 C 都是實務上會被接受的做法，只是在本題給定的限制下不成立。選中這些代表方向對但沒讀出關鍵條件，而考場上正是這種題目在分高下。
