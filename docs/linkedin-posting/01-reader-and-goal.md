# 01｜先決定誰需要讀，與你能證明什麼

一篇工程貼文最有用的起點，是一個你能說清楚的問題。例如：影像模型的分數相同，為什麼操作員卻需要花更多時間複判？這個問題讓視覺工程師想到資料分布，讓設備工程師想到工作節拍，也讓軟體 RD 想到結果如何進入系統。

你的背景可以跨域，單篇文章仍需要一個主要讀者。先決定他讀完要能做哪個判斷，才容易刪去與任務無關的術語。

## 產業、角色與技術是三個座標

半導體描述產業；設備軟體 RD、應用工程師與 ML 工程師描述角色；LLM、機器視覺與 Agent 描述技術。把三者排成競爭選項，容易讓題目散成產業新聞與工具公告。選題時把它們交會起來：

> 寫給設備軟體工程師，討論影像判定超時後，程式需要留下哪些資訊才能追查。

這句話已有角色、問題與可能的能力證據。它可以先在模擬程式中完成，之後再討論哪些條件仍需設備端驗證。

| 內容方向 | 主要讀者 | 能讓他評估你的材料 | 需要另行證明的範圍 |
|---|---|---|---|
| 設備／視覺 AI | AOI、視覺與應用工程師 | 影像條件、錯誤分類、取捨理由 | 現場效益、量產可靠性 |
| 設備軟體整合 | 軟體 RD、整合工程師 | 狀態、識別碼、超時、日誌、回歸測試 | 實機通訊、控制與驗收 |
| 工業 AI／ML | ML 與資料工程師 | 資料版本、固定測例、模型比較與回退 | 大規模維運與跨場域泛化 |
| LLM 應用 | 應用 RD、產品工程師 | 文件來源、檢索結果、答案評分與失敗例 | 未測文件與使用者上的品質 |
| Agent 工程 | 軟體與 Agent 開發者 | 工具輸入輸出、重試紀錄、完成條件 | 長時間自主運作的可靠性 |

這張表是本書的內容規劃，不是職缺需求調查。先以最熟悉的一列建立主線，再挑一列作延伸，通常比較容易準備連續的材料。

## 把能力主張分成三種

**做過的事**要能交代負責部分、條件與結果。「參與一個影像專案」範圍太大；若實際負責的是標註檢查，就寫標註檢查如何發現類別定義不一致。

**正在驗證的事**可以展示設計、途中失敗與下一步。公開原型的價值在於別人能看見判斷過程。Raymond Goh 的設備模擬器貼文把技術組合、尚缺現場經驗及請教問題放在一起，是呈現能力邊界的案例；我們沒有檢查其外部程式或驗證部署情況。[原貼文，發布日期未知；查核 2026-09-30](https://www.linkedin.com/posts/raymond-goh-571b0b20a_mes-secsgem-semiconductor-activity-7449805293129183232-eex_)

**讀後的推論**應先交代原作者說了什麼，再說你如何連到自己的問題。例如：「這篇文章討論長文件問答評估；我的下一個問題是，設備手冊的答案缺少適用型號時，該如何判錯？」此時可以提出測試設計，還不能報告改善結果。

三者都能形成有內容的文章。關鍵是讓讀者知道證據停在哪裡。

## 寫一張定位卡

以下是可修改的教學範例，請用自己的事實填寫：

> **我想交流的人：** 需要把模型接到設備程式的工程師。
>
> **我關注的問題：** 判定結果如何被追查、比較與回退。
>
> **我能公開的材料：** 自製模擬資料、測試程式與流程圖。
>
> **我正在補的能力：** 狀態與錯誤處理的設計。
>
> **讀者能帶走的東西：** 一份檢查自己資料流的問題清單。

再把它縮成一句內容定位：「我記錄設備與影像 AI 的整合問題，透過公開小實驗說明資料、模型與軟體如何一起驗證。」這是草稿。只有符合自己的經歷，才適合用作自介。

## 成果要能回到你的目的

想累積作品，可以看是否留下可重現的例子與清楚的說明；想認識同行，可以看是否交換過具體技術問題；想探索未來角色，可以看自己是否真的享受那些任務，並能說明取捨。

曝光提供文章被顯示的背景，不能替代上述成果。一次面試邀請也可能來自多篇文章、既有人脈或其他作品，先記錄對方提到的線索，不急著歸因。

本章練習：寫好定位卡，挑出一項已有材料的主張與一項待驗證的問題。若連材料在哪裡都說不出來，先把主張改寫成問題。接著到[第二章](02-platform-and-evidence.md)，建立判讀平台建議的標準。
