# 角色與寫法：讓同一份工程材料服務不同讀者

從設備／視覺 AI 延伸到軟體 RD、LLM 與 Agent，不必每換一個技術名詞就重做個人定位。先問：這篇要讓哪位讀者判斷什麼？再挑能支持這項判斷的材料和寫法。下表是依讀者工作與可展示證據提出的**編輯推論**；尚未由按讚成效比較驗證。

| 角色方向 | 讀者讀完要能判斷 | 可公開材料 | 可試的主要模式 | 為何適配（編輯推論） |
|---|---|---|---|---|
| 設備／視覺 AI 工程師 | 失敗來自影像、判定條件，還是設備狀態？ | 去識別的影像或合成圖、取像條件、判定定義、錯誤紀錄 | 教學拆解、經驗敘事、專業提問 | 保留物件、成像與操作脈絡，讓跨域讀者看懂模型輸出如何落到檢查任務。 |
| 軟體 RD／整合工程師 | 問題在哪個狀態或介面出現，能否重現？ | 請求識別碼、狀態轉換、預期／實際輸出、錯誤與測試紀錄 | 案例復盤、作品展示、教學拆解 | 可呈現系統如何保留上下文，讓別人檢查你的除錯與介面設計。 |
| LLM 應用工程師 | 回答依據是否足夠，評估如何進行？ | 輸入、模型／提示版本、來源片段、輸出、人工評分規則與失敗例 | 資料解讀、觀點論證、資源整理 | 把「看起來合理」轉成可核對的來源與評分問題，方便工程讀者討論限制。 |
| Agent 工程師 | 任務是否按規則選工具、處理回傳並在合適時停止？ | 任務條件、允許工具、呼叫與參數、回傳、追蹤紀錄、完成條件 | 案例復盤、作品展示、專業提問 | 讀者能沿著執行紀錄檢查行為和邊界，不必只聽系統自述完成。 |
| 資深工程師／顧問 | 哪個方案符合限制，風險與驗收點是什麼？ | 選項、取捨、決策依據、驗證計畫、已知風險與責任範圍 | 觀點論證、案例復盤、里程碑公告 | 從交付單一任務，延伸到說明取捨與協助他人決策；是否採用視你的工作內容而定。 |

模式名稱沿用[04｜發文模式](04-post-patterns.md)：教學拆解、案例復盤、觀點論證、經驗敘事、資料解讀、專業提問，加上作品展示、資源整理、里程碑公告。模式描述文章主要交付什麼，不是技術領域標籤；一篇可有次要模式，但先選一個主要任務。

## 同一份「失敗可追查」材料，四種工程讀者

以下四個都是**假設草綱**，不是親身經歷、實測結果或已完成作品。共用的合成材料只有：一項輸入、預期與實際行為、版本或時間資訊、狀態／錯誤紀錄，以及尚待回答的問題。各領域的欄位名稱是取材建議，不代表已有特定演算法或結果；若換成真實案例，先移除可識別的客戶、設備與人員資訊。

1. **設備／視覺 AI｜教學拆解**：先說明檢查任務與判定落差 → 列出需要對照的影像、取像條件及設備狀態 → 說明如何把影像識別碼連回錯誤紀錄 → 結尾標出還缺哪項證據，暫不判定根因。
2. **軟體 RD｜教學拆解（重現設計）**：交代請求與預期狀態 → 依識別碼整理介面回應、狀態變化及錯誤時間點 → 說明下一步如何重現並核對測試 → 沒有執行結果時，停在待驗證問題，不寫成修復成果。
3. **LLM｜教學拆解（評分設計）**：列出輸入、模型／提示版本、可用來源和輸出 → 指出需要人工核對的引用或評分項目 → 說明失敗紀錄如何連回該次輸入 → 未完成標註前，不填品質分數或宣稱改善。
4. **Agent｜專業提問**：交代假設任務、允許工具與完成條件 → 按序列出預計記錄的工具呼叫、參數、回傳和中止位置 → 說明哪些紀錄可判定任務是否完成 → 邀請同行檢查追蹤欄位；沒有執行資料就不宣稱 Agent 已完成任務。

完成實際測試後，軟體草稿可補結果改為案例復盤，LLM 草稿可補固定測例的數據改為資料解讀。只有設計時先保留教學／待測語氣。

四稿共用「讓一次失敗能被重建」的核心，讀者問題改變後，材料順序也跟著變。你可以把一張事故卡依序改成四版：每版只留該讀者需要的欄位，再到[09｜衡量成效](09-measure-and-learn.md)記下原先目標和後續觀察。這些紀錄可幫你修正選題假說，不能單憑前後差異證明模式造成結果。

## 借寫法，不照搬資深作者的職涯結果

作者故事要連同發文當時的角色、既有受眾和目標來讀。Brendan Gahan 回顧每日發文時是行銷代理商合夥人與 Chief Social Officer；Kiran Shahid 的挑戰則來自內容行銷和接案工作。這些自述能供參考記錄方式，不能替設備工程師預測追蹤者、商機或發文頻率。[Gahan 的回顧](https://www.entrepreneur.com/science-technology/what-i-learned-from-posting-to-linkedin-every-day-for-a-year/365747) · [Shahid 的挑戰紀錄](https://zapier.com/blog/linkedin-challenge/)。接近工程背景的 Didier Lopes 也把早期 side project 與專業對話連在一起，但這是作者回憶，不是轉職機率證據。[原文](https://didierlopes.com/blog/10000-followers-later-heres-where-it-all-began/)

同樣地，軟體工程研究貼文論文只分析特定會議論文分享，不能代表設備、個人職涯或 Agent 貼文。[Wyrich 與 Bogner 的研究](https://arxiv.org/abs/2401.02268)。更多案例能支持什麼，見[案例與作者歷程的判讀方法](research-method.md)。

## 練習

選一份能公開的故障材料，填好讀者、要回答的問題、已有證據與一種主要模式；再寫一版給相鄰領域讀者。若目前只有假設，就把它標成假設或測試計畫。可從[01｜讀者與目標](01-reader-and-goal.md)的定位卡開始，完成後回[導讀](README.md)接續全書流程。
