# 08｜建立可持續的發文流程

查核日：2026-09-30。前章：[07｜對話與再利用](07-conversation-and-reuse.md)；下一章：[09｜衡量與學習](09-measure-and-learn.md)；相關工具：[附錄 A01](appendix-source-checklist.md)。Buffer 頻率分析發布於 2025-08-28、時段分析發布於 2026-09-09、題目提示發布於 2024-07-11；本章查核日皆為 2026-09-30。Anthropic 工程文章發布於 2026-01-09；John D. 貼文日期未知（查核時頁面顯示「5mo」）。

發文流程的目的，是把一份工程材料整理成可讀、可查、可回顧的內容。流程應配合你實際能投入的時間；每週篇數不是平台承諾的最佳值。Buffer 的頻率與時段分析可供形成假說，但樣本關聯不能決定個人帳號應採用的節奏。[頻率分析（Tamilore Oladipo，2025-08-28）](https://buffer.com/resources/how-often-to-post-on-linkedin/)；[時段分析（Kirsti Lang，2026-09-09）](https://buffer.com/resources/best-time-to-post-on-linkedin/)

本章八題全部是**待執行的練習計畫**，不是既有專案或已完成成果。若實驗還沒做完，可以分享問題、設計或閱讀心得；只有在有實際紀錄時，才寫成「測出」「修正」或「改善」。

## 從材料到發文

1. **收集一張素材卡**：只記一個問題、來源或測試、預計讀者，以及哪些內容可以公開。把事實、推論和待驗證假說分開。
2. **選一個讀者收穫**：讀者讀完能理解什麼、比較什麼，或自己嘗試什麼？一篇只處理一個工程問題。
3. **決定內容模式與證據**：教學要有步驟，復盤要有決策與結果，資料解讀要有分母和範圍。若結果尚不存在，改寫成計畫或問題。
4. **做草稿和素材**：先寫清主張，再補圖、流程圖、表格或程式片段。圖只呈現論點需要的資料，不用裝飾替代證據。
5. **做公開檢查**：核對數字、連結、素材權利與敏感資訊；標出模擬資料、尚未實作的部分和未驗證限制。檢查表見[附錄 A01](appendix-source-checklist.md)。
6. **發布並留紀錄**：保存 permalink、發布時間與版本。依固定觀察窗記錄自己的帳號分析；公開可見的讚數不能代替觸及或曝光。
7. **回應和回收題目**：回覆有內容的問題，把不同意見、更正或新問題存回素材庫。不是每篇都要加 CTA，也不必為了湊數發布未完成的結論。

Buffer 的個人發文提示可用來擴充素材庫；像「30 天提示」是題目來源，不是每天都要發文的規則。[Buffer：30 Days of LinkedIn Post Prompts（Kirsti Lang，2024-07-11）](https://buffer.com/resources/30-linkedin-prompts/)

## 四週八篇練習表

每週兩篇的完整版共四篇設備／視覺 AI、兩篇軟體、各一篇 LLM 和 Agent。每題都先準備材料，再決定是否公開；表內作品要求是交付規格，沒有完成前不得寫成成果。

| 週次／類別 | 題目（待執行） | 發文前準備 | 作品要求 |
|---|---|---|---|
| 第 1 週｜視覺 1/4 | 離線分數能回答什麼，不能回答什麼？ | 用公開或合成資料做一份小型混淆表；寫明標籤、誤檢／漏檢和資料範圍。 | 一張表或圖，說明某個分數的含義和不足；合成數字明確標示。 |
| 第 1 週｜視覺 2/4 | 光線或角度改變時，同一物件看起來如何不同？ | 自行拍攝可公開的普通物件，或選有授權的圖片；一次只改一個成像條件並記下條件。 | 對照圖、條件標籤和一段觀察；不得稱為實機或產線缺陷結果。 |
| 第 2 週｜視覺 3/4 | 一次誤判應先查資料、標註還是門檻？ | 用合成案例或可公開的小型資料，建立錯誤分類表，至少列出「原因未知」。 | 展示判斷次序及一個反例；不從少量案例推出通用修正法。 |
| 第 2 週｜視覺 4/4 | 新舊模型的整體分數和單類錯誤如何取捨？ | 在同一組公開／合成樣本上比較兩份預先定義的結果；記錄門檻、版本和限制。 | 一頁比較表，列出有利與不利的錯誤類別；未連接設備就明說。 |
| 第 3 週｜軟體 1/2 | API 超時後，紀錄如何幫助除錯？ | 在本機 mock 服務注入延遲或失敗，準備 request ID、時間、錯誤狀態和測試。 | 小型流程圖或程式片段，加一個失敗測試及修正後預期行為。 |
| 第 3 週｜軟體 2/2 | 多個影像來源如何避免 ID 對錯？ | 建兩個本機模擬來源，刻意重用 frame ID，追蹤來源 ID 穿過佇列和推論函式。 | 一段可重現的測試，展示來源混淆如何被發現與避免。 |
| 第 4 週｜LLM 1/1 | 手冊問答的引用真的支持答案嗎？ | 選可公開閱讀的手冊，確認使用條款；寫 8–10 個問題，含手冊未回答的題目。 | 列問題、引用依據、答案是否有支持，以及何時應回答「資料不足」。 |
| 第 4 週｜Agent 1/1 | 工具暫時失敗時，Agent 重試會不會重複動作？ | 在本機沙盒建立 mock 工具與可重現失敗；設定允許動作、重試上限及人工接手條件。 | Trace 和測試結果，說清楚工具輸入、重試及副作用檢查；不連線到實際設備或正式系統。 |

最後兩篇可參照工程案例的呈現方式：用測試中的具體失敗說明為什麼需要 trace 和 eval，但要清楚標記自己的原型範圍。[Anthropic：Demystifying evals for AI agents（Mikaela Grace 等，2026-01-09）](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)；[John D. 的公開 eval-harness 貼文（日期未知，頁面顯示「5mo」）](https://www.linkedin.com/posts/johndorlus_part-2-is-here-good-news-the-eval-harness-activity-7437542551236124672-odwS)。貼文是作者自述，不是獨立驗證。

## 按可用時間縮放

- **完整版**：每週兩篇，四週完成八個題目卡；先做準備和測試，再決定哪篇值得發布。
- **慢速版**：每週一篇，八週做完同一組題目，保留四篇視覺、兩篇軟體、一篇 LLM、一篇 Agent 的比例。
- **最低負擔版**：先做每週一張素材卡，不急著發布。等有可公開的證據後，從卡片中挑一題寫成貼文；沒有新證據就延後，而不是補寫成已完成。

每週安排一段做實作或查來源，另一段整理與校稿即可；長度依工作量調整。持續記錄實際花費時間，四週後只保留自己能穩定做到的步驟。這是本書的工作設計，不是平台對發文頻率或觸及的保證。下一章會把每篇的發布觀察和技術測試分開記錄。
