# 統整分析：從作者案例選出自己的寫法

**對設備／視覺 AI 工程師，本書建議先以「問題如何被定位、選擇如何被驗證」作為寫作主線。** 它能容納現有設備經驗，也能逐步延伸到軟體 RD、LLM 與 Agent。先寫自己能交代條件的小問題，再增加跨系統的取捨與產業判斷。

這是依現有材料作出的**編輯建議**。本章統整已讀作者文章、職涯自述與研究；沒有新增網路蒐集。多數作者材料來自部落格、專欄或訪談，能分析論述結構，尚不能判定它們在 LinkedIn 的互動效果。

## 一、作者之間，真正值得比較的是什麼？

同樣是「教學」或「觀點」，作者提供的價值可能不同。以下比較只限已讀案例，並非對作者所有作品的定論。原文、日期、角色及讀取範圍見[知名作者選讀](notable-authors.md)與[作者歷程](author-journeys.md)。

| 案例對照 | 材料與寫法的差異 | 讀者得到什麼 | 你可以怎麼用 |
|---|---|---|---|
| 洪士灝／Alex Xu | 洪以工程經驗支持能力清單；Alex 聚焦「何時不該提前最佳化」的一個決策 | 前者幫讀者盤點能力，後者幫讀者避免某個步驟的錯誤 | 手上只有一次經驗時，先回答一個具體決策；累積多個案例後，再整理能力框架 |
| Karpathy／Hamel Husain | 前者以論文重現、實作比較展開推理；後者談如何從工作與反覆被問的問題取材 | 前者讓讀者檢查技術理解，後者讓作者找到值得解釋的問題 | 題目從工作疑問來；證據從可公開的小實驗來，不必每篇都做大型研究 |
| Simon Willison／Harrison Chase | Simon 解釋 coding agent 仍需要哪些操作者判斷；Harrison 回顧產品發展與選擇 | 前者調整使用者預期，後者說明產品路線背後的理由 | 現在可寫工具使用邊界；有長期維護與回饋紀錄後，再寫系統演進 |
| Doug O’Laughlin／Dylan Patel | Doug 已讀部分先解釋背面供電機制；Dylan 的已讀文章組合投資、產能與人才因素形成產業論點 | 前者建立理解門檻，後者提供產業判斷框架 | 優先解釋自己熟悉的機制；要提出宏觀判斷，先補齊不同因素及反例 |
| 李宏毅／Gergely Orosz | 前者課程頁交代讀者前提與學習順序；後者以編者導言引入專家文章 | 幫讀者判斷從哪裡開始、為何值得讀 | 資源整理應說明適合誰、需要哪些前提及能解決什麼問題 |

最後一組比較的是教學安排與編輯功能。李宏毅的來源不是個人短貼文；Gergely 案例的客座技術正文由 Dave O’Connor 撰寫，不能當作 Gergely 的個人經歷。

**共同可借鏡之處，是把讀者的下一個判斷寫清楚。** 「我知道這項技術」可以改成「遇到哪種條件，應該先檢查哪裡」。這比照搬知名作者的開場口氣，更容易落到自己的工作材料上。

## 二、發文模式應跟著材料與責任改變

現有資料不足以證明「職級升高就該改寫觀點文」。更實用的選擇方式，是先問自己握有哪些證據，以及讀者需要做哪種決定。

| 手上有的材料 | 優先模式 | 正文必須交代 | 適合建立的專業印象 |
|---|---|---|---|
| 一個可重現的問題、操作或概念 | 教學拆解 | 前提、步驟、適用邊界 | 能把問題解釋清楚 |
| 已完成的處理過程與結果 | 案例復盤 | 原假設、失敗嘗試、判斷轉折、剩餘問題 | 能排查問題並修正判斷 |
| 可展示的程式、圖表或原型 | 作品展示 | 任務、如何檢查、做到哪裡 | 能把想法做成可查看的成果 |
| 多個方案與明確限制 | 觀點論證 | 選擇標準、代價、什麼條件會改選 | 能處理取捨 |
| 有來源及一致口徑的資料 | 資料解讀 | 樣本、期間、分母、不確定性 | 能區分觀察與推論 |
| 真實卡點與已嘗試的方法 | 專業提問 | 問題條件、嘗試、需要哪種協助 | 能與同行交換有效資訊 |

經驗敘事適合交代「我的判斷為何改變」；里程碑適合交代「現在完成了什麼、接著驗證什麼」。兩者都能搭配上表，但不能替代技術細節。沒有實測結果時，可以寫測試設計及待解問題，等結果出來再寫復盤。

## 三、你的角色可以怎麼串起來？

建議採用一條能延續的問題線：**如何讓工程系統的失敗可觀察、可追查、可驗證。** 這是根據你的領域方向提出的定位假設，需要用實際寫作與讀者回應修正。

| 角色方向 | 可以優先取材的問題 | 讓下一個角色看懂你的關鍵證據 |
|---|---|---|
| 設備／視覺 AI | 影像條件改變後，如何區分資料、光學與模型問題？ | 條件定義、錯誤分類、排查順序 |
| 軟體 RD／系統整合 | 跨模組故障時，日誌能否還原一次請求？ | 狀態轉移、關聯識別碼、重現步驟、測試 |
| LLM 應用 | 文件問答答錯時，如何區分檢索、來源與生成問題？ | 測試題、來源對照、評分準則、失敗樣本 |
| Agent 開發 | 工具呼叫錯誤或流程失控時，如何定位與停止？ | 工具輸入輸出、執行紀錄、停止條件、人員接手 |

表中的問題是選題方向，不代表你已做過這些實驗。更完整的材料範例見[角色與模式選擇](role-pattern-guide.md)。

跨領域的轉換點，是拿出下一個角色能檢查的材料。例如，設備端故障故事若只有「最後成功修好」，軟體讀者較難判斷你的能力；補上狀態、重現與測試，才讓整合與排查能力可見。這個推論關乎作品呈現，並不保證轉職結果。

## 四、讚數目前能告訴我們多少？

現有定量證據能支持「要分開看反應與討論」，還不能支持「哪種模式對你最有效」。

Wyrich 與 Bogner 的 98 篇軟體工程研究貼文，總反應中位數為 20.5；排除發文者與論文作者留言後，48% 沒有其他留言。其精選案例中，一篇有 81 次反應、17 則非作者留言，另一篇有 200 次反應、5 則非作者留言。**反應排名與討論排名可以不同。** 這些精選案例不能用來估計模式的平均效果。[原始論文](https://arxiv.org/html/2401.02268v1)

Kiran Shahid 則自述，一篇互動不高的工作流程貼文帶來客戶詢問。它提示我們記錄詢問的內容與相關性；單一行銷作者自述，不能推出工程師也會得到相同結果。[作者復盤](https://zapier.com/blog/linkedin-challenge/)

| 想回答的問題 | 現在可作的判斷 | 還缺什麼 |
|---|---|---|
| 高反應是否等於有效交流？ | 兩者應分開量測 | 留言內容、對方需求及後續交流紀錄 |
| 哪種模式最適合設備工程師？ | 可先按證據與讀者任務選模式 | 接近此角色的跨作者普通／低互動對照 |
| 作者升職後，寫法與效果是否改變？ | 職涯自述可提出待查假設 | 當時職位、跨期正文、固定觀察窗數據 |
| 中文與英文哪個較有效？ | 目前不能比較；來源體裁與讀者不同 | 同主題、相近受眾與條件下的持續觀察 |

大型平台報告另有公司頁與個人帳號、分母與取樣差異，不能混成一個排行榜。詳見[研究洞察](research-insights.md)及[數據判讀方法](research-method.md)。

## 五、把結論變成第一組寫作練習

先選一個能公開、確實理解的問題，依材料成熟度寫成以下四篇。這是練習順序，沒有要求固定週更或日更。

1. **拆解問題：** 描述一個失敗症狀，列出可能原因與分辨方式。目的是讓相關同行看得懂問題。
2. **展示檢查方法：** 提供最小範例、流程圖或測試設計。只有設計時，清楚標記尚未驗證。
3. **復盤一次判斷：** 有實際結果後，解釋哪個假設被推翻、哪個證據改變決定。沒有結果就繼續提問，不硬湊成功故事。
4. **延伸到相鄰領域：** 說明同一排查方法用到軟體、LLM 或 Agent 時，哪些能沿用、哪些需要改變。

每篇用相同觀察窗記錄反應、具體技術留言、相關詢問與投入時間；能取得曝光時再另行記錄。尤其留下「哪段讓人不理解」「哪個案例被追問」，用來決定下一篇。少量觀察只作個人調整，不宣稱模式勝出。

### 哪些觀察會讓我們改變建議？

- **同行反覆追問同一細節：** 把下一篇改成該細節的教學，逐步形成系列。
- **展示作品有人回應，但看不懂用途：** 先補問題情境、輸入輸出與限制，再增加功能。
- **產業觀點獲得反應，卻少有目標角色交流：** 檢查是否吸引到想服務的讀者，再決定觀點文比例。
- **某種寫法持續帶來有內容的交流，且時間可負擔：** 增加該模式的練習；保留主題、受眾與時機也可能影響結果的解釋。

## 統整結論

現階段最值得模仿的是作者的推理動作：界定問題、解釋機制、比較選項、展示證據及承認尚未解決的部分。你的起點可以是設備與視覺問題，逐步用軟體、LLM、Agent 讀者可檢查的形式呈現。

下一步研究最需要補的是**接近你角色的作者、同一作者跨期的普通貼文，以及發布當時的職位和反應快照**。更多名人能擴充寫法，但現有作者數量增加，尚未解決模式成效與職涯時間軸的資料缺口。

要進一步選擇說話方式，讀[發文語氣：作者樣本、同題改寫與角色選擇](tone-and-voice.md)。
