# 06 工具如何讓模型可靠地做事

工具應清楚定義接受什麼、會改變什麼，以及成功或失敗時回傳什麼。這份約定稱為「工具契約」，讓模型與執行系統能依結果決定下一步。

本章讓你寫出一份最小的編輯工具契約，並辨認格式檢查、權限與實際執行的不同責任。

## 一個名稱不足以說明行為

本書自編的運費任務需要把 `total > 1000` 改成 `total >= 1000`。假設工具只叫 `edit`，接受一段自由文字，回傳「好了」。模型不知道工具會替換第一處、全部位置，還是重新寫整份檔案；執行系統也難以核對結果。

工具設計者可以把請求寫成三個欄位：

- `path`：要修改的檔案路徑。
- `old`：要找到的原有文字。
- `new`：用來替換的新文字。

再補上一條規則：原有文字必須恰好出現一次，否則不寫入。這就把含糊的「幫我改」變成可檢查的操作。

但欄位完整還不夠。路徑可能超出工作目錄，舊文字可能是空字串，檔案可能已被其他人修改。工具契約必須說明這些情況如何處理，不能把所有意外都交給模型猜。

## 把契約寫成可以核對的表

下面是準備把編輯能力公開成工具時的設計草圖，不代表任何產品完整介面，也不是本書實驗已全部實作的功能：

| 項目 | 明確規則 |
|---|---|
| 目的 | 在指定文字檔替換唯一一段文字 |
| 輸入 | `path`、非空的 `old`、允許為空的 `new` |
| 範圍 | 僅允許工作目錄內已存在的目標檔 |
| 成功 | 替換一次，回傳成功與修改位置摘要 |
| 找不到 | 不寫入，回傳 `not_found` |
| 找到多處 | 不寫入，回傳 `ambiguous` 與匹配數量 |
| 無法讀寫 | 回傳可辨認的錯誤及已知副作用狀態 |

本書的 `edit_demo.py` 只實作輸入型別、非空原文、唯一匹配與拒絕時原檔不變。示範程式自行選定可信的暫存路徑，沒有提供工作目錄授權；成功回傳 `None`，不符前提時拋出 `ValueError`。若要供模型直接呼叫，還需補上表中的路徑限制與結構化結果，不能把示範函式直接當成完整工具介面。

`new` 可以為空，因為刪除一段已定位文字是合理操作；`old` 不可為空，因為空字串沒有提供要改哪裡的依據。這個差別說明輸入驗證應反映操作含義，不能只檢查每個欄位都是字串。

範圍限制也需要真實路徑判斷。只檢查輸入是不是以某個字串開頭，可能把相似路徑誤認成工作目錄。正式工具還要依平台處理符號連結與執行期間的狀態變動。本書小實驗只示範有限檔案操作，不宣稱提供作業系統等級的隔離。

## 格式正確、准許操作與執行成功是三件事

工具要求進入系統後，可以依序問：

1. 工具先檢查格式：必要欄位齊全嗎？型別與值符合約定嗎？
2. 權限系統再檢查授權：此回合可以改這個檔案嗎？
3. 工具執行時確認結果：目標存在且符合前提嗎？寫入完成了嗎？

即使前兩項通過，檔案仍可能在執行前被移走。相反地，路徑存在也不代表代理有權修改。把三種結果混成一個「錯誤」，會讓模型選錯恢復方式：缺少欄位應補參數，權限拒絕應遵守限制，檔案變動則應重新讀取。

論文快照中的工具介面有很大差異。Claude Code 把驗證、權限、並行安全與呈現分成不同責任；Gemini CLI（在終端機使用的程式開發代理）的排程器讓要求經過驗證、執行及完成或錯誤狀態。這些案例可用來理解責任分工，不表示小型工具也必須照搬相同類別架構。[來源：論文 §8.2](https://arxiv.org/html/2609.00006v1#S8.SS2)

## 錯誤回傳要支持下一個動作

「編輯失敗」沒有告訴模型如何修正。較有用的回傳可以是：

```json
{
  "ok": false,
  "error": "ambiguous",
  "matches": 2,
  "changed": false,
  "message": "舊文字出現兩次；請加入周邊程式碼定位。"
}
```

這份本書自編回傳讓下一輪知道兩件事：檔案沒有改，以及應縮小定位範圍。`changed: false` 必須由工具實際行為支持，不能在任何例外都盲目填入。若寫入可能已發生，工具應回報不確定，讓執行系統重新讀檔核對。

同樣地，命令執行工具應區分執行結束碼、標準輸出與錯誤輸出。輸出中有「error」一詞，不一定代表命令失敗；沒有文字也不一定代表成功。模型需要程式提供清楚的狀態，而不是靠語氣猜測。

工具輸出太長時，可以截斷，但應標明哪些內容被省略，並提供進一步讀取方式。若把測試結果尾端切掉，卻回傳「完整輸出」，模型可能錯過最後的失敗總結。控制篇幅不能犧牲結果的可判讀性。

## 工具少，不一定代表權限小

論文快照的工具數量從單一命令工具到數十種以上。Shell（讓程式或人輸入並執行命令的介面）只需一個工具，就可能讀檔、刪檔、連網或啟動其他程式。因此，工具數量不能直接當成權限範圍，也不能當成安全程度。[來源：論文 §8.1–8.2](https://arxiv.org/html/2609.00006v1#S8)

專用的讀檔、搜尋和編輯工具較容易提供清楚的參數與錯誤，但每增加一種工具，都要維護說明和執行行為。通用命令工具較靈活，卻把更多格式與命令組合的責任交給模型。選擇應看實際失敗：是否經常截斷輸出、誤用命令，或難以判斷副作用。

論文作者建議從少量工具開始，再依觀察到的失敗補充工具。本書的無金鑰實驗選擇白名單操作，方便讀者重跑與核對；這是教學範圍的選擇，不是宣稱通用命令在所有部署都不合適。[來源：論文 §16.3](https://arxiv.org/html/2609.00006v1#S16.SS3)

## 先用反例檢查工具說明

工具說明寫完後，可以先不用模型，直接送入幾個反例。缺少路徑時，工具是否清楚拒絕？舊文字是空字串時，是否在讀寫前擋下？舊文字出現兩處時，回傳的匹配數量是否正確？這些檢查針對契約，不依賴模型剛好願意遵守規則。

接著檢查成功回傳的含義。如果工具只確認資料已交給背景工作，回傳應寫「已開始」，不能寫「已完成」。執行系統需要保存可查詢的工作識別碼，再取得真正結果。否則下一輪可能在測試尚未結束時就結案。

有副作用的工具尤其需要說明能否重複呼叫。運費替換成功後，原有文字已經消失，第二次相同要求可能回傳找不到；這不表示第一次失敗。重試前讀取現況，能避免把成功操作誤認為需要再次修復。對外部服務，還可能需要服務提供的重複請求識別機制。

最後比較工具文件與實作。文件說「未讀過就不能編輯」，並不代表程式真的追蹤讀取紀錄。論文在提示分析中就指出了描述與實作不一致的案例。閱讀原始碼研究時，要確認規則由哪一層執行；設計自己的工具時，也要讓說明符合真正提供的保證。[來源：論文 §7.3](https://arxiv.org/html/2609.00006v1#S7.SS3)

## 工具很多時，讓模型按需找到它

每個工具的名稱、說明與參數都占用輸入空間。工具目錄變大後，可以先提供搜尋入口，等模型找到需要的工具，再載入完整說明。這稱為「延後載入工具」。它減少初始輸入，也增加一次發現工具的步驟。

論文 §8.3 區分兩種容易混淆的延後載入：延後把工具說明放入模型輸入，以及延後連上外部服務。前者主要處理提示篇幅，後者主要處理啟動成本。名稱相似，解決的問題不同。[來源：論文 §8.3](https://arxiv.org/html/2609.00006v1#S8.SS3)

如果運費任務只有讀檔、編輯、測試三個工具，直接列出通常比較容易理解。當大量工具說明開始占用可觀空間時，再評估搜尋是否能節省成本。論文提出的工具數量門檻屬於作者的實務建議，不是所有模型都適用的硬限制。

## 進階：已登記、看得見與能執行是三個狀態

當工具目錄變大，系統通常不會把所有工具一律交給每個模型。論文快照中的 Hermes 把工具登記與曝光分開，再依平台選出模型看到的工具集合。它還會探測工具是否可用，並保留短暫故障前的可用狀態，避免一次外部檢查失敗就讓整組工具消失。[來源：論文 §8.2](https://arxiv.org/html/2609.00006v1#S8.SS2)

設計者要分清三種狀態：

- **已登記：**程式知道工具名稱及執行方式。
- **看得見：**本輪模型收到工具說明。
- **能執行：**工具還要通過授權與執行前檢查。

延後載入會改變可見性，但不應自行擴大授權。工具即使剛被搜尋出來，也仍須遵守原本的資源範圍。

以下是本書教學例子。運費代理搜尋到測試工具，當時環境探測顯示測試程序可啟動。幾秒後，工作目錄被移除，實際呼叫仍可能失敗。因此，可用性探測只能協助選擇工具，不能保證稍後操作成功；真正結果仍要由執行時回傳。

反過來，一次探測失敗也不必永久移除工具。若故障只是短暫連線問題，系統可以標記暫時不可用並稍後重查。但若原因是授權撤銷，就不能把先前成功當成繼續執行的理由。可用性快取與權限檢查承擔不同責任。

工具可見性改變後，相關說明也要一起更新。唯讀角色若仍收到「可以修改檔案」的提示，模型會依過時指引反覆提出無法執行的要求。保持工具目錄、提示與執行規則一致，能減少這類無效往返；最終的權限限制仍必須由執行端落實，不能只靠把工具名稱藏起來。
