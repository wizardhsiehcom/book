# 三組不用模型服務金鑰的實驗

這三組實驗讓你直接觀察工作迴圈、檔案編輯與資訊保留。它們使用固定資料，不代表真實模型的解題能力。

需要 Python 3.8 以上版本。下載檔案後，在存放檔案的資料夾開啟終端機，用 `python 檔名.py` 執行；若電腦以 `python3` 啟動 Python，請替換命令開頭。不要加 `-O`，它會停用本實驗的 `assert` 檢查。

## 先看工作何時算完成

下載 [loop_demo.py](loop_demo.py)，執行：

```text
python loop_demo.py
```

程式列出每一步的編號、工具與結果，最後印出 `PASS: loop checks`。

| 情境 | 預期狀態 | 意義 |
|---|---|---|
| 讀取、修正、檢查、完成 | `completed` | 模擬狀態通過三個指定檢查 |
| 要求不存在的工具，再修正 | `completed`，前面有錯誤紀錄 | 錯誤保留下來，後續動作仍可修正 |
| 讀檔工具模擬執行失敗，再修正 | `completed`，前面有錯誤紀錄 | 工具內的例外也回到流程 |
| 持續讀取而超出上限 | `step_limit` | 沒有完成，也沒有執行超出上限的動作 |
| 修正後直接說完成 | `unverified` | 缺少檢查證據 |
| 對原本錯誤狀態檢查 | `unverified` | 1,000 元邊界仍失敗 |
| 檢查通過後再次修改 | `unverified` | 舊驗證不替新修改背書 |

這裡的 `fix` 只改變記憶體中的布林狀態，不編輯真正程式。工具白名單包含 `read`、`read_missing`、`fix`、`check`、`finish`；沒有可執行任意命令的工具。`read_missing` 故意拋出模擬的檔案不存在錯誤，沒有碰觸磁碟。請把正常案例中的 `check` 移到 `fix` 前面，再執行：你應看到該案例的斷言失敗，因為舊檢查不能替新修改背書。

要恢復原本檢查，請重新下載或改回動作順序。這是本書的故意失敗練習，不表示 Python 安裝有問題。

## 再確認拒絕修改時檔案沒有變

下載 [edit_demo.py](edit_demo.py)，執行：

```text
python edit_demo.py
```

程式在暫存資料夾自行建立 `price.py`，完成後由 Python 清理。唯一匹配會成功；找不到原文、兩處匹配、重疊匹配與空字串會拒絕。最後印出 `PASS: edit checks`。

程式使用位元組替換，讓原有 CRLF 換行（Windows 常見的換行格式）保持原樣；先寫旁邊的暫存檔，再替換目標，減少直接寫壞原檔的風險。它沒有模擬磁碟損毀，也沒有協調其他同時寫入者。實驗也不保證保留檔案權限、時間戳記等附加資料。

`replace_unique` 的檔案路徑由可信的示範程式提供。若要把函式直接公開成代理工具，還必須加入工作目錄及路徑授權；不要把這個函式當成沙箱。

閱讀[第 7 章](../07-file-editing.md)後，試著說明：為什麼找到第一處之後，仍要從下一個位置搜尋第二處？`aaa` 中的 `aa` 又有幾個可能起點？

## 最後比較摘要保留了什麼

下載 [context_demo.py](context_demo.py)，執行：

```text
python context_demo.py
```

預期輸出：

```text
漏掉事實: ['constraint', 'evidence']
把未知改成成功: ['evidence']
保留必要資訊: []
PASS: context checks
```

`REQUIRED` 是事先由人指定的驗收資料，不是程式自行從對話發現的真相。空串列表示這五項固定資料吻合，沒有表示任意自由文字都被理解。把正確資料改成同義句也會判為不吻合；這正是精確檢查的範圍限制。

練習新增一項事實：「測試只能在指定副本執行」。然後觀察舊摘要缺少哪個欄位。回到[第 9 章](../09-context-compaction.md)，說明哪些資訊應保留原文，哪些可摘要。

## 三組通過之後能說什麼

你能說：這些固定案例下，停止狀態、唯一匹配與關鍵資訊核對符合程式中的預期。你還不能說：模型能穩定修好陌生專案、摘要語意一定正確，或此原型適合執行不可信程式。
