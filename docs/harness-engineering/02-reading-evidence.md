# 02　原始碼比較能告訴我們什麼

原始碼研究能幫你理解系統怎麼組成，不能單獨證明哪個系統跑得最快或最會修程式。讀本書時，請把「觀察到的實作」和「值得採用的設計」分開判斷。

本書根據指定論文整理知識，沒有重新稽核所有產品的原始碼。因此，「論文指出」表示我們能定位作者的記錄；不表示本書已獨立重現那個產品行為。

## 先看研究到底問了什麼

作者選取不同設計取向的系統，沿七個面向讀原始碼。這種研究很適合回答：「有哪些工作迴圈？上下文放不下時如何處理？權限在哪裡攔截？」

它沒有把全部系統放到相同模型、相同題目與相同執行設定下比賽。因此，它無法直接回答：「我的專案用哪個產品成功率最高？」後者需要另外設計實驗。[來源：論文 §4](https://arxiv.org/html/2609.00006v1#S4)、[§15.6](https://arxiv.org/html/2609.00006v1#S15.SS6)

把這個差別帶回免運案例。你讀到系統甲採用精確文字替換，系統乙提供多階段模糊匹配。這能告訴你兩種編輯策略存在，也能推導它們面對找不到原文時的處理方向。要判斷哪個在你的程式庫更可靠，仍需要同一批修改任務與可核對的結果。

## 「十一個系統」不代表十一個相同樣本

論文樣本包含主要處理程式工作的 Harness，也包含跨訊息平台的助理 OpenClaw。作者把 OpenClaw 當作非程式開發的對照，藉此觀察擴充或協定是否跨領域出現。

Omnigent 則另作上層協調系統的對照。它位於 Harness 之上，不是多出來的一個同類編輯迴圈。若把它直接納入編輯工具數量排名，分母就失去一致性。[來源：論文 §4.1](https://arxiv.org/html/2609.00006v1#S4.SS1)

所以，讀到「若干系統採用某功能」時，要連同分母一起讀。研究全部十一個樣本，和只看十個以程式工作為範圍的 Harness，回答的問題不同。採用次數也不是滿意度、穩定度或市場占有率。

## 版本是主張的一部分

作者把多數案例定位在 2026 年 7 月的版本；具體標籤列於原文表 3。其中 Claude Code 的原始碼材料來自 2026 年 3 月流傳快照，不能把同表列出的 7 月執行檔版本當作已完成原始碼查核的對象。

這個差異影響可重現性：讀者若下載另一個版本，可能找不到同樣的內部結構。此時先核對來源，而不是立刻認定作者或產品有錯。[來源：論文表 3、§15.6](https://arxiv.org/html/2609.00006v1#S15.SS6)

本書把常見主張分成兩類。**版本清單主張**包括工具數量、設定檔名稱與特定功能是否存在。它們容易隨更新改變。**結構主張**包括「工具結果要送回工作迴圈」或「權限判斷與執行隔離負責不同工作」。它們較適合拿來建立概念，但也要保留適用條件。

| 看見的句子 | 先查什麼 | 可以暫時得到的結論 |
|---|---|---|
| 系統甲有某工具 | 版本及啟用條件 | 該快照中有這項設計 |
| 多個系統採用同一模式 | 樣本與模式定義 | 這是值得比較的常見做法 |
| 某模式讓成功率提升 | 相同條件與對照實驗 | 若條件不完整，先保留因果判斷 |
| 應該採用某模式 | 部署情境與替代方案 | 這是一項需要驗證的建議 |

## 缺席是一條線索，不是禁止令

論文的一個醒目發現是：作者在檢查範圍內，沒有找到通用 agent 編排框架用於受查 Harness 的工作執行路徑，也沒有找到以向量嵌入檢索程式碼的機制。

這個發現有範圍。程式碼檢索不等於對話記憶檢索；檢查相依清單與匯入語句，也不等於窮盡所有動態載入和內部改寫。作者在限制章承認框架缺席查核的這些邊界。[來源：論文 §13.2](https://arxiv.org/html/2609.00006v1#S13.SS2)、[§15.6](https://arxiv.org/html/2609.00006v1#S15.SS6)

合理用法是先問：「現成的檔案路徑、文字搜尋與符號資訊，是否已足以找到我要的程式？」如果足夠，就有理由先保持簡單。若你的工作主要是查跨專案設計文件，這份樣本未必能回答全部需求。

不合理用法則是：「十一個樣本沒用，所以任何人都不該用。」它把研究範圍擴張成全領域定律，也略過了任務差異。第 8 章會把這個問題變成可執行的查找流程。

## 三種常見的推論跳躍

**把程式量當成效果。** 程式多可能是在處理介面、平台相容、治理與恢復；程式少也可能把責任交給外部環境。只看行數，無法知道任務成功率，更無法知道總維護成本。

**把自報分數當成排名。** 不同模型、題目處理及執行權限，都會影響分數。論文移除了概覽表中的舊分數比較，也提醒讀者不要拿不同條件的數字作直接勝負判定。[來源：論文 §5](https://arxiv.org/html/2609.00006v1#S5)

**把相似做法當成抄襲或因果。** 系統設計與公開工程建議相近，可能出於相同限制，也可能受公開資料影響。沒有額外證據，就不能判定唯一原因。來源有明確沿用記錄時，才另作較強的描述。

還有一種更隱微的跳躍：看到作者畫出合理曲線，就以為已完成量測。論文 §15.5 的架構複雜度與能力關係，是待驗證的直覺。它可用來提出問題，不能拿來預測「加一個功能必然提升多少」。

## 用一張卡片保存判斷

下表是本書的原創讀論文工具。挑一項你準備用在工作上的建議，填完再採用。

| 欄位 | 免運案例的填法 |
|---|---|
| 我想改善什麼 | 不讓編輯工具誤改第二個相似條件 |
| 來源說了什麼 | 原文比較唯一匹配與其他編輯策略 |
| 來源怎麼知道 | 讀取指定快照的實作 |
| 我的推論 | 這個小任務可先要求唯一匹配 |
| 缺少什麼證據 | 我的專案出現重複片段時如何處理 |
| 最小檢查 | 測零、一、兩個匹配；拒絕時檔案不變 |
| 何時重新選擇 | 實際任務持續因合法格式差異而失敗 |

這張卡片沒有把一切變成研究專案。它只讓你在「來源說了什麼」與「我準備做什麼」之間，留下可回頭檢查的一步。
