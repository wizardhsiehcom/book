# 14　如何比較不同系統的設計

先固定任務與限制，再比較架構。功能數量只能描述系統有什麼，無法直接告訴你哪個設計適合自己。

前面各章拆開了工作迴圈、工具、上下文與權限。本章把它們放回同一張桌上：同樣是修正免運門檻，個人練習、團隊日常開發與無人值守服務，可能需要不同的安排。

## 比較前先寫下四個條件

假設你要評估兩個設計：甲用一個簡單迴圈操作本機副本；乙把每一步寫成事件紀錄，並提供權限控制與續跑。不要先問哪個「比較先進」，先問下列問題。

1. **結果是什麼？** 只提出修改建議，還是寫檔、執行檢查並留下證據？
2. **輸入可信到什麼程度？** 是自己寫的小程式，還是來源不明的專案及工具輸出？
3. **失敗後誰接手？** 開發者在旁邊，還是要隔天才有人查看？
4. **工作會持續多久？** 一次短任務，還是會中斷、恢復與交接的長任務？

這些問題先決定必要能力，再決定比較項目。若工具會執行專案程式，輸入來源尤其重要：把不可信程式放進副本，不會自動限制它讀取電腦其他資料。

## 同一個任務，三種合理的部署

下表是本書的設計練習，不是原文產品評分。

| 情境 | 不能省的事 | 可以先保持簡單的事 | 首要失敗成本 |
|---|---|---|---|
| 個人讀書實驗 | 限定操作、保留原檔、檢查邊界案例 | 模擬模型、序列操作、沒有長期記憶 | 看不懂或得到錯誤學習結論 |
| 團隊有人值守開發 | 規則可見、權限清楚、差異可審查、測試可追溯 | 單一 agent，先沿用既有工具 | 誤改共享工作、漏掉回歸 |
| 共用的自動處理服務 | 工作隔離、憑證邊界、預算、中止與稽核 | 先限制可接受任務類型 | 跨使用者資料暴露、失控操作 |

三個情境都能用 `shipping_fee` 當功能測試。但後兩者還要檢查部署行為，例如中途取消後有沒有留下半份修改，或某項寫入是否超出允許範圍。

因此，功能測試通過只回答了部分問題。它無法替代隔離檢查，也無法證明成本可接受。

## 從論文取三組有用的對照

**簡單迴圈與持久事件紀錄。** 論文中的 Mini-SWE-Agent 提供容易追蹤的線性流程；OpenHands 則把動作與觀察保存為事件，支援較豐富的工作階段操作。這組對照適合問：「任務是否需要中斷後恢復、重建狀態或分支？」[來源：論文 §6](https://arxiv.org/html/2609.00006v1#S6)

不要把「有事件紀錄」理解成重跑外部動作一定安全。重播紀錄以理解過去，和再次執行寫檔或外部請求，是兩件事。若上次已送出操作卻沒有收到回覆，恢復流程還需要處理結果不明。

**把功能放在核心，或交給擴充。** Pi 的研究快照把許多能力放入擴充機制。這讓核心較小，但部署者必須知道需要哪些擴充、擴充何時生效，以及更新後是否仍相容。省下核心程式，不等於省掉部署責任。[來源：論文 §10.8](https://arxiv.org/html/2609.00006v1#S10.SS8)、[§13.1](https://arxiv.org/html/2609.00006v1#S13.SS1)

**單一模型取向與多供應商支援。** 論文的案例顯示，支援多家模型不必只取最少共同功能；也可以集中維護各模型的差異。但新增的快取、訊息格式與推理設定，都要有人維護。這組對照適合問：「可切換性值不值得這份持續成本？」[來源：論文 §7.1、§15.4](https://arxiv.org/html/2609.00006v1#S7.SS1)

以上是論文快照的教學比較。選購或部署今日產品前，仍須核對當前文件與實際設定。本章不把歷史功能表當作現況保證。

## 五個取捨方向不能直接加總成分數

論文 §13.4 提出幾個比較方向：簡單與能力、安全與自主、供應商耦合與可切換性、整體組裝方式，以及架構複雜度與模型能力。這些方向能幫你找問題，不適合機械式各打五分再相加。

原因是各項責任可能有最低門檻。共用服務若不符合資料隔離要求，不能用「介面很好用」補回缺口。同樣地，要求每一步人工批准的系統，也可能根本不符合無人值守的目的。

「安全與自主」也不一定是單純此消彼長。把執行範圍限制清楚後，某些低風險操作反而能自動進行，減少重複詢問。要比較的是實際保護範圍與工作阻力，不只是彈窗次數。

論文 §13.4 對供應商耦合的簡化描述，應與 §7.1、§15.4 一起讀；後兩節明確討論多供應商系統保留專屬最佳化的做法。讀比較框架時，要讓細節修正標籤，而不是反過來。

## 為免運案例設計一次公平比較

下面是可執行的比較方法。它是本書建議，不是論文已完成的量測。

先固定程式、需求與驗收答案。兩個方案都要處理 999、1,000、1,001 元；都不得改動其他費用規則。接著固定模型版本、可用操作及執行環境。若你只想比較編輯契約，就不要同時更換模型。

準備三類檔案：原文只出現一次、完全沒有出現、出現兩次。記錄是否改對、是否拒絕不明確修改、失敗後檔案是否原樣保留。這比只問「最後有沒有說成功」更容易查核。

若真實模型會參與，單次執行不足以描述穩定性。對相同條件重複測試，保留每次結果與失敗類型。別把多次重試中最好的一次，與另一方案的第一次直接比較。

| 要觀察的結果 | 如何記錄 | 不能混淆的事 |
|---|---|---|
| 修改正確 | 比對預期差異與邊界測試 | 寫檔成功不等於規則正確 |
| 失敗可恢復 | 確認原檔、錯誤訊息與下一步 | 捕捉例外不等於恢復完成 |
| 成本 | 記錄模型呼叫、工具時間與人工介入 | 更少步數不必然代表更低總成本 |
| 權限有效 | 提出禁止操作，觀察是否真的被阻擋 | 模型口頭答應不算強制執行 |

## 進階：分辨單一機制的效果與組合效果

如果方案乙同時換了模型、編輯工具和摘要策略，即使成功率上升，也不知道是哪個改動有幫助。論文提供架構觀察，並未替你完成這種因果比較。以下是本書延伸的評估方法。

先建立基準方案，再一次改一項條件。例如固定模型與工具，只加入摘要。除了記錄完成率，也記錄是否漏掉「不得改其他費用」的限制。摘要可能節省輸入，卻增加重讀檔案的次數；只量單次提示長度會漏掉後續成本。

單項比較後，再測兩項機制一起工作。摘要與子 agent 各自可用，不代表組合後也可用。主 agent 若把尚未驗證的修改摘要成「已完成」，子 agent 即使忠實執行交接，也會從錯誤前提出發。這是交接邊界的失敗，不能只歸咎於子 agent 的能力。

| 比較步驟 | 固定什麼 | 想排除的誤判 |
|---|---|---|
| 基準對新增摘要 | 模型、工具、任務集、預算 | 把模型變強誤當成摘要有效 |
| 基準對新增分工 | 同樣的驗收與總預算 | 把額外花費誤當成架構優勢 |
| 摘要加分工 | 交接欄位與版本證據 | 忽略各自通過、合起來失敗的情況 |

調整方案時使用一組任務，最後用另一組未參與調整的保留任務檢查。否則可能只是把提示修到剛好適合已看過的錯誤。小樣本先報告「通過幾次／總共幾次」和失敗類型，別讓百分比掩蓋樣本太少。

最後檢查結果是否改變了原先決策。如果摘要省下的成本小於漏掉限制後的修復成本，就沒有理由只因提示變短而採用。相反地，若長任務無摘要就無法繼續，重點應轉為如何保留限制與回查來源。取捨必須連回部署條件。

## 比較的產物是一項可改變的決定

對本書的單檔實驗，可以先選序列迴圈與唯一匹配編輯。理由是工作短、操作少，而且失敗情況容易觀察。升級條件則可以寫成：「若需要跨工作階段恢復，先加入可靠的狀態紀錄；若多個工作共用服務，先補齊隔離設計。」

這種寫法保留了取捨的原因。日後情境改變，你知道要檢查哪個假設，不必把原先選擇捍衛成永遠正確。
