# 07 修改檔案前要確認什麼

修改前先確認目標仍符合預期，而且能唯一定位。不明確時停止寫入，通常比猜一個位置繼續更容易恢復。

本章讓你比較文字替換、補丁與模糊匹配，並用實驗核對拒絕編輯時原檔是否保留。

## 改一個符號，也需要定位依據

本書自編的 `price.py` 原本包含：

```python
def shipping_fee(total):
    return 0 if total > 1000 else 60
```

需求是滿 1,000 元免運，因此要把 `>` 改成 `>=`。如果要求是「把第 2 行的大於改掉」，有人在檔案開頭加上一行註解後，行號就不再指向原處。行號適合顯示位置，但不宜單獨承擔修改前提。

較明確的要求是：在 `price.py` 找到整段 `return 0 if total > 1000 else 60`，確認恰好一處，再換成使用 `>=` 的版本。原有內容同時提供位置和前提：只有檔案還長這樣，才套用這次修改。

這種做法稱為「精確文字替換」。精確指字元必須符合，不代表程式語意一定正確。模型仍可能把正確的免運條件改錯；工具只能確定它改到了約定的文字。

## 零處、一處與多處要分開處理

| 找到的位置數 | 代表什麼 | 本書教學工具的動作 |
|---|---|---|
| 0 | 舊內容不在檔案中 | 不寫入，要求重新讀取 |
| 1 | 能唯一定位 | 套用一次替換 |
| 2 或更多 | 定位內容不足 | 不寫入，要求補充周邊內容 |

零處匹配有多種原因。可能是縮排不同、其他人改過，也可能模型記錯文字。工具不能直接知道是哪一種。回傳「找不到」後，模型應先讀目前內容；盲目重送相同要求沒有增加任何資訊。

多處匹配則是另一個問題。假設註解和函式本體都出現 `total > 1000`，只給這段短字串就不夠。可以把函式名稱與周邊行一起加入 `old`，讓工具只找到預期函式。若需求真的要修改全部位置，應使用另外明確宣告的操作，不能把「第一處」當成任意的預設答案。

還要拒絕空的舊文字。空字串沒有提供定位資訊，某些字串函式卻會把它視為出現在許多位置。這是輸入契約問題，應在搜尋前擋下。

## 精確、補丁與模糊匹配各付出什麼

精確替換容易說明與驗證，但模型若產生不同空白，就可能失敗。補丁則描述要刪除、加入及保留的周邊行，適合表達多處修改；執行器必須解析補丁，並核對每個區塊的上下文。

模糊匹配允許某些差異，例如忽略部分空白，或找出相似內容。它可能減少格式偏差造成的拒絕，卻也增加「匹配到相似但不是目標的位置」的風險。相似分數只描述文字接近程度，不證明兩段程式承擔相同功能。

論文快照記錄了多種實作：Claude Code 採精確唯一替換，Codex 使用補丁格式，其他系統會逐步放寬匹配或借助模型修復編輯要求。這些是來源版本中的設計，不是當前產品功能保證，也不是同條件下的勝負排名。[來源：論文 §8.4](https://arxiv.org/html/2609.00006v1#S8.SS4)

論文作者建議依模型能力選擇編輯契約。本書把它視為需要驗證的起點：若精確匹配經常失敗，先記錄失敗原因。若多半只是尾端空白，未必需要加入完整的相似度搜尋。若要放寬匹配，應同時測試誤改率，不能只計算成功套用的次數。[來源：論文 §16.4](https://arxiv.org/html/2609.00006v1#S16.SS4)

## 不要把「提供候選」和「自動套用」混在一起

工具找到一段相似文字後，可以回傳給模型參考，也可以直接把它當作匹配位置。兩者的責任不同。提供候選讓模型有機會重新讀取與確認；自動套用則把選擇位置的責任交給匹配演算法。

論文 §8.4 的修正註記尤其值得注意：作者重新查核後指出，Mistral Vibe 某個舊版本的模糊匹配用來產生最接近的錯誤提示，並沒有直接套用模糊編輯。因此，書中不能只看「有模糊匹配」就寫成「會自動模糊替換」。[來源：論文 §8.4](https://arxiv.org/html/2609.00006v1#S8.SS4)

在運費案例中，回傳另一段相似條件可能幫助模型發現定位太短。但若另一個函式其實處理不同費用，直接套用就會引入新錯誤。候選內容應當作重新判斷的線索，不是修改授權。

## 多處修改要先確認失敗時留下什麼

若一次要求改三個區塊，而第三個區塊找不到，前兩個是否已寫入？這個問題必須由契約回答。逐一寫入的工具可能留下部分修改；先驗證全部區塊再套用，則能避免已知匹配失敗造成的半套結果。

但「全部匹配先通過」仍不等於任何故障都能回復。磁碟寫入、程序中斷或其他程序同時修改，都可能帶來新的問題。正式實作可能需要暫存檔與替換、版本檢查或鎖定。這些機制各有平台限制，不能用一句「原子操作」掩蓋未實作的保證。

本書的實驗只處理單一檔案、單次唯一替換，並檢查零處或多處匹配時沒有寫入。這個範圍足以理解定位契約，不代表實驗已涵蓋多程序競爭、當機復原或多檔交易。

即使只有一處修改，讀取與寫入之間仍可能發生變動。在共享工作目錄中，可以比較讀取時的版本指紋與寫入前的檔案內容；若不一致，就重新讀取。版本指紋是檔案內容的摘要，能用來偵測改變，不能告訴你別人的修改是否合理。若要求更強的並行保證，還要處理最後檢查與寫入之間的競爭。

## 套用成功後，還有兩種檢查

第一種是檢查差異：是否只修改預期位置，是否意外重寫了空白、換行或其他內容。第二種是檢查行為：999、1,000、1,001 元是否分別回傳 60、0、0。前者確認修改範圍，後者確認需求附近的行為。

兩種檢查不能互相替代。一份只有一個符號的差異仍可能改錯規則；一組通過的測試也可能漏掉無關檔案的意外變動。完成回覆應交代自己真正檢查了什麼。

## 依失敗原因選擇下一步

遇到零處匹配時，先重新讀取指定函式。若檔案其實已經是 `>=`，就不必再編輯，而應確認這個現況符合需求並執行檢查。若內容仍是 `>`，只是縮排不同，就把實際讀到的文字用作新的定位依據。

遇到多處匹配時，增加上下文，而不是先放寬相似度。歧義表示候選太多，放寬通常只會增加候選。相反地，如果唯一目標只是換行形式不同，可以評估受限的格式正規化，但仍要確認唯一性與保留未修改內容。

如果修改已套用、測試卻失敗，問題就不再是文字匹配。應讀取失敗案例，檢查修改是否理解錯規則，或是否有另一條呼叫路徑需要處理。一直調整匹配演算法無法修正語意錯誤。

這條決策路徑把三種失敗分開：找不到位置、位置不唯一，以及改完後行為不符。讀者可以先分類，再選工具；避免每次失敗都改用更寬鬆的寫入方式，把原本可恢復的錯誤變成誤改。

## 進階：容忍格式差異，不等於重寫整份檔案

假設模型提供的舊文字使用一般空格，原檔卻帶有不同 Unicode 字元或尾端空白。工具可能先把文字正規化，也就是轉成統一形式後再比較。這與「找一段相似度夠高的文字」不同：前者明定忽略哪些差異，後者依距離或分數接受近似候選。

論文快照中的 Pi 採用 Unicode 與空白正規化，沒有使用相似度門檻。替換位置在正規化內容中計算，再按行套回原始位元組，讓未修改行保留原有空白。這個安排把「方便匹配的表示」與「需要保存的原檔」分開。[來源：論文 §8.4](https://arxiv.org/html/2609.00006v1#S8.SS4)

本書據此推導一個失敗案例：工具為了找到運費條件，先統一整份檔案的換行，再把正規化版本直接寫回。條件雖然改對，差異卻變成數百行，掩蓋了真正修改。較清楚的契約應說明正規化只用於匹配，還是也會改寫檔案；讀者不能從「支援空白差異」推定未修改內容一定保留。

縮排又有另一層意義。論文記錄 Aider 的相對縮排做法：先表示相鄰行之間的縮排增減，再重建絕對縮排。這讓編輯區塊較能適應不同外層縮排，不必把每一行都綁死在相同空格數。但它沒有消除語意風險；Python 中若區塊層次改錯，文字可以套用，行為仍會改變。[來源：論文 §8.4](https://arxiv.org/html/2609.00006v1#S8.SS4)

選擇這些機制前，先確認失敗確實來自表示差異，而非定位錯誤。驗證時同時看三件事：預期區塊是否匹配、未修改內容是否保留，以及修改後的語法與行為是否正確。提高匹配容忍度只能改善第一項，不能替後兩項提供保證。
