# 04 Agent 何時該停下來

停止只表示這次執行不再繼續，不代表任務成功。Harness 應保存停止原因，並用最新證據判斷能否宣稱完成。

本章讓你為修錯任務訂出停止條件，分清楚完成、等待、失敗與預算用完。

## 「沒有工具要求」不等於「修好了」

延續本書自編的運費例子：`shipping_fee` 要讓金額滿 1,000 元免運。模型讀過 `price.py` 後回答「把大於改成大於等於即可」，但沒有要求工具修改。對最簡單的迴圈而言，模型沒有再呼叫工具，可以結束回合；對使用者的任務而言，檔案還沒有修好。

因此，至少要分開兩個問題。第一個是流程是否繼續：還有工具要求、等待中的工作或可用預算嗎？第二個是任務是否達標：需要的修改是否完成，測試是否檢查了修改後的版本？兩者混在一起，就容易把自然語言的完成宣告當作事實。

論文 §6 描述了各系統不同的退出方式。論文快照中的 Aider 依回應串流與待處理的修正來結束；其他工具呼叫迴圈可能依模型的結束訊號退出。這些機制沒有共同保證「使用者目標已達成」。[來源：論文 §6](https://arxiv.org/html/2609.00006v1#S6)

## 先寫出可以核對的完成條件

對運費任務，本書採用以下完成條件：

1. `price.py` 的判斷符合「滿 1,000 元免運」。
2. 修改後，999、1,000、1,001 元的結果依序為 60、0、0。
3. 完成回覆交代修改內容及實際執行的檢查。

三個條件各有證據來源。第一項看檔案差異，第二項看測試結果，第三項看交付說明。模型的自信程度不是其中一項，因為自信無法替代檔案或測試。

測試也有範圍。這三個金額檢查的是門檻附近的行為，沒有涵蓋負數、非數字或幣別。若原任務沒有要求這些功能，不必擴大修正；但也不能把三項檢查寫成「所有情況都正確」。完成條件應對齊使用者需求，並保留驗證邊界。

## 用停止原因保留尚未做完的事

下表是本書的教學設計，不是某一產品的列舉值。名稱可以改，區別應保留。

| 停止原因 | 典型情況 | 回覆應交代什麼 |
|---|---|---|
| 已完成 | 修改後的指定檢查通過 | 修改、驗證及限制 |
| 等待資訊或權限 | 缺少必要輸入，或操作不獲准 | 缺少什麼、已做什麼 |
| 工具無法繼續 | 檔案系統錯誤，沒有可行替代 | 錯誤、已產生的效果 |
| 預算用完 | 達到步數、時間或費用上限 | 目前成果、未完成項目 |
| 使用者取消 | 使用者要求停止 | 已停止部分與仍在結束的工作 |

假設程式已改好，但執行環境沒有測試工具，應回報「已修改，尚未驗證」。若只用成功或失敗兩種狀態，這種中間結果容易被壓成誤導的結論。保留停止原因，也讓後續接手者知道應從哪一步開始。

停止時還要考慮已啟動的工作。主迴圈退出，不會自動終止子程序。若測試仍在背景執行，Harness 必須等待、取消或明確移交；不能顯示「已全部停止」卻留下仍會寫檔的工作。這是本書依流程責任推導的設計要求。

## 上限避免無止境執行，卻不判斷品質

若把一步定義為一次模型呼叫，步數上限就限制呼叫次數；有些系統會用其他計數方式。本書模擬器計算的是固定動作數。時間上限限制經過時間，費用上限限制花費，它們防止不同形式的失控。一次工具若卡住很久，步數可能仍停在一；只設步數上限，不能限制等待時間。

上限應在下一個有成本的動作開始前檢查。例如模型已呼叫三次、上限也是三次，就不要再啟動第四次。若系統允許最後一次整理回覆，這筆額外成本應預先納入規則。論文快照中的 Hermes 提供預算到期後的整理機會；這是一種產品取捨，並非所有系統的共同做法。[來源：論文 §6.2](https://arxiv.org/html/2609.00006v1#S6.SS2)

費用通常在請求結束後才取得確切用量。因此，「本輪前尚未超額」不保證本輪完成後仍在額度內。若必須嚴格控制總額，就要另限制單次請求、預留空間或使用供應端限制。單純加總既有費用只是一道檢查，不能冒稱完整的費用保證。

論文作者建議先加入便宜的上限，再依實際失敗模式決定是否需要複雜偵測。這是工程建議；論文沒有證明某個固定步數適合所有任務。[來源：論文 §16.9](https://arxiv.org/html/2609.00006v1#S16.SS9)

## 重複不一定卡住，要看新資訊

連續三次讀取同一個檔案，可能是模型忘記自己讀過，也可能是另一個工作者正在更新檔案。相同工具名稱不足以判斷。即使參數相同，外部狀態也可能已經改變。

較有用的線索是：相同要求是否持續得到相同錯誤，下一次嘗試是否改變了條件。若編輯工具三次回報「找到兩處」，模型卻一直提交相同舊字串，就沒有縮小範圍，也沒有獲得新證據。此時可以提示模型增加定位內容，並限制相同失敗的重試次數。

論文快照中的 OpenHands 偵測多種重複模式；OpenCode 則將連續相同工具要求交給權限流程判斷；另一些系統沒有自動卡住偵測。這些差異說明停止策略需要配合使用情境，不能把「有偵測」直接當作效能較好的證據。[來源：論文 §6.2](https://arxiv.org/html/2609.00006v1#S6.SS2)

## 結束前檢查證據的新舊

假設 10:00 的測試通過，10:01 又修改了運費判斷，10:02 模型準備結束。紀錄中雖然存在成功測試，卻沒有檢查最新修改。最簡單的結束檢查是確認：最後一次影響程式的修改之後，是否產生了適當的驗證結果。

論文快照中的 Hermes 有結束前驗證守門機制。如果回合修改了程式卻缺少新驗證證據，就把純文字結束改成繼續工作。這能攔住某一類過早完成，不能保證測試本身足夠，也不能證明所有需求都被涵蓋。[來源：論文 §6.2](https://arxiv.org/html/2609.00006v1#S6.SS2)

驗證也有成本。如果沒有執行測試的環境，無限制要求「再驗證」只會製造另一種迴圈。此時應如實停止在「已修改、未驗證」，並留下缺少的環境條件。

## 寫一份能讓人接手的停止說明

對使用者有用的停止說明，應回答「目前到了哪裡」與「還差什麼」。例如：「已將門檻改為大於等於 1,000；測試工具啟動失敗，因此尚未確認三個邊界案例。」這比「遇到問題」更容易接手，也沒有把修改誇大成驗證完成。

如果原因是步數用完，說明可以保留最後一份有效證據，以及下一個必要動作。不要把所有嘗試逐條倒回給使用者；應指出與接續工作有關的事實，例如編輯已成功、檢查尚未開始。重新啟動時，仍要確認檔案沒有在停止期間改變。

當多個停止條件同時成立，也應避免丟失資訊。例如模型剛提出完成，而時間上限也剛到，系統可以記錄執行已停止，同時另記完成證據是否足夠。若測試已通過，預算到期不會使既有證據失效；若測試尚未執行，模型提出完成也不會補上它。

這些區分不要求複雜的狀態框架。最小設計可以只有停止原因、已完成動作和待辦三個欄位。真正需要保留的是事實，讓畫面、紀錄與後續流程不必從一段模糊文字重新猜測。

## 進階：外層驗證不能無限重啟內層工作

前面的停止檢查放在一次工作裡。還有另一種安排：先讓 agent 完成一趟，再由外層檢查目標；若未達標，就把缺口交回，啟動下一趟。外層關心整體目標，內層負責工具動作，兩者的停止條件不同。

論文以 OpenHands 的目標流程說明外層驗證：一趟執行結束後，由模型判斷是否繼續提示或停止。Hermes 的結束前守門則從內層退出位置攔住過早完成。這是兩個不同的介入位置，不代表模型判斷器比測試更可靠，也不代表每個回合都需要再呼叫一個模型。[來源：論文 §6.1](https://arxiv.org/html/2609.00006v1#S6.SS1)

以下是本書對運費案例的教學推導。若外層看到「已修改，但測試未跑」，可要求內層補測試。若測試失敗，外層應帶回實際失敗輸入與結果。只有「再努力修好」的重啟訊息沒有提供新資訊，容易重複上一趟的錯誤。

外層也需要總預算。假設內層每趟最多五步，外層卻允許無限重啟，整個系統依然沒有上限。應共同計入各趟執行、驗證與重試成本，並保留已完成動作，避免每次重新修改已正確的檔案。

最後要防止驗證標準被工作過程悄悄降低。若 agent 把失敗的 1,000 元案例刪除，再回報剩餘測試全過，外層不能只看成功訊號。運費需求與必測輸入應獨立保留，再核對結果是否涵蓋它們。外層的價值在於守住目標與證據的關係；若只是讓另一個模型重讀相同成功宣告，就沒有增加可靠的驗證。

若驗證器本身無法啟動，也要回報「無法驗證」，不要當成修正失敗而重啟編輯。錯誤發生在檢查環境時，繼續改程式不會改善證據；先辨認哪一層失敗，才能決定恢復哪一層。

## 用同一條紀錄判斷不同結局

執行[工作迴圈實驗](examples/loop_demo.py)，比較正常完成、工具失敗與步數上限三種路徑。檢查結束原因與實際紀錄是否一致，尤其留意「預算用完」不應顯示成成功。
