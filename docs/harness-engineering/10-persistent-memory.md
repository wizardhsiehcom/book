# 10 哪些知識應留到下一次任務

跨任務記憶應保存穩定、可追溯而且仍適用的知識。某次工作做到了哪裡，先留在工作紀錄；不要把暫時狀態直接升格成長期規則。

## 同一句話，保存多久會改變用途

本書教學例子中，「已把 `>` 改成 `>=`」對接續目前任務很有用。幾週後再開新任務，這句話卻不一定值得放進提示。檔案可能已經重構，修改也可能被撤回。它應留在版本差異或工作紀錄，供需要時查閱。

相較之下，「運費規則以折扣後金額判斷」若有正式需求支持，就可能對下一次任務有用。但這仍不是永久真理。規則可能改變，記憶必須能回答：從哪裡得知、適用哪個專案、何時核對，以及什麼情況需要重新確認。

上一章的對話壓縮，是為了讓同一次任務繼續。持久記憶則把資訊帶到之後的任務。兩者都可能使用摘要，但保存期限、讀取時機與錯誤後果不同。壓縮摘要漏掉一步，影響目前工作；長期記憶寫錯一條規則，可能持續影響多次工作。

## 先分開四種資訊

對一個小型專案，單純的 Markdown 檔就能保存記憶。真正需要設計的是內容邊界，而不是先選資料庫。

| 資訊 | 本例 | 較合適的位置 |
|---|---|---|
| 穩定的專案慣例 | 金額使用整數元，測試放在指定目錄 | 專案指示或可查證記憶 |
| 正式業務規則 | 滿 1000 元免運，包含門檻 | 需求來源；記憶保留來源索引 |
| 本次工作進度 | 條件已修改，測試尚未跑 | 任務紀錄或交接摘要 |
| 未證實猜測 | 可能是浮點誤差 | 調查紀錄，明示尚未證實 |

這個分類是本書的教學方法。它避免把「模型曾說過」當作「專案已接受」。如果記憶來源只是一則猜測，反覆載入只會讓猜測看起來更熟悉，不會增加證據。

也要避免把私人資料當作方便的上下文。密碼、API 金鑰及無關個人資訊不應因為曾出現在輸出中就存入記憶。需要保存的通常是取得資料的方法或設定位置，而不是秘密本身。

## 一則記憶要能回到證據

以下為本書教學範例，不是要求所有 Harness 使用相同格式。來源名稱也屬於案例設定。

```text
範圍：此教學專案的運費計算
事實：滿 1000 元免運，門檻包含 1000。
來源：使用者本次需求；price.py 的邊界測試
核對狀態：需求已確認；測試結果另見本次工作紀錄
使用時機：修改 shipping_fee 或結帳金額規則時
重新確認：需求改版、金額單位改變，或測試與規則衝突時
```

注意「需求已確認」沒有被擴寫成「程式已正確實作」。規則、實作與驗證結果分開，下一次 Agent 才知道要信任哪一部分。如果測試仍未執行，不能把測試檔存在當成驗證通過。

來源不一定要把整段對話複製進去。檔案路徑、版本或可查詢的紀錄識別碼通常更有用。記憶負責引導下一次找對證據，證據本體負責承受查核。當來源消失或版本不符，系統應降低信任並重新讀取，而不是把舊摘要當作替代品。

## 誰寫入，誰審核，是兩個決定

論文 §9.6 把持久記憶的重要差異放在寫入路徑。論文快照中的 Codex 使用背景流程，先從工作紀錄擷取，再由受限的內部 agent 整理成檔案。Gemini CLI 則把部分擷取結果送進待審核區，讓使用者查看並套用。兩者都能自動提出記憶，正式保存前的把關方式卻不同。

自動整理減少人工維護，但錯誤或過時內容可能直接進入下次任務。人工審核提高可見性，但待審項目可能堆積，使用者也未必逐條仔細閱讀。選擇時要看記憶的後果：一條格式偏好寫錯，與一條部署規則寫錯，所需把關程度不同。

論文也記錄了容量受限的 Markdown 記憶。以 Hermes 的快照為例，系統在工作開始時載入固定快照；中途寫入磁碟，不立刻改變已載入的內容。這能維持提示快取的穩定，但必須讓使用者與 agent 明白：已保存不等於本次請求立即讀到。

所以至少要分辨三個時刻：候選記憶被提出、內容被接受並寫入、下一個任務實際載入。若把三者都叫作「記住了」，除錯時就很難知道問題出在擷取、保存還是讀取。

## 記憶需要更新與刪除

假設免運門檻後來改為 1200。最危險的更新方式，是新增「滿 1200 免運」，卻留下同樣有效的「滿 1000 免運」。搜尋時兩則都可能出現，模型只好猜哪個較新。更新應明確取代舊規則，或標示舊規則的有效期間。

同樣地，記憶不應只按「被讀取很多次」判定價值。過時規則也可能經常被讀到。使用頻率可以幫助排序，仍要配合來源、版本及適用範圍。若某項規則與新需求衝突，Agent 應指出差異，回到權威來源確認。

儲存位置也影響治理。寫進受版本管理的專案指示，團隊可以一起審查；寫進個人記憶，則可能只對一位使用者可見。若團隊規則只存在某位 agent 的私人記憶中，別人很難重現它的決定。公共規則應有公共來源，個人偏好才適合個人作用範圍。

此外，記憶內容仍可能帶有惡意指令。從網頁擷取到一句要求外傳資料的文字，不會因為寫進 Markdown 就變成可信規則。擷取流程要保留來源角色，讀取流程也不能讓記憶繞過工具權限。記憶讓內容活得更久，並不自動提高內容的授權等級。

## 小專案先用可追查的少量記憶

若 Agent 每次都花時間重新找測試命令，可以先保存測試入口與適用環境，再量測是否減少重複查找。若跨任務沒有穩定重複資訊，就不必先建自動擷取管線。

新增記憶後，可用另一個乾淨任務檢查三件事：Agent 是否在適當時機找到它、是否回到來源核對，以及遇到矛盾時是否更新而非硬套。這樣的檢查比「記憶檔有內容」更能說明價值。

論文觀察到樣本主要使用可讀檔案與確定性的查找機制，但這不是所有記憶系統的上限。若大量跨專案資料確實需要語意查找，應先測試是否比現有全文搜尋更有幫助。保存什麼、誰能改、如何淘汰，仍比檢索技術的名稱更早需要決定。

## 讀到記憶後，仍要核對適用範圍

假設另一個專案也有 `shipping_fee`，卻以分為單位計算。只按函式名稱取回「門檻 1000」就可能套錯規則。記憶的專案範圍、單位與來源，必須一同出現在讀取結果中。檢索命中不等於內容適用。

當兩則記憶衝突時，也不宜只選較新的那則。較新的內容可能來自較弱證據，或屬於另一個環境。Agent 應比較來源及適用條件，必要時回到正式需求。這讓記憶扮演查找助手，而不是取代判斷的另一層權威。

## 進階：把擷取與正式寫入分成兩段

自動記憶若直接把每次對話摘要貼入同一檔案，內容很快就會重複或互相矛盾。論文快照中的 Codex 分成兩段：先從個別工作紀錄擷取結構化候選，再把多份候選整理成可供後續使用的檔案。中間以資料庫追蹤工作，包含有期限的工作占用、失敗後延遲重試及秘密遮蔽。整理者則在受限環境檢視檔案差異。[來源：論文 §9.6](https://arxiv.org/html/2609.00006v1#S9.SS6)

兩段式流程把兩個問題拆開：這次紀錄有哪些可保存資訊？它們與既有知識應如何合併？工作占用避免多個背景工作者同時處理同一項目；到期後能重新派工，避免工作者中斷就永遠卡住。不過，能重試不代表內容只會寫入一次。以下是本書推導：若擷取已完成、狀態更新卻失敗，重試可能再次提出同一則門檻規則。整合端仍需辨認來源與已處理狀態，不能只把文字追加到檔案。

人工審核的待辦匣也有版本問題。論文中的 Gemini CLI 讓使用者審查擷取出的補丁。假設候選提出「滿 1000 免運」，使用者批准前需求已改為 1200，原候選即使忠實反映舊對話，也不再適合寫入。審核因此不只是檢查句子是否正確，還要核對來源版本與目前規則。這個案例是本書對非同步寫入的推導，不是論文回報的事故。

小專案可先用人工維護的短檔案，免去背景工作排程。當跨任務重複資訊增加，再考慮自動提出候選；當候選數量超出人工整理能力，才評估自動合併。無論採哪一種查找技術，都應分別測試擷取正確性、合併衝突及載入時效，不能用一次成功回憶替整條記憶流程背書。
