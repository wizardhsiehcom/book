# 13 新能力應接在哪一層

先判斷缺的是知識、可執行動作，還是系統整合，再選擇擴充方式。把所有需求都做成新工具，會增加模型的選擇負擔，也讓權限與維護更難管理。

## 同一句「支援運費檢查」，可能是四種需求

在本書教學例子中，代理已有讀檔、改檔與執行測試的能力。若團隊只想讓它每次檢查門檻上下兩側，就缺一份可重複使用的工作說明。新增工具未必帶來價值。

若團隊要查詢另一個系統中的正式運費規則，就缺一個可驗證的外部資料入口。若要在每次改檔後自動記錄差異，就需要在執行流程的特定時機掛上動作。若要把上述能力一起分發給團隊，才涉及套件安裝與版本管理。

這四種需求分別關乎操作知識、工具能力、流程事件及分發。它們可以組合，但不要混成一個沒有邊界的「擴充功能」。先分清責任，後續才知道哪一層失敗，以及誰能修正。

## 規則與技能教模型怎麼工作

專案規則適合放持續適用的要求，例如金額單位、測試入口及禁止修改的檔案。技能則把一種可重複執行的工作整理成可發現、可按需讀取的內容。論文中的技能常以 `SKILL.md` 為入口，配合名稱、說明、參考資料或腳本。

可以把技能想成附帶材料的操作手冊。運費技能可能說明：先確認門檻是否包含等號，再檢查 999、1000、1001，最後回報實際執行的測試。這份手冊增加的是程序知識，不會憑空產生讀取外部系統的權限。

技能也不是每次都要完整載入。系統可先把名稱與適用條件放進目錄，等任務匹配時才讀正文，需要時再讀附帶材料。這稱為漸進揭露：先讓模型知道有什麼，再取回需要的細節。它能控制上下文成本，但技能描述必須足以讓模型選對。

如果技能叫「最佳實踐大全」，模型很難判斷何時使用。如果描述寫明「檢查金額門檻的包含關係與邊界測試」，用途就比較清楚。內容則要說明輸入、完成條件與不適用情況，避免把一次性的修正寫成永遠適用的命令。

## 工具提供動作，MCP 提供連接方式

工具是可由執行系統執行的具體操作，例如查詢運費規則、讀取檔案或執行一組測試。它需要明確輸入、輸出與失敗回傳。模型必須知道查詢結果來自哪個版本，查不到時是回傳空值、錯誤，還是要求補資料。

MCP（讓執行系統連接外部工具、資源與提示的共同通訊規則）全名是 Model Context Protocol。它不是運費規則本身，也不會替工具保證安全或正確。即使兩端都支援 MCP，仍要處理身分認證、可見工具、權限及錯誤。

論文 §12.4 記錄多數樣本支援 MCP，但支援範圍並不一致。有些不只支援工具，也支援資源與提示。這提醒我們：「支援某協定」只是開始，還要確認需要的功能與傳輸方式是否相容。本章不提供當前產品設定指令，因為論文描述的是指定快照。

若外部系統已有穩定的命令列工具，一份清楚的使用說明可能足夠。若多個執行系統都要連接同一服務，標準協定可能減少重複整合。選擇應由使用情境決定，不是因為工具有了協定名稱就更適合。

## MCP、ACP 與 A2A 接在不同邊界

協定是系統之間約定的通訊規則。下列三種協定連接的對象不同，不能互相代替：

- **MCP：**讓執行系統使用外部工具、資源與提示。
- **ACP（讓編輯器或上層系統連接代理的通訊規則）：**全名是 Agent Client Protocol。
- **A2A（讓不同代理系統交換任務與結果的通訊規則）：**全名是 Agent2Agent。

對運費案例，查詢正式規則的外部工具可以透過 MCP 連接。若你希望從編輯器操作同一個修錯代理，ACP 是另一個整合邊界。若另一個遠端代理系統要派任務給它，才會進入跨系統代理通訊的問題。這些都是角色說明，不表示每個部署都需要三種協定。

論文快照中的 OpenHands 也透過 ACP 使用外部執行系統作為後端。這說明相同協定可服務編輯器，也可服務代跑其他執行系統的上層系統。它沒有把外部工具呼叫、代理工作與內部子代理排程變成同一件事。[來源：論文 §13.3](https://arxiv.org/html/2609.00006v1#S13.SS3)

自己的子代理若都在同一個處理程序內，函式、佇列或其他本地通訊可能已足夠。不要只因名稱有「代理」就加入跨網路協定。需要跨邊界時，再核對取消、權限、串流與狀態回報是否受支援；協定相容也不能證明任務已做對。

## 流程事件適合固定時機的檢查

事件掛鉤（hook）是在特定事件前後自動執行的擴充動作，例如工具執行前檢查路徑，或執行後寫入紀錄。與技能不同，它可以由系統事件觸發，不必每次等模型記得呼叫。

假設團隊要求所有檔案寫入都留下差異紀錄，把要求放在提示中只能請模型記得做。若執行系統在寫入成功後自動記錄，觸發點就更明確。但仍要定義記錄失敗時怎麼辦，以及哪些工具路徑會經過這個掛鉤。

掛鉤可能改寫參數或拒絕動作，因此不只是裝飾。若它修改了工具目標，權限審查必須針對實際參數重新判斷。多個掛鉤的執行順序、逾時與錯誤處理，也會影響結果。把檢查移到掛鉤，不會讓這些責任消失。

| 需求 | 優先考慮的入口 | 驗證重點 |
|---|---|---|
| 每次遵守金額單位 | 專案規則 | 載入範圍與衝突處理 |
| 重複做邊界檢查 | 技能 | 任務能否選到，步驟能否完成 |
| 查外部正式規則 | 工具，必要時透過 MCP | 認證、版本、錯誤與權限 |
| 每次寫入後記錄 | 事件掛鉤 | 觸發完整性、順序與失敗處理 |
| 一起分發上述能力 | 外掛套件 | 來源、依賴、版本及移除方式 |

這張表是本書的選擇指南，不是互斥分類。技能可以附帶腳本，外掛也可以同時提供工具與掛鉤；重點是每一項能力仍有清楚的責任。

## 外掛把能力包起來，也帶來維護責任

外掛（plugin，可安裝的擴充套件）常把工具、技能、設定與事件掛鉤包成可安裝單位。它解決發現與分發問題，卻增加另一組工作：安裝哪些依賴、如何確認來源、版本升級會改變什麼，以及移除後會留下哪些設定。

論文記錄了多種外掛方式。OpenClaw 使用明確的套件描述與公開介面；Pi 把許多能力留在執行時載入的擴充模組；一些系統採用其他產品已存在的格式。這些做法各有維護成本，不能只因格式相同就推定行為完全相容。

公開介面很重要，因為外掛若直接依賴核心內部檔案，核心一次重構就可能使它失效。對只有一個內部使用者的小工具，簡單介面可能足夠；對公開分發的外掛，版本與相容性就成為實際承諾。第 15 章會接著討論平台責任。

外掛來源也屬於信任判斷。技能可能含有會執行的腳本，工具描述可能影響模型選擇，掛鉤則可能攔截或改寫操作。安裝前應知道它會讀寫哪些資源，以及來自哪個來源。安全檢查不能只看副檔名是 Markdown 還是程式碼。

## 先做能解決當前缺口的擴充

對運費案例，先寫一份短技能，讓代理在既有工具下確認門檻與測試。如果實際任務反覆卡在取得正式規則，再補查詢工具。如果多人需要相同能力，再考慮分發成套件。每一步都有可觀察的原因，較容易判斷是否值得維護。

驗收時也要分層。技能要看是否引導出正確工作；工具要檢查輸入與失敗回傳；掛鉤要確認每條適用路徑都觸發；外掛要測試安裝、升級與移除。只看到模型說「我已使用技能」，不能證明整條流程有效。

論文作者建議以技能處理能力模板，以 MCP 處理外部整合。這是有條件的設計起點，不是要求每個小專案都建立技能目錄與伺服器。若一次性的幾句說明已足夠，就先保留簡單做法；等重複需求出現，再固定為擴充能力。

停用擴充也應列入驗收。若移除技能後工具還留著，或卸載外掛後掛鉤仍在執行，使用者就難以理解系統目前的能力。清楚列出載入來源與生效範圍，能讓新增與移除都可查證。

## 進階：發現、適用與獲准是三道不同的關卡

系統找到一份技能，不代表它現在能用。論文記錄 OpenClaw 會依必要程式、環境變數與作業系統篩選技能；Claude Code 與 OpenHands 則可在碰到特定路徑時載入相關技能。前者處理執行條件，後者處理任務相關性，兩者都不能代替執行時的授權判斷。[來源：論文 §12.5](https://arxiv.org/html/2609.00006v1#S12.SS5)

以下是本書教學例子。運費技能需要一個查詢正式規則的程式。系統發現技能檔，但機器沒有該程式，應提示缺少依賴，而不是讓模型反覆嘗試不存在的命令。程式已安裝但帳號無權讀取某份規則時，則是授權問題。把兩種失敗混在一起，容易導致無意義的重新安裝，甚至要求不必要的權限。

按需載入還有一個成本轉移：初始提示變小，但模型必須正確選擇並讀取技能。論文 §12.5 描述多數採用者先載入名稱、說明等資料，再按需取回正文；這種做法需要清楚的適用描述。若兩份技能描述過於相近，模型可能選錯版本。檢查時應從真實任務開始，觀察找到哪份技能，而不只直接指定技能後測試步驟。

技能若能由代理自動產生，審核就要延伸到分發前。論文記錄背景工作者從已完成任務產生或修補技能，也記錄信任分級、掃描及待審核流程。一次成功修正可提供候選經驗，不能直接證明流程適合其他專案。對本例，應把「檢查門檻是否含等號」抽成可重用步驟，不能把「所有專案都把 > 改成 >=」發布成規則。[來源：論文 §12.5](https://arxiv.org/html/2609.00006v1#S12.SS5)

當擴充只供個人一次使用，明確說明與本地檢查可能足夠；當它會自動載入或分發到多個專案，就要驗證依賴、版本及撤回方式。載入愈自動，錯誤擴散愈快，驗收也應涵蓋不適用情境。
